# 설계 결정 기록 (Architecture Decision Record)

안동잇다 개발 과정에서 내린 기술적 판단과 그 근거를 기록한다.
"무엇을 했는가"보다 "왜 그렇게 했는가"를 남기는 것이 목적이다.

---

## ADR-001. 백엔드 서버와 데이터베이스를 두지 않는다

**결정일**: 2026-07-23
**상태**: 확정

### 배경
안동잇다는 공공 OpenAPI를 조합해 정보를 제공하는 서비스다.
원천 데이터를 직접 생산하지 않고, 외부 API의 데이터를 가공·결합해 보여주는 구조다.

### 결정
별도 백엔드 서버(Spring Boot 등)와 RDB를 두지 않는다.
Nuxt 하나로 프론트엔드와 서버 API 라우트를 모두 처리하고, Vercel에 배포한다.

```
브라우저 → Nuxt server/api (프록시 + 캐싱) → 공공 OpenAPI
```

### 근거
- **원천 데이터를 소유하지 않는다.** 관광지·버스 정보는 공공 API가 원본이며,
  이를 DB에 복제해두면 갱신 시점 관리라는 문제만 새로 생긴다.
- **데이터 규모가 작다.** 안동 관광지는 100개 내외 수준으로, DB가 필요한 규모가 아니다.
- **개발 리소스를 핵심 기능에 집중한다.** 1인 개발이고 마감이 정해져 있다.
  서버 구축·배포·운영에 드는 시간을 기능 완성도에 쓰는 편이 심사 배점상으로도 유리하다.
  (심사 기준: 서비스 완성도 30점 = 기획력 30점)

### 트레이드오프
- 응답 속도가 외부 API 성능에 종속된다 → 서버 라우트 캐싱으로 완화
- 외부 API 장애 시 서비스가 함께 영향받는다 → 폴백 UI 필요
- 사용자별 데이터(찜하기 등)를 서버에 저장할 수 없다 → localStorage로 처리

## ADR-002. 서버 API 라우트를 반드시 경유한다

**결정일**: 2026-07-23
**상태**: 확정

### 결정
모든 외부 API 호출은 브라우저에서 직접 하지 않고 Nuxt `server/api`를 경유한다.

### 근거
세 가지 문제가 동시에 해결되기 때문이다.

1. **인증키 보호** — TourAPI 인증키가 클라이언트 번들에 노출되면 안 된다.
   서버에서만 `.env`의 키를 참조한다.
2. **Mixed Content 차단 회피** — 안동시 버스 API(`http://bus.andong.go.kr`)와
   LocgoHub API(`http://apis.data.go.kr`)가 모두 http다.
   https로 배포되는 페이지에서 브라우저가 http 요청을 차단한다.
   서버 간 통신은 이 제약을 받지 않는다.
3. **CORS** — 공공 API 대부분이 브라우저 직접 호출을 허용하지 않는다.

## ADR-003. 원천 데이터는 실시간 호출, 자체 가공 데이터만 정적 관리

**결정일**: 2026-07-23
**상태**: 확정

### 배경
공모전 심사 요건에 다음 조항이 있다.

> 데이터 활용은 한국관광공사 OpenAPI 형태만 인정되며,
> 단순 파일 데이터(Excel, CSV 등) 다운로드 활용은 인정되지 않아 심사에서 제외됩니다.

성능만 생각하면 관광지 데이터를 미리 받아 JSON으로 박아두는 편이 빠르지만,
이는 위 조항에 저촉될 소지가 있다.

### 결정
데이터를 두 종류로 나눠 다르게 취급한다.

| 구분 | 처리 방식 | 예시 |
|---|---|---|
| **공공 API 원천 데이터** | 런타임에 실제 호출 + 서버 캐싱 | 관광지, 음식점, 축제, 버스 도착정보 |
| **자체 생성 가공 데이터** | 정적 JSON 관리 | 관광지↔정류장 매핑 |

캐싱은 성능 최적화이지 데이터 사전 다운로드가 아니다.
매핑 테이블은 TourAPI가 제공하지 않는, 직접 만들어낸 부가가치 데이터다.

### 캐시 정책
| 데이터 | TTL | 근거 |
|---|---|---|
| 버스 실시간 도착 | 캐시 없음 | 실시간성이 기능의 본질 |
| 관광지·음식점 목록 | 6시간 | 변경 빈도 낮음 |
| 중심관광지 순위 | 1일 | 월 1회 갱신(매월 8일) |
| 축제·행사 | 6시간 | 일 단위 변경 |

## ADR-004. 중심관광지 API를 데이터 뼈대로 삼는다

**결정일**: 2026-07-23
**상태**: 확정

### 배경
국문 관광정보 서비스(KorService2)로 안동 데이터를 조회한 결과,
안동의 대표 관광지가 데이터셋에 없다는 문제를 발견했다.

| 조회 | 개수 | 문제 |
|---|---|---|
| KorService2 지역기반 관광지(contentTypeId=12) | 64 | 하회마을·도산서원·월영교 없음 |
| KorService2 지역기반 문화시설(contentTypeId=14) | 12 | 박물관 위주 |

반면 기초지자체 중심관광지 정보(LocgoHubTarService1)에는 전부 존재했다.

> **정정 (2026-08-02)** — 원문에 "키워드 검색(searchKeyword2)으로도 확인되지
> 않았다"고 적었으나 **틀렸다.** `searchKeyword2`로 이름을 검색하면 전부 있고
> 이미지도 전부 있다.
>
> 없는 게 아니라 **`areacode`·`sigungucode`가 빈 값**이라 지역 기반 조회
> (`areaBasedList2`)의 그물에 안 걸리는 것이다. 한국관광공사 쪽 데이터 결함이다.
>
> ```
> 하회마을 894027 · 도산서원 126200 · 월영교 988449
> 병산서원 126227 · 봉정사 126158 · 만휴정 126998   — 전부 areacode ''
> ```
>
> 이 ADR의 **결정 자체는 유효하다.** LocgoHub는 순위를 주고 KorService2는
> 이름 검색이 필요하므로 여전히 LocgoHub가 뼈대다. 다만 "KorService2에는
> 없다"를 전제로 한 서술(아래 ADR-021 포함)은 "지역 조회로는 안 잡힌다"로 읽어야 한다.
> 보충 구현은 `backfillImages()`. → ADR-022 부수 효과

```
1위 안동하회마을 / 2위 월영교 / 3위 병산서원 / 4위 도산서원 / 5위 봉정사
```

### 결정
**LocgoHubTarService1을 관광지 데이터의 뼈대로 삼고,
KorService2를 상세 정보 보강용으로 결합한다.**

### 근거
두 API는 서로의 결핍을 채운다.

| API | 가진 것 | 없는 것 |
|---|---|---|
| LocgoHub | 실제 방문 기반 순위, 좌표, 핵심 관광지 | 설명, 이미지, 운영시간 |
| KorService2 | 설명, 이미지, 주소, 운영시간 | 대표 관광지, 인기도 |

두 API를 결합하는 것 자체가 제안서에서 밝힌 "데이터 융합" 전략의 실현이며,
심사 항목의 데이터 활용 적절성(20점)에 대한 근거가 된다.

### 조인 방법
두 API 사이에 공통 키가 없다.
(LocgoHub: `hubTatsCd` 해시 / KorService2: `contentid`)

좌표와 이름으로 매칭한다.
1. 좌표 거리 200m 이내 AND 이름 유사도 임계값 이상 → 동일 장소로 판정
2. 매칭 성공 → 순위 + 상세정보 병합
3. 매칭 실패 → LocgoHub 단독 표시, 이미지는 폴백 처리

## ADR-005. API별로 지역 코드 체계가 다르다

**결정일**: 2026-07-23
**상태**: 확정 (주의사항)

### 문제
같은 "안동시"를 가리키는 코드가 API마다 다르다.
이를 모르고 호출하면 빈 응답을 받는다.

| API | 파라미터 | 안동시 값 |
|---|---|---|
| KorService2 (국문 관광정보) | `areaCode` + `sigunguCode` | `35` + `11` |
| LocgoHubTarService1 (중심관광지) | `areaCd` + `signguCd` | `47` + `47170` |

파라미터 이름 자체도 다르다 (`areaCode` vs `areaCd`).

### 대응
API별 지역 코드를 상수로 분리해 관리한다.

```ts
// constants/region.ts
export const ANDONG = {
  korService: { areaCode: '35', sigunguCode: '11' },
  locgoHub:   { areaCd: '47',  signguCd: '47170' },
} as const
```

## ADR-006. 버스 도착 시간은 계산하지 않고 API 값을 그대로 쓴다

**결정일**: 2026-07-23
**상태**: 확정 (당초 기획 변경)

### 배경
제안서에서는 "남은 정류장 수 → N분 후 계산"으로 기획했다.
API 명세서에도 응답 필드가 `rstop`(남은정류장), `provideType`(도착예정)으로 기재되어 있다.

### 실제 응답
명세서와 실제 응답 필드가 달랐다.

```json
{
  "routeNum": "212",
  "routeNm": "212(국립경국대-도청)",
  "via": "국립경국대 -> 정부경북지방합동청사",
  "predictTm": 3.0,
  "remainStation": 4
}
```

`predictTm`에 도착 예정 시간이 분 단위로 이미 계산되어 온다.

### 결정
자체 계산 로직을 만들지 않고 `predictTm`을 그대로 표시한다.
`remainStation`은 보조 정보로 함께 노출한다.

### 근거
- 추정 계산보다 운영 시스템의 값이 정확하다
- 계산 로직 자체가 불필요해져 구현 범위가 줄어든다

### 예외 처리
`predictTm`이 null로 오는 경우(차량 위치 미확보)를 대비해
`remainStation` 기반 대체 표시 또는 "곧 도착" 폴백을 둔다.

### 부수 발견
명세서에 없던 `via` 필드(기점 → 종점)가 실제로는 응답에 포함된다.
여행자가 버스 정보에서 가장 혼란스러워하는 "이 버스가 내가 가려는 방향인가"를
해결해주는 정보이므로, 화면에 우선 노출한다.

## ADR-007. 막차·귀로 안내를 실시간 3단 결합으로 구현한다

**결정일**: 2026-07-23 (제외) → **2026-07-29 번복**
**상태**: 확정 (구현)

### 최초 판단 (2026-07-23) — 오류
안동시 버스 API 5개 오퍼레이션 어디에도 운행 시간표·막차 필드가 없다는 이유로
막차 안내 기능을 MVP에서 제외했다.

### 번복 사유 (2026-07-29)
명세서만 보고 판단한 것이 잘못이었다. 노선 목록(`tab=3`)을 실제로 호출해보니
**방향별 노선이 별도 routeId로 등록되어 있었다.**

```
354300006  210(교보생명-하회마을)     ← 가는 편
354300008  210(하회마을-교보생명)     ← 오는 편  ★
354300386  급행3(안동터미널-도산서원)
354300387  급행3(도산서원-안동터미널) ★
```

시간표 문서에 귀로 시각이 생략되어 있었을 뿐,
운행 자체는 왕복으로 등록되어 있었다.

또한 노선 목록 응답에 **`runTotCnt`**(현재 운행 중 차량 수)가 있음을 발견했다.
실제 값을 대조해 의미를 확인했다.

| 노선 | runTotCnt | 검증 |
|---|---|---|
| 급행2 계열 | 0 | 주말 전용 노선, 호출 시점이 수요일이므로 정확 |
| 210 하회 양방향 | 1 | 각 방향 1대 운행 중 |
| 210 병산서원 | 0 | 하루 3회 운행이라 대기 시간대 |
| 순환1 / 110번 | 4 / 5 | 시내 노선이라 다수 |

### 결정
세 소스를 결합해 귀로 안내를 구현한다.

| 정보 | 출처 |
|---|---|
| 지금 오는 버스 | `tab=2` 도착정보의 `predictTm` |
| 오늘 운행 여부 | `tab=3`의 `runTotCnt` |
| 첫차·막차 | 안동시 공공데이터 운행시간표 (정적) |

```
도착정보 있음                 → "12분 후"
도착정보 없음 + runTotCnt > 0 → "접근 중인 버스 없음 · 배차가 길어요"
도착정보 없음 + runTotCnt = 0 → "오늘 운행이 끝났어요" (경고)
```

세 번째 분기가 이 기능의 본질이다.
막차 시각을 알려주는 것보다 **"지금 차가 다니는가"**를 알려주는 것이
여행자의 불안을 실제로 해소한다. 시각을 보여주면 사용자가 계산해야 하지만,
운행 종료를 알려주면 즉시 행동을 바꿀 수 있다.

### 한계
`tab=3` 응답의 `stTm`, `edTm`, `maxInterval`, `minInterval`, `runCnt` 필드는
**전부 null**이다. 안동시가 해당 항목을 입력하지 않았다.
따라서 첫차·막차는 정적 시간표에 의존한다.

### 교훈
**문서보다 실물이 정확하다.**
명세서에 없던 `via`·`predictTm`·`runTotCnt`가 실제 응답에는 있었고,
명세서에 있던 `rstop`·`provideType`은 오지 않았다.
이후 모든 API 판단은 실호출 결과를 기준으로 한다.

## ADR-008. 낙강물길공원 야간 코스 기획을 재검토한다

**결정일**: 2026-07-23
**상태**: 검토 필요

### 발견
LocgoHub 응답에서 해당 장소의 명칭이 다음과 같이 확인된다.

```
"낙강물길공원/공사중(2028년12월31일개장예정)"
```

제안서에서 야간 도보 코스의 핵심으로 제시한 장소가 현재 방문 불가 상태다.

### 대응 방향
야간 코스를 월영교 중심으로 재구성한다.
월영교는 중심관광지 2위이며 야간 조명으로 알려진 곳이다.
인접한 월영공원(76위), 안동민속촌(55위)과 도보 연결이 가능한지 검토한다.

> **두루누비 확인 완료 (2026-08-16)** — 걷기 코스를 공공 API에서 가져올 수 있는지가
> 미해결로 남아 있었다. **가져올 수 없다. 그래서 우리가 만든 코스를 쓴다.**
>
> `Durunubi/courseList` 실측: 전국 **144개 코스**가 전부이고 `routeList`는 **4개**다.
>
> | routeIdx | 노선 | 코스 수 |
> |---|---|---|
> | T_ROUTE_MNG…0001 | 남파랑길 | 31 |
> | T_ROUTE_MNG…0043 | 서해랑길 | 44 |
> | T_ROUTE_MNG…0047 | DMZ 평화의 길 | 30 |
> | T_THEME_MNG…11235 | 해파랑길 | 39 |
>
> 즉 이 API가 담은 것은 두루누비 전체가 아니라 **「코리아둘레길」 하나**다.
> 해안선과 접경을 따라 한반도 외곽을 도는 길이라 **내륙인 안동은 지날 수가 없다.**
> `sigun` 값 57종 중 경북은 경주·포항·영덕·울진 넷뿐이고 전부 동해안이다.
> 제주올레·지리산둘레길·북한산둘레길도 0건이다. 누락이 아니라 수록 범위 밖이다.
>
> ⚠️ `brdDiv`를 어떤 값으로 넣어도 항상 144건이 온다. 파라미터가 먹지 않으므로
> "분류를 바꾸면 더 나온다"는 기대를 하지 말 것.
>
> 문자열 '안동'으로 검색하면 2건이 걸리는데 둘 다 `sigun`이 아니라 본문이다 —
> 파주 코스의 "부인 안동김씨", 화천 코스의 "안동철교". 코스 위치와 무관하다.
>
> 안동 걷기길을 공공 데이터로 얻으려면 두루누비가 아니라 안동시·경북 쪽을 찾아야 한다.

## ADR-011. 음식점 데이터 구성

**결정일**: 2026-07-23
**상태**: 확정

### 조회 결과
안동 음식점(contentTypeId=39) `totalCount: 16`.
수는 적지만 제안서에서 목표한 향토음식이 모두 포함되어 있다.

| 향토음식 | 해당 업소 |
|---|---|
| 헛제삿밥 | 맛50년 헛제사밥, 헛제사밥까치구멍집 |
| 찜닭 | 안동 유진찜닭 |
| 간고등어·한식 | 옥야식당, 일직식당, 안동한우갈비 |

### 분류 기준
응답의 카테고리 코드로 탭을 구분한다.

| 코드 | 분류 |
|---|---|
| `lclsSystm2 = FD01` / `cat3 = A05020100` | 향토음식·한식 |
| `lclsSystm2 = FD05` / `cat3 = A05020900` | 카페·베이커리 |

### 이미지 결손
16건 중 7건(약 44%)이 `firstimage` 빈 값이다.
옥야식당, 헛제사밥까치구멍집 등 인지도 높은 업소가 포함되어 있어
카드 UI에서 폴백 이미지 처리가 필수다.

### 보완 방향
중심관광지 API의 안동구시장·중앙신시장을
"식도락 거점"으로 함께 노출해 음식점 수 부족을 보완한다.
제안서에서 언급한 찜닭골목이 곧 안동구시장 일대다.

> **보강 (2026-08-02)** — 구현 전에 재조회했다. 위 수치는 그대로 재현된다
> (16건, 이미지 9/결측 7, `cat3`·`lclsSystm2` 1:1). 다만 세 가지가 추가로 드러났다.
>
> **1. 이미지 결측 7건은 보충할 수 없다.** ADR-022에서 관광지 이미지를
> `searchKeyword2`로 채웠기에 같은 방법을 기대했으나 **0/7이다.**
> 원인이 다르다. 관광지는 지역 조회에 안 잡히는 레코드가 따로 있었지만,
> 음식점은 지역 조회에 정상적으로 잡히고 그 레코드에 이미지가 없다.
> **진짜로 없는 것이다.** 폴백이 유일한 답이고 `SpotPhoto`가 이미 그렇게 돼 있다.
>
> **2. `tel`이 16건 전부 빈 값이다.** `areaBasedList2`는 전화번호를 주지 않는다.
> `FoodPlace.tel`을 정의해 뒀지만 채울 소스가 없다. `detailCommon2`가 필요한데
> 미검증이다. **전화 걸기 UI를 넣지 말 것.** 16곳 전부 빈 버튼이 된다.
>
> **3. 위 분류표는 API가 준 것이 아니다.** API가 주는 구분은 한식(FD01) /
> 카페(FD05) 둘뿐이다. 이름으로 찜닭·헛제삿밥은 판별되지만
> **간고등어(옥야식당·일직식당)는 이름에 안 드러난다.** 이 표는 사람이 아는
> 사실로 만든 것이므로, 코드로 재현하려면 별도 결정이 필요하다.
> **→ ADR-023에서 확정했다.** 이름이 밝히는 찜닭·헛제삿밥만 태깅하고
> 간고등어는 넣지 않는다. 위 표는 사람의 지식으로 남고 코드에는 들어가지 않는다.
>
> ⚠️ 원문의 "안동구시장(21위)·중앙신시장(23위)"에서 순위를 뺐다.
> 202606 실측은 **29위·26위**다. `hubRank`는 매월 바뀐다. → ADR-021

## ADR-012. 화면 구조를 4개 페이지로 확정한다

**결정일**: 2026-07-23
**상태**: 확정

### 설계 기준
이 서비스의 사용 장면은 "여행 계획 단계"가 아니라
**"안동에 도착한 여행자가 현장에서 폰을 꺼내는 순간"**이다.
따라서 화면은 "지금 여기서 무엇을 할 수 있는가"에 즉답하는 구조여야 한다.

또한 데이터 조사 결과, 안동 관광지는 대부분 시내가 아닌 외곽(풍천면·도산면 등)에 있다.
사용자는 두 상태 중 하나이며 화면은 양쪽을 모두 커버해야 한다.

| 상태 | 필요한 것 |
|---|---|
| A. 시내에 있음 | 도보권 장소 + 다음 목적지로 가는 버스 |
| B. 외곽 관광지에 있음/가려 함 | 해당 관광지 정보 + 오가는 버스 |

### 화면 구조

```
[지금 여기]  홈 — 미니맵 / 가까운 정류장 버스 / 도보권 장소 / 인기 관광지
[둘러보기]   목록 — 관광지·식도락 탭, 리스트↔지도 토글
  └ 상세     관광지 상세 — 정보 + 지도 + 여기 가는 버스
[도보 코스]  낮·밤 코스
```

### 홈 화면의 정보 우선순위
**버스를 최상단에 배치한다.**

제안서의 핵심 인사이트는 "배차 간격이 길다 = 대기 시간이 생긴다 =
그 시간에 주변을 즐길 수 있다"이다.
이를 화면 순서로 그대로 옮긴다.

1. 가까운 정류장의 다음 버스 (몇 분 후)
2. 그 시간 안에 걸어서 갈 수 있는 곳
3. 안동 인기 관광지 순위

### 관광지 상세 화면의 차별점
관광지 정보와 버스 안내를 **한 화면에** 배치한다.

기존 안동 서비스들은 교통 정보(안동버스정보 앱)와 관광 정보(안동을 담다, 안동관광)가
분리되어 있어 여행자가 앱을 오가야 했다.
이 화면이 제안서에서 밝힌 차별성의 실체다.

### 폴백
위치 권한 거부 또는 안동 외 지역인 경우, 안동역을 기준 위치로 사용한다.

## ADR-013. 지도를 도입하되 전면 지도 UI는 채택하지 않는다

**결정일**: 2026-07-23
**상태**: 확정

### 결정
카카오맵을 도입하되, 지도 중심 UI가 아니라 필요한 화면에 부분 배치한다.

| 위치 | 형태 | 목적 |
|---|---|---|
| 홈 | 미니맵 (높이 200px 내외) | 현재 위치·정류장·주변 관광지 위치감 |
| 관광지 상세 | 위치 지도 | 관광지 ↔ 가까운 정류장 거리 시각화 |
| 둘러보기 | 리스트↔지도 토글 | 전체 분포 파악 (기본값은 리스트) |

### 근거
**지도를 넣는 이유** — 안동 관광지는 시내와 외곽에 흩어져 있어,
리스트만으로는 "이게 걸어갈 거리인지 버스를 타야 하는지" 감이 오지 않는다.
위치 기반 서비스의 핵심 가치가 전달되지 않는다.

**전면 지도 UI를 피하는 이유** — 마커 클러스터링, 바텀시트, 지도-리스트 상태 동기화 등
개발량이 크게 늘어난다. 모바일에서는 정보 밀도도 리스트가 더 높다.
1인 개발·기한 제약 하에서 핵심 기능 완성도(심사 30점)를 지키는 편이 낫다.

### 지도 선택
카카오맵을 사용한다.
- 국내 지도 데이터 정확도가 높다
- 스크립트 로드 방식이 단순해 Nuxt 통합 부담이 적다
- 무료 할당량이 서비스 규모에 충분하다

> **구현 (2026-08-02)** — JavaScript 키를 발급받아 `MapCard`에 실제 지도를 붙였다.
> 위 표에서 하나가 달라졌다. **둘러보기의 리스트↔지도 토글은 만들지 않았다.**
> 우측 지도가 상시 노출되고 목록 필터를 그대로 따라가므로 토글이 가리킬 상태가 없다.
> 칩으로 '카페'만 걸러 놓으면 지도에도 5곳만 남는다. 토글은 두 화면이 서로
> 다른 것을 보여줄 때 필요한 장치인데, 여기서는 둘이 같은 것을 본다.
>
> **처음에는 지도를 조작할 수 없게 했다**(`draggable: false`, `setZoomable(false)`).
> 스크롤을 지키려는 것이었다.
>
> **정정 (2026-08-13)** — 이동·확대·축소를 연다. 고정된 그림으로는 "이게 걸어갈
> 거리인가"를 카드 안에서 확인할 수 없어 결국 지도 앱으로 나가게 된다. 전면 지도
> UI를 안 쓴다는 결정과 카드 크기는 그대로다. 조작만 열었다.
>
> 스크롤은 다른 방법으로 지킨다. **휠 줌만 끈다**(`scrollwheel: false`).
> 데스크톱에서 카드 위 스크롤이 확대로 바뀌면 페이지가 그 자리에 붙잡힌다.
> 휠을 껐으니 줌 수단이 더블클릭뿐이 되지 않도록 `ZoomControl`을 붙였다.
> 모바일은 한 손가락 드래그가 지도 이동이 된다 — 카드 높이(200~340px)만큼
> 페이지 스크롤을 내준 셈이고, 이동이 되는 값으로 그만큼을 지불한다.
>
> 마커는 기본 핀을 쓰고, 홈의 중심(=사용자 위치)만 원과 점으로 따로 그린다.
> 중심을 마커로 그리면 관광지 마커와 모양이 같아져 어느 것이 나인지 알 수 없다.
>
> ⚠️ **키가 있어도 도메인이 등록되지 않으면 지도는 안 뜬다.**
> 카카오는 등록되지 않은 출처에 SDK 대신 401을 준다.
> 실측(2026-08-02): `caller=http://localhost:3123` → `AccessDeniedError: domain mismatched`.
> **포트까지 본다.** 콘솔 > 앱 설정 > 플랫폼 > Web에 쓰는 주소를 그대로 등록해야 한다.
> 실패는 조용하므로 `MapCard`가 "지도를 불러오지 못했어요"로 구분해 보여준다.
> "지도 준비 중"(키 없음)과 다른 문구다. 둘을 같은 말로 덮으면 원인을 못 찾는다.
>
> ⚠️ **지도를 붙이면 좌표가 카카오로 나간다.** 둘러보기·상세는 관광지 좌표뿐이라
> 무관하지만, 홈의 반경 원은 사용자 위치를 넘긴다. 위치정보 취급 범위가 여기서
> 한 번 넓어진다는 사실을 남겨 둔다.

## ADR-014. 찜하기 기능을 MVP에서 제외한다

**결정일**: 2026-07-23
**상태**: 확정 (후순위 이관)

### 배경
제안서 발전 방향에 "사용자 맞춤 내 여행 저장 기능"을 포함했다.

### 결정
MVP 범위에서 제외하고, 핵심 기능 완성 후 여유가 있으면 구현한다.

### 근거
- **로그인 기능이 없다.** ADR-001에 따라 백엔드·DB가 없으므로 계정 개념이 성립하지 않는다.
- localStorage로 구현할 수는 있으나, 기기·브라우저를 바꾸면 데이터가 사라진다.
  "저장"이라는 단어가 주는 사용자 기대와 실제 동작이 어긋난다.
- 핵심 기능(버스 안내·주변 탐색·관광지 정보)의 완성도를 우선한다.

### 구현 시 방식
추후 구현한다면 localStorage 기반으로 하되,
"이 기기에만 저장됩니다"를 명시해 기대를 정확히 설정한다.

## ADR-015. 관광지 정류장은 방향별로 별도 ID를 매핑한다

**결정일**: 2026-07-29
**상태**: 확정

### 발견
같은 이름의 정류장이 방향별로 다른 `stationId`를 갖는다.

| ID | 정류장명 | 역할 | 도착정보 조회 |
|---|---|---|---|
| 354000701 | 하회보건진료소 | 시내→하회 종점 | ✅ 210번 25분 후 |
| 354002046 | 하회보건진료소 | 하회→시내 기점 | ❌ 빈 배열 |

기점 정류장은 "접근 중인 차량"이라는 개념이 성립하지 않으므로
도착정보 API가 항상 빈 배열을 반환한다.

### 결정
관광지마다 정류장을 두 개씩 매핑하되 용도를 나눈다.

- **inbound** — 실시간 도착정보 조회에 사용
- **outbound** — 도착정보 조회 불가. 정적 시간표와 `runTotCnt`로 대체

`data/spot-station-map.json`에 `realtimeAvailable: false`로 명시한다.

### 주의
관광지에서 나가는 편은 원리적으로 실시간 조회가 불가능하다.
"들어온 차가 회차해서 나간다"는 사실과 계획 시간표로 안내하며,
**정확한 출발 시각을 추정해 단정하지 않는다.**
부정확한 교통 정보는 여행자를 정류장에 세워둔다.

## ADR-016. 버스 시간표는 정적 파일로, 관광 데이터는 API로 관리한다

**결정일**: 2026-07-29
**상태**: 확정 (ADR-003 보완)

### 배경
공모전 심사 요건은 "한국관광공사 OpenAPI 형태만 인정"이다.
이 조항은 관광공사 API 활용을 필수로 요구하는 것이며,
다른 출처의 보조 데이터를 파일로 쓰는 것을 금지하지 않는다.

관광공사 API 활용은 LocgoHubTarService1과 KorService2로 이미 충족했다.

### 결정
안동시 공공데이터포털의 시내버스 운행시간표 엑셀을 정적 데이터로 활용한다.

### 파싱 방식
4개 파일, 42개 시트, 166개 정류장 컬럼을 수확했다.
시트마다 컬럼 구조가 전혀 달라 완전 파싱을 포기하고
**첫차·막차·운행횟수만** 추출하는 방식을 택했다.

파싱상 마주친 문제들:
- 시트별 헤더 구조 상이 (`구분` 열이 없는 시트가 4개)
- 시각 형식 혼재 (`datetime.time`, `"06:40"` 문자열이 한 시트에 공존)
- 셀 안에 경로 설명 문장이 들어 있음
- 시트별 시행일 상이 (파일명은 26.8.1이나 210번은 24.1.5 기준)
- 조건부 운행 규칙 (급행2는 8월·축제기간 한정)

### 발견된 구조적 한계
공식 시간표는 **안동 기준으로만** 작성되어 있다.
생활 노선(610 길안, 512 도산, 임하)에는 "○○에서 안동출발" 컬럼이 있으나
**관광 노선(210 하회, 310 봉정사, 112 안동댐)에는 없다.**

주민 통근 노선은 귀로가 필요하니 적었고, 관광 노선은 그 배려가 없었다.
이 공백 자체가 제안서의 문제의식("정보가 흩어져 있어 동선을 짜기 어렵다")을
실증하는 근거다.

### 화면에서 경고해야 할 위험 정보
- **병산서원** — 하루 3회, 마지막 도착 15:30. 오후 출발 시 방문 불가
- **월영교** — 야경 명소이나 막차 18:45. 조명 점등 시각에 버스가 끊긴다

## ADR-017. 개발 환경 — 경로에 비ASCII 문자를 두지 않는다

**결정일**: 2026-07-30
**상태**: 확정 (환경 제약)

### 증상
`pnpm install`이 정상 종료되었으나 `pnpm dev` 실행 시
`'nuxt'은(는) 내부 또는 외부 명령... 아닙니다` 오류가 발생했다.
`package.json`은 정상이었고 의존성 591개도 설치되어 있었다.

프로젝트 경로가 `C:\Users\...\Desktop\안동\andong-itda`였다.
pnpm은 전역 저장소에 패키지를 두고 프로젝트에는 심볼릭 링크만 생성하는데,

### 기록 사유
설치가 "성공"으로 끝나므로 원인 추적이 어렵다.
Python 스크립트, 빌드 도구, 배포 파이프라인에서도 유사한 문제가 발생할 수 있어
개발 폴더 경로는 영문으로 유지한다.

## ADR-018. 공공 API 인증키는 한 번 디코딩해서 쓴다

### 배경
`/api/spots` 첫 구현에서 LocgoHub·KorService2가 모두 401 Unauthorized를 반환했다.
키는 `.env`에 정상적으로 들어 있었다.

### 원인
data.go.kr은 인증키를 **Encoding**과 **Decoding** 두 형태로 발급한다.
`.env`에 담겨 있던 값은 Encoding 키였다(96자, `%` 이스케이프 포함, 디코딩하면 88자).
이걸 그대로 쿼리 파라미터로 넘기면 ofetch가 직렬화하며 한 번 더 인코딩해
`%`가 `%25`가 된다. 서버는 존재하지 않는 키를 받는다.

실측(2026-07-30, KorService2 areaBasedList2):

| 전달 방식 | 결과 |
|---|---|
| 원문 그대로 (재인코딩 없음) | 200 OK |
| `encodeURIComponent` 적용 | **401 Unauthorized** |
| 디코딩 후 재인코딩 | 200 OK |

### 결정
키를 한 번 `decodeURIComponent`로 원문화해 보관하고,
인코딩은 쿼리 직렬화 단계에 딱 한 번만 맡긴다. (`server/utils/tourApi.ts`)

### 근거
Encoding 키와 Decoding 키 **어느 쪽을 붙여넣어도 동작한다.**
Decoding 키에는 `%`가 없어 디코딩이 무연산이기 때문이다.
키 형태를 사람이 기억해야 하는 설계는 다른 PC에서 반드시 한 번 더 틀린다.
유효하지 않은 이스케이프가 섞인 키는 디코딩이 실패하므로 원문을 그대로 쓴다.

### 기록 사유
PROJECT-PROMPT §2에는 "Decoding 키 사용"이라고 적혀 있으나
실제 `.env`에 들어 있던 값은 Encoding 키였다.
401은 키가 틀렸다는 신호로 읽히기 때문에 원인을 엉뚱한 데서 찾게 된다.

## ADR-019. 안동시 버스 API는 https로 직접 호출한다

### 배경
지시서와 타입 주석 모두 베이스를 `http://bus.andong.go.kr/m01/s04.do`로 적고 있고,

## ADR-020. 관광지 통합 정보의 시간표는 spot-station-map.json에서 가져온다

### 배경
`/api/spot-bus/[spot]`의 `schedule` 필드를 채울 소스가 두 개다.
`server/data/timetable-spots.json`(엑셀 파싱 원본)과
`server/data/spot-station-map.json`의 `timetable` 필드.

### 문제
`timetable-spots.json`은 `SpotTimetable` 타입과 구조가 맞지 않는다
(`routes[].times[]` + `summary` 형태). 게다가 내용이 어긋난다.

| 관광지 | map의 `returnTimesKnown` | timetable-spots의 `hasReturnTimetable` |
|---|---|---|
| 안동하회마을 | false | **true** |
| 봉정사 | false | **true** |
| 도산서원 | **true** | false |
| 병산서원 | false | false |

원인은 두 가지다. `timetable-spots.json`은 주말·8월 한정 급행2를 귀로 시간표로 세고,
정작 도산서원의 온혜발 귀로(07:50~20:40)는 파싱에서 놓쳤다.
수록 범위도 5곳뿐이라 만휴정·임청각이 없고, 월영교는 "안동댐·월영교"로 이름이 다르다.
월영교 운행 횟수도 원본은 9회(10:30·12:50 중복)지만 정리본은 7회다.

### 결정
`spot-station-map.json`의 `timetable`을 유일한 소스로 쓴다.
`timetable-spots.json`은 그 원본으로 남기고 런타임에서 읽지 않는다.

### 근거
`spot-station-map.json`의 `timetable`은 파싱 원본을 사람이 검증·정리한 결과이고,
타입상으로도 `SpotTimetable` 그 자체라 무변형으로 내려보낼 수 있다.
파싱 산출물을 그대로 쓰면 중복 시각과 계절 노선이 막차 정보에 섞인다.

`returnTimesKnown: false`인 관광지의 귀로 시각은 추정해서 채우지 않는다.
부정확한 막차 정보는 여행자를 정류장에 세워둔다. → ADR-016

## ADR-021. 두 관광 API의 조인은 좌표를 1순위, 이름을 게이트로 쓴다

### 배경
ADR-004에서 좌표 + 이름으로 매칭하기로 정했으나 구체적 기준은 미정이었다.

### 결정
1. LocgoHub 좌표에서 **200m 이내** KorService2 후보를 거리순으로 세운다
2. 이름 유사도 **0.4 이상**인 것 중 가장 가까운 항목을 택한다
3. 통과하는 후보가 없으면 병합하지 않고 LocgoHub 단독으로 표시한다

이름 비교 전에 `안동` 접두어와 괄호를 제거한다
(`안동하회마을`→`하회마을`, `개목사(안동)`→`개목사`).
그 외에는 2-gram Dice 계수를 쓴다. 유사도 라이브러리는 도입하지 않았다.

좌표 필드명이 서로 다르다. LocgoHub는 `mapX`/`mapY`(대문자), KorService2는
`mapx`/`mapy`(소문자)이며 **양쪽 다 문자열로 온다.** 숫자 변환이 필요하다.

### 근거 — 이름을 보조 게이트로 둔 이유
거리만으로는 틀린다. 실측에서 **안동시립박물관의 최근접 항목은 1m 거리의
"안동민속촌"이었다.** 이름 게이트가 이를 걸러내고 87m 거리의 정답
(contentid 129772)을 골랐다. 같은 방식으로 오매칭 9건을 막았다.

거리를 1순위로 둔 이유는 그 반대다. 이름 표기는 데이터셋마다 흔들리지만
좌표는 흔들리지 않는다. 이름을 1순위로 두면 접두어 차이에서 먼저 무너진다.

### 실측 결과 (2026-07-30, baseYm 202606)
- 숙박 36건 제외 후 64건 중 **19건 병합** (주소 19, 이미지 18)
- ADR-004에 적어둔 알려진 겹침 4건 전부 매칭:
  안동시립박물관↔129772, 이육사문학관↔2721929,
  하회세계탈박물관↔130150, 체화정↔1621549

### 알게 된 것 — 결측 범위가 문서보다 넓다
KorService2 **지역 조회로** 안 잡히는 것이 하회마을·도산서원·월영교만이 아니다.
**병산서원·봉정사·안동역·만휴정·부용대도 없다.**
최근접 항목이 287m~2.4km 거리에 유사도 0이라 반경을 넓혀도 해결되지 않는다.
인기 상위 6곳이 전부 LocgoHub 단독 표시이므로 **이미지 폴백 UI가 상위권에서 바로 필요하다.**

> **정정 (2026-08-02)** — "반경을 넓혀도 해결되지 않는다"는 맞지만,
> 결론이 "그러니 폴백뿐"은 아니었다. 반경이 아니라 **조회 방식**을 바꿔야 했다.
> `searchKeyword2`로 이름을 검색하면 이 6곳이 전부 이미지까지 딸려 온다.
> → ADR-004 정정, ADR-022
>
> **재정정 (2026-08-24)** — 조회 방식이라는 진단은 맞았고 처방이 우회로였다.
> 이름으로 재검색할 필요가 없다. `lDongRegnCd=47`·`lDongSignguCd=170`으로 지역
> 조회를 하면 6곳이 **처음부터 목록에 들어온다.** → ADR-034

### 알게 된 것 — hubRank는 매월 바뀐다
202606 기준 1위 월영교, 2위 안동하회마을로 지시서 기록(1위 하회마을)과 다르다.
알려진 겹침 4건의 순위도 25→31, 36→45, 59→56, 86→63으로 이동했다.
순위를 코드나 정적 데이터에 하드코딩하지 않는다.

## ADR-022 여행자 목록의 노이즈는 이름 패턴으로 걷어낸다

**결정** — LocgoHub 목록에서 골프장·영화관·교통시설·체육시설·도매시장을
이름 패턴으로 제외한다. 구현은 `noiseReason()`이고 `fetchHubSpots`에서 숙박
필터(ADR-009) 바로 옆에 건다.

### 문제
LocgoHub는 통신사 방문 데이터 기반이라 "사람이 많이 간 곳"을 준다.
그건 "여행자가 갈 만한 곳"과 다르다. 실측(202606) 상위권이 이렇다.

```
 6위 안동역        10위 안동터미널     17위 남안동CC
19위 안동레이크GC   20위 리버힐CC       21위 CGV/안동
```

방문 데이터로서는 정확한 결과다. 안동역에는 실제로 사람이 많이 간다.
하지만 "안동에서 뭘 하지?"에 대한 답으로 CGV를 6번째로 내미는 목록은 못 믿는다.

### 왜 카테고리로 자르지 않는가
상류 분류가 목적과 어긋난다.

| 카테고리 | 걷어낼 것 | 남길 것 |
|---|---|---|
| 문화관광 | CGV/안동, 롯데시네마 | 하회세계탈박물관, 이육사문학관 |
| 레저스포츠 | 남안동CC, 리버힐CC | 선성수상길, 유교랜드 |
| 쇼핑 | 안동수산물도매시장 | 중앙신시장, 안동구시장 |

카테고리를 자르면 양쪽이 같이 날아간다. 남길 것이 더 중요한 항목들이다.

### 왜 이름 패턴인가
무딘 도구지만 여기서는 그게 맞다.

1. 걷어낼 대상이 **전부 이름에 정체를 드러낸다.** CC·GC·시네마·역·구장·도매시장
2. 무엇이 왜 빠졌는지 **읽어서 감사할 수 있다.** 분류 코드는 그게 안 된다
3. 오탐이 나면 이름만 보고 즉시 안다

슬래시 앞부분으로만 판정한다. 뒤까지 보면 "한국국학진흥원/KSI연수원"이
엉뚱한 패턴에 걸리고 "안동퇴계예던길/1코스"도 위험하다.

전통시장(중앙신시장·안동구시장·구담시장)은 남긴다. 여행자가 실제로 간다.
도매시장만 뗀다.

### 실측 결과 (2026-08-02, baseYm 202606)
**64건 → 49건. 15건 제외, 오탐 0건.**

```
교통시설 3   안동역, 안동터미널, 옹천역/폐역
골프장   3   남안동CC, 안동레이크GC, 리버힐CC
영화관   2   CGV/안동, 롯데시네마/프리미엄안동
체육시설 4   안동드림베이스볼파크, 안동강변구장,
             용상체육공원/야구장, 안동시생활체육공원
도매시장 3   안동시농산물도매시장, 안동수산물도매시장, 안동청과합자회사
```

### 부수 효과 — 이미지 결측률이 함께 내려간다
제외한 15건 중 14건이 이미지가 없던 항목이다. 당연하다.
**역과 골프장에 관광 사진이 없는 것이 정상이다.**
노이즈 필터와 이미지 결측은 같은 문제의 두 얼굴이었다.

이미지 보유율 **61% → 76%**. 백필 대상이 줄어 첫 요청도 16초 → 11초로 짧아졌다.

> **후속 (2026-08-24)** — 76%는 그대로 두고 첫 요청만 1.8초가 됐다. 백필의
> 주요 단계가 네트워크 검색에서 로컬 재탐색으로 내려왔기 때문이다. → ADR-034

### 한계
이름에 정체가 안 드러나는 것은 못 거른다. `웨이블리`(91위),
`플레이방월드`(51위)가 남아 있다. 패턴 목록은 앞으로 늘어날 텐데,
**새 항목을 넣기 전에 실제 응답에서 오탐부터 확인할 것.**
회귀는 `node scripts/check-spot-match.ts`가 지킨다.

## ADR-023 음식점 분류는 응답에서 다시 만들 수 있는 것만 쓴다

**결정일**: 2026-08-02
**상태**: 확정

**결정** — `foodCategory`를 `찜닭 | 헛제삿밥 | 한식 | 카페` 네 값으로 한다.
앞의 둘은 **상호에서 읽어내고** 뒤의 둘은 API의 `cat3`를 옮긴다.
간고등어는 넣지 않는다. 구현은 `foodCategoryOf()`이고 `/api/food`가 쓴다.

### 문제
API가 주는 구분은 한식(FD01) / 카페(FD05) 둘뿐이다.
그런데 이 탭의 이름은 "식도락"이고, 안동에서 그 말은 찜닭·헛제삿밥·간고등어를 뜻한다.
16곳을 한식 11 / 카페 5로만 내놓으면 탭이 존재할 이유가 없어진다.

ADR-011은 분류표를 적어 뒀지만 그건 **API가 아니라 사람이 아는 사실로 만든 것**이었다.
옥야식당이 간고등어집이라는 정보는 응답 어디에도 없다.

### 선택지
| | 방법 | 문제 |
|---|---|---|
| 1 | 한식/카페 2분류만 | 정직하지만 향토음식이라는 색이 사라진다 |
| 2 | **이름 패턴 + API 2분류** | 간고등어를 놓친다 |
| 3 | 16곳 정적 매핑 | 정확하지만 출처가 사람이고 손으로 관리한다 |

**2번을 택했다.** 기준은 정확도가 아니라 **근거가 어디 있느냐**다.

1번은 가진 정보를 버린다. 찜닭·헛제삿밥은 상호가 스스로 밝히고 있는데
그걸 안 읽을 이유가 없다.

3번은 정확하다. `spot-station-map.json`이라는 선례도 있다. 하지만 그 파일에는
"임의로 채우지 말 것"이라는 조건이 붙어 있었고, 그건 **좌표로 검증할 수 있었기
때문에** 지킬 수 있는 조건이었다. 간고등어에는 대조할 원본이 없다.
검증 못 하는 사실을 코드에 박으면 다음 사람은 그게 어디서 왔는지 알 수 없다.

### 규칙
```
cat3 = A05020900        → 카페      API가 직접 답한 것이라 이름 추측보다 앞선다
title에 '찜닭'          → 찜닭      안동 유진찜닭
title에 '헛제사밥|헛제삿밥' → 헛제삿밥  맛50년 헛제사밥, 헛제사밥까치구멍집
그 외                   → 한식
```

상호 표기가 '헛제**사**밥'이고 분류명이 '헛제**삿**밥'이다. 둘 다 받는다.
표기를 하나만 잡으면 영원히 0건인 칩이 남는다.

카페 판정을 먼저 한다. 한식/카페는 API가 직접 준 답이므로 이름 추측보다 강하다.
향토음식 태깅은 그 한식 안에서만 한다.

### 결과 (2026-08-02 실측, 16건)
```
찜닭     1   안동 유진찜닭
헛제삿밥 2   맛50년 헛제사밥, 헛제사밥까치구멍집
한식     8   옥야식당, 일직식당, 안동한우갈비, 신라국밥, 효자통닭,
             황소곳간, 농가맛집 뜰, 묵향
카페     5   맘모스베이커리, 카페뒤뜰, 폴모스트, 396커피컴퍼니, 월영당
```

**옥야식당·일직식당이 '한식'에 있는 것은 버그가 아니라 결정이다.**
여기를 '간고등어'로 고치고 싶어진다면 그 근거가 응답 밖에 있다는 뜻이다.
회귀는 `node scripts/check-spot-match.ts`가 지킨다.

### `/api/food`가 `/api/spots`와 다른 점
| | `/api/spots` | `/api/food` |
|---|---|---|
| 소스 | LocgoHub + KorService2 병합 | KorService2 단독 |
| 순위 | `hubRank` | **없다** (LocgoHub에 음식점이 없다) |
| 이미지 보충 | 4단계로 채움 (30 + 6 + 4 + 1) | **안 한다** (0/7) |
| 첫 요청 | 약 1.8초 (ADR-034 전 최악 12.6초) | 2~3초 |
| 지역 조회 | 법정동 코드 (ADR-034) | 아직 옛 지역 코드 — 옮기면 27건 |

이미지 보충을 붙이지 않는 이유는 결측의 원인이 다르기 때문이다.
관광지는 `areacode`가 빈 값이라 지역 조회에 안 잡히는 레코드가 따로 있었지만,
음식점은 지역 조회에 정상적으로 잡히고 **그 레코드에 이미지가 없다.**
조회를 몇 번 하든 없는 건 없다. 44% 결측은 `SpotPhoto` 폴백이 받는다.

순위가 없으므로 "인기순" 토글도 만들지 않는다. 없는 축을 비활성 버튼으로
남겨두지 않는다. 기본 정렬은 분류 순서(`FOOD_CATEGORY_ORDER`)이고
향토음식을 앞에 세운다.

### 화면
- 칩은 `FOOD_CATEGORY_ORDER` 상수에서 만든다. 관광지 탭과 반대다.
  거기는 분류가 상류의 것이라 응답에서 만들었고, 여기는 우리가 정의한
  닫힌 집합이라 상수에서 만든다. 단, 0건인 분류는 칩을 띄우지 않는다
- 칩 선택 상태를 탭마다 따로 둔다. 하나로 묶으면 '역사관광'을 고른 채
  식도락으로 넘어갔을 때 사용자가 건 적 없는 필터로 0곳이 뜬다
- **카드에 상세 링크를 붙이지 않는다.** `/spots/[id]`는 `/api/spots`에서 id를
  찾는데 음식점은 거기 없어 404가 된다. 갈 곳 없는 링크를 만들지 않는다
- **전화 버튼을 넣지 않는다.** `tel`이 16건 전부 빈 값이다 → ADR-011
- 사진 없는 카드가 7곳이라 목록 아래에 이유를 한 줄 적는다.
  폴백이 고장으로 보이면 안 된다

### 한계
새 음식점이 등록되고 그 상호에 '찜닭'이 없으면 '한식'이 된다.
패턴 목록은 늘어날 텐데 **추가 전에 실제 응답의 `title`부터 확인할 것.**
상호에 없는 단어를 넣으면 영원히 0건인 칩이 생긴다.

## ADR-024 사용자 좌표는 브라우저 밖으로 내보내지 않는다

**결정일**: 2026-08-06
**상태**: 확정

**결정** — 좌표를 파라미터로 받는 서버 라우트를 두지 않는다.
`/api/spots/nearby`와 `/api/bus/nearby-stations`를 삭제하고, 목록을 통째로
내려보낸 뒤 브라우저에서 `nearest()`로 고른다.

### 문제
법적 검토 과정에서 코드가 문서와 다르다는 것이 드러났다.
"좌표는 브라우저 메모리에서만 쓰고 서버로 보내지 않는다"고 적어 뒀지만
실제로는 이런 요청이 나가고 있었다.

```
GET /api/spots/nearby?lat=36.5684&lng=128.7294&radius=30000&limit=12
GET /api/bus/nearby-stations?lat=36.5684&lng=128.7294&limit=5
```

`useFetch`의 `query`가 `computed`라 `locate()`가 성공하는 순간 실제 GPS 좌표로
재요청이 나간다. 그리고 **쿼리스트링은 요청 URL의 일부라 배포 로그에 남는다.**
DB가 없다는 것과 로그가 없다는 것은 다른 이야기였다.

이 구조에서는 「위치정보의 보호 및 이용 등에 관한 법률」상 사업자가 위치정보를
'수집'한 것으로 볼 여지가 생긴다. 제9조 위치기반서비스사업 신고 대상이 되면
제40조에 따라 3년 이하 징역 또는 3천만원 이하 벌금이 걸린다.
계정이 없으니 개인위치정보가 아니라는 주장도 가능하지만, 로그에 IP와 좌표가
한 줄로 남는 이상 다툼의 여지가 크다. 다투지 않는 쪽을 택한다.

### 왜 서버에서 계산했었나
두 라우트의 주석이 이유를 적어 두고 있었다.

- `nearby-stations` — 정류장 전체가 1.86MB다. 브라우저로 내려보낼 수 없다
- `spots/nearby` — 하버사인을 클라이언트에 두 번째로 구현하게 된다

**둘 다 사실이 아니었다.**

`walkMinutes`는 이미 `#shared`에 있었고 `distanceMeters`만 `server/utils`에
있었다. 옮기면 구현은 한 벌이다.

크기는 재 봤다 (2026-08-06 실호출, 2107건).

| | raw | gzip |
|---|---|---|
| 14필드 전부 | 1,479 KB | 125 KB |
| 4필드 | 165 KB | 39 KB |
| 4필드 + 좌표 5자리 | **153 KB** | **31 KB** |

1.86MB의 정체는 안 쓰는 필드 10개(다국어명 3종·BIT ID·카드번호 등)와
소수점 10자리 좌표였다. 화면이 쓰는 건 `stationId`·`stationNm`·좌표뿐이다.
31KB면 사진 한 장이다.

### 선택지
| | 방법 | 문제 |
|---|---|---|
| 1 | 사업 신고 + 약관 + 동의 절차 | 신고·약관·동의·확인자료 보관이 전부 따라온다. 무료 공모전 출품물에 붙일 무게가 아니다 |
| 2 | 좌표를 뭉개서 전송 | 소수점 2자리(1.1km)면 최근접 정류장이 바뀐다. 정밀도를 지키면 여전히 개인 위치다. 법적으로 애매한 채로 남는다 |
| 3 | **목록을 내려보내고 브라우저가 계산** | 31KB를 더 받는다 |

**3번을 택했다.** 31KB로 쟁점 자체가 사라진다.

### 구조
- `distanceMeters`를 `server/utils/tourApi.ts`에서 `shared/constants/location.ts`로 옮겼다
- `nearest(items, from, { radius, limit })`를 같은 파일에 두었다. 정류장과 관광지가
  같은 함수로 돈다 — 그래서 `/api/bus/stations`가 상류의 `gpsX`/`gpsY`를
  `lat`/`lng`으로 바꿔 내보낸다
- `stationId` 중복 제거를 `stations` 라우트로 옮겼다. 캐시되는 자리라 한 번만 돈다
- 상세 화면의 "근처에 함께 볼 곳"은 자기 자신을 **먼저** 뺀다.
  나중에 빼던 기존 코드는 4곳을 고른 뒤 3곳만 남기고 있었다
- SSR은 그대로다. 첫 렌더는 안동역 폴백 기준으로 계산되고, 브라우저에서 좌표가
  잡히면 같은 `computed`가 다시 돈다. 네트워크 요청은 추가로 나가지 않는다 → ADR-012 유지

### 남는 것
**좌표 발자국이 0이 되지는 않는다.** 홈의 `MapCard`가 사용자 좌표를 지도 중심으로
받고, 카카오맵 SDK가 그 중심으로 타일을 요청한다. 우리 서버에서 지워도 카카오에는 간다.
지도를 쓰는 모든 서비스가 같고 카카오는 등록된 사업자지만, "좌표가 아무 데도 안 간다"고
쓰면 거짓말이다. 안내 문구에 지도 사용을 밝힌다.

법 해석에 다툼의 여지가 있는 부분도 남는다. 단말 내 처리만으로도 위치기반서비스에
해당한다는 해석이 문언상 불가능하지 않다. 위치정보지원센터 서면 질의 항목으로 남긴다.

### 검증
`node scripts/check-spot-match.ts` — `nearest`의 거리순 정렬·반경 컷·개수 제한과
원본 배열 불변을 확인한다. 홈의 두 목록이 전부 이 함수 하나로 돈다.

## ADR-025 도착 버스가 닿는 관광지는 노선상 순번으로 판정한다

**결정일**: 2026-08-07
**상태**: 확정

**결정** — 도착정보에 그 버스가 닿는 관광지를 붙인다. 판정 근거는
`routeId` 일치 **그리고** `arrival.stationOrd < spot.stationOrd`다.
순번을 확인하지 못한 관광지는 표시하지 않는다.

### 문제
홈은 "212번 12분 후"까지만 말했다. 화면에 있던 `via`는 노선의 기점 → 종점이라
종점이 우연히 관광지일 때만 읽혔다. 종점이 안동터미널이면 그 버스가 도산서원을
지나는지 알 방법이 없었다.

상세 화면은 "하회마을 가려면 뭘 타나"에 답하는데, 홈은 그 반대인
"지금 오는 이 버스가 어디로 가나"에 답하지 못했다. 두 화면을 잇는 것이
이 서비스의 주장이므로 그대로 둘 수 없다.

### 왜 routeId만으로는 안 되는가
같은 노선이어도 내 정류장이 관광지보다 뒤면 그 버스는 이미 지나쳤다.
"→ 하회마을"을 잘못 붙이면 여행자를 반대 방향 버스에 태운다.
ADR-015·ADR-016이 일관되게 거부해 온 종류의 거짓말이다.

그래서 순번을 비교한다. `BusArrival.stationOrd`(내 정류장의 노선상 순번)는
이미 응답에 오고 있었고, 관광지 쪽 순번만 없었다.

### 순번을 채우는 방법
`spot-station-map.json`에 `stationOrd`가 적혀 있던 것은 7곳 중 2곳(월영교·임청각)뿐이었다.
나머지는 `tab=4`(노선별 정류장)를 노선 수만큼 불러 `stationId`로 찾는다.
`tab=4`는 그동안 한 번도 쓰지 않은 오퍼레이션인데 `BusRouteStation` 타입에
`stationOrd`가 이미 정의되어 있었다.

1일 캐시한다. 노선의 정류장 순서는 시간표만큼도 자주 바뀌지 않는다.
도착정보는 캐시하지 않는 핫 패스이므로 이 조회가 거기 얹히면 안 된다.

### 실측 (2026-08-07, 7곳)
```
OK(기재)  월영교                     ord=7
OK(기재)  안동임청각·법흥사지칠층전탑   ord=3
OK(조회)  안동하회마을                ord=52 / 노선정류장 53
OK(조회)  만휴정                     ord=59 / 노선정류장 60
MISS      병산서원   route=354300007 station=354002027
MISS      봉정사     route=354300060 station=354002024
MISS      도산서원   route=354300386 station=354001832
```

### MISS 3건의 원인 — 매핑 데이터 오류다
세 곳 모두 `inbound.stationId`에 **나가는 편 노선의 기점 정류장 ID**가 들어가
있다. 들어오는 편 노선에는 그 ID가 아예 없다.

| 관광지 | 기재된 ID | 실제 위치 | 들어오는 편의 진짜 정류장 |
|---|---|---|---|
| 병산서원 | 354002027 | outbound ord=1 | `354000711` @ ord 57 |
| 봉정사 | 354002024 | outbound ord=1 | `354000522` @ ord 32 |
| 도산서원 | 354001832 | outbound ord=1 | `354001831` @ ord 64 |

**파장이 이 기능 밖에 있다.** `ord=1`은 기점이고, 기점 정류장의 도착정보는
항상 빈 배열이다(ADR-015). `/api/spot-bus/[spot]`이 실시간 도착을 조회하는
대상이 바로 이 `inbound.stationId`이므로, 세 곳의 상세 화면은 실시간 도착이
계속 비어 있었을 것이다. 이 기능이 아니었으면 드러나지 않았다.

### 3건을 고쳤다 (2026-08-07)
`spot-station-map.json`을 위 표대로 정정했다. 이 파일에는 "임의로 채우지 말 것"이
붙어 있지만, 여기서 넣은 값은 추측이 아니라 상류 `tab=4` 노선 정류장 목록에서
읽은 것이므로 그 금지에 걸리지 않는다. 근거는 위 표에 남아 있다.

```
병산서원   stationId 354002027 → 354000711   stationOrd 57 추가
봉정사     stationId 354002024 → 354000522   stationOrd 32 추가
도산서원   stationId 354001832 → 354001831   stationOrd 64 추가
           stationNm "도산서원(서원)" → "도산서원"
```

도산서원은 이름도 함께 고쳤다. `354001832`(나가는 편 기점)의 상류 표기가
"도산서원(서원)"이었을 뿐, 들어오는 편 정류장 `354001831`의 이름은 "도산서원"이다.
ID를 바꾸면서 이름을 그대로 두면 다음 사람이 대조할 때 어긋난다.

정정으로 `stationOrd`가 적힌 곳이 2곳에서 5곳이 됐다. `tab=4`를 실제로 부르는
대상은 하회마을·만휴정 2곳만 남았다.

### 정정 뒤 실측 (2026-08-10 월 10:09~10:19)
상류 `tab=4`로 세 정류장이 각 노선에 실존함을 먼저 확인했다. 순번은 위 표와 일치하고,
**셋 다 들어오는 편 노선의 종점**이었다. 기점(`ord=1`)을 조회하던 것을 종점으로 고친 셈이다.

```
병산서원  354000711  ord 57 / 노선 정류장 58 (마지막 순번 57)
봉정사    354000522  ord 32 / 노선 정류장 33 (마지막 순번 32)
도산서원  354001831  ord 64 / 노선 정류장 64 (마지막 순번 64)
```

도착정보(`tab=2`)를 옛 ID와 새 ID로 각각 불러 비교했다.

| 관광지 | 옛 ID | 새 ID | 노선 runTotCnt |
|---|---|---|---|
| 병산서원 | 0건 | 0건 | 0 (미운행) |
| 봉정사 | 0건 | 0건 | 0 (미운행) |
| 도산서원 | 0건 | **1건** | 1 (운행 중) |

**도산서원이 결정적이다.** 같은 시각 같은 노선인데 옛 ID는 0건, 새 ID는 급행3 1건이
잡혔다(`predictTm` 33분 → 21분, `remainStation` 32 → 18로 접근이 이어졌다).
버그는 해소됐다.

병산서원·봉정사가 0건인 것은 정정과 무관하다. 두 노선 모두 `runTotCnt=0`,
즉 그 시각에 도는 차가 없었다(ADR-015의 `closed`). 옛 ID였다면 운행 중이어도
영원히 0건이었을 것이므로 이 0건과는 의미가 다르다. 다만 **두 곳은 운행 시간대에
다시 확인해야 확증된다.** 210은 하루 3회다. → 미해결 과제

`/api/spot-bus/도산서원`도 `status=arriving`, `arrivals=1`, `runTotCnt=1`로 정합했다.

### 표시 규칙
- 순번을 확인하지 못한 관광지는 담기지 않는다. 빈 배열이 "닿는 곳이 없다"와
  "판정하지 못했다"를 구분하지 못하지만, 화면은 둘 다 아무것도 표시하지 않으므로
  구분할 이유가 없다. 틀린 것을 보여주지 않는 쪽이 기준이다
- 상세 화면(`SpotBusPanel`)에는 붙이지 않는다. 이미 목적지를 알고 들어온
  화면에서 "이 버스가 어디로 가는지"를 다시 말할 이유가 없다
- 한 노선의 `tab=4`가 실패해도 나머지는 살린다. 여기서 던지면 도착정보 전체가
  502가 된다. 부가 정보가 본체를 죽이면 안 된다

## ADR-026 같은 이름의 승강장은 "방면"으로 가르고, 도착이 없는 승강장은 뒤로 보낸다

**결정일**: 2026-08-13
**상태**: 확정

### 문제
홈의 정류장 칩에 **"안동역(안동터미널)"이 셋 나란히** 떴다. 이름·거리만으로는
어느 승강장에 서야 하는지 고를 수 없다. 게다가 그중 하나는 도착 정보가 늘 비었고,
그 승강장이 첫 화면에 기본 선택되고 있었다 — 기본 좌표(`ANDONG_ORIGIN`)가
하필 그 승강장의 좌표였기 때문이다. 서비스의 첫 문장이 "버스가 없어요"였다.

정류장 2105곳 중 **1644곳이 다른 정류장과 이름이 같다.** 특수한 사례가 아니다.

### 결정
카카오·네이버가 쓰는 것과 같은 꼬리표를 붙인다. **방면 = 노선상 다음 정류장의 이름.**
그리고 도착정보가 원리적으로 오지 않는 승강장은 목록 맨 뒤로 보낸다.

| stationId | 방면 | 판정 |
|---|---|---|
| 354000416 | 노하동입구 | 기점 59 / 중간 31 → 정상 |
| 354000459 | 송야교사거리 | 기점 5 / 중간 47 → 정상 |
| 354000536 | (하이마삼거리) | 종점 62 / 기점 6 / **중간 0** → 도착 없음 |

카카오맵 표기(`노하동 입구 방면` · `송야교사거리 방면`)와 일치한다.

### 방면을 구하는 방법
상류는 방면을 주지 않는다. 노선별 정류장 목록(`tab=4`)에서 직접 센다.

⚠️ **바로 다음 정류장을 그냥 집으면 안 된다.** 승강장이 여러 개인 곳은 다음 순번도
이름이 같아서 "안동역(안동터미널) 방면 안동역(안동터미널)"이 나온다.
**이름이 다른 첫 정류장**까지 건너뛴다. 노선마다 다음이 갈리면(지선 분기)
최다 득표 하나만 남긴다. 여럿을 붙이면 칩이 문장이 된다.

### 정적 파일로 굽는 이유
노선이 **421개**다. 요청 시점에 계산하면 상류를 421번 부른다. 캐시가 비는 첫 요청이
그 값을 다 치르므로 안 된다. `node scripts/build-station-directions.ts`로 미리 구워
`server/data/station-directions.json`에 둔다. 노선의 정류장 순서는 시간표만큼도
자주 바뀌지 않는다(ADR-016과 같은 판단). 노선 개편 때 다시 돌리면 된다.

### 도착이 없는 승강장 — 지우지 않고 뒤로 보낸다
**노선 중간에 한 번도 놓이지 않는 정류장**은 기점이거나 종점으로만 쓰인다.
그런 승강장에는 "접근 중인 차량"이 성립하지 않아 `tab=2`가 항상 빈 배열이다(ADR-015).
전체 2105곳 중 42곳이 해당한다.

지우지 않는 이유 — 실재하는 승강장이고, 거기 서 있는 사람에게는 "여기는 안 뜬다"는
사실 자체가 답이다. 목록에서 없애면 그 사람은 자기가 선 자리를 찾다가 화면을 닫는다.
대신 뒤로 밀어 기본 선택에서 빠지게 하고, 칩과 카드가 이유를 말한다.
**`실시간` 배지도 끈다.** 실시간이 원리적으로 없는 자리에서 점이 뛰면 기다리게 된다.

### 대가
응답이 164KB → 201KB(gzip 38KB → 47KB). 브라우저가 목록을 통째로 받기 때문이다(ADR-024).
이름이 겹치는 정류장이 1644곳이라 "겹치는 것만 붙이기"로 아껴 봐야 gzip 2KB다.
나눌 이유가 없어 전부 붙였다.

회귀는 `node scripts/check-bus-logic.ts`가 지킨다 — 같은 이름 건너뛰기와
기·종점 전용 판정 두 가지다.

## ADR-027 화면에서 끊지 않는다 — 길찾기·새로고침·되돌리기

**결정일**: 2026-08-14
**상태**: 확정

### 문제
화면마다 사용자가 더 할 수 있는 일이 없는 막다른 곳이 있었다.

| 자리 | 막다른 지점 |
|---|---|
| 홈 지도 | 움직일 수 있게 해 놓고 되돌아올 방법이 없다 |
| 홈 지도 | 승강장이 안 찍힌다. 이름이 같은 셋을 글자로만 갈라야 한다 |
| 홈 정류장 | "안동역(안동터미널)"까지 왔는데 **거기로 걸어가는 길**이 없다 |
| 홈 위치 | 권한을 거부하면 이유 한 줄이 남고 다시 시도할 수단이 없다 |
| 도착 카드 | "실시간" 점만 뛴다. 언제 받은 값인지, 다시 받을 방법이 없다 |
| 상세 | 자동 갱신 타이머가 아예 없어 열어 두면 값이 그대로 늙는다 |

### 결정
- **되돌리기** — `MapCard`에 "처음 화면으로". `draw()`에서 화면 맞추기를 `fit()`으로
  떼어내 데이터 갱신과 버튼이 같은 함수를 쓴다
- **정류장 마커** — 홈 지도에 정류장을 함께 찍는다. 관광지는 핀, 정류장은 점이다.
  고른 승강장만 채운 점과 방면 이름표로 도드라진다(ADR-026의 연장). 지도는 도보권
  관광지 섹션 밖으로 꺼냈다 — 그 목록이 비는 위치에서는 지도까지 함께 사라졌다
- **길찾기** — 카카오맵 `link/to`로 넘긴다. 홈은 정류장까지, 상세는 관광지까지.
  목적지만 넘기면 출발지는 앱이 현재 위치로 잡으므로 사용자 좌표를 URL에 싣지 않는다
  (ADR-024와 어긋나지 않는다)
- **실시간 배지** — `RealtimeBadge`로 묶어 도착 카드 둘이 함께 쓴다.
  갱신 시각("방금" · "3분 전")과 새로고침이 배지에 붙는다
- **위치 재시도** — 폴백 사유 옆에 "내 위치로 다시". 확인 중일 때는 그 문구를 보여준다
- **마커 이름** — 상용 지도처럼 마커 옆에 이름을 **인쇄해 둔다**. 기본 마커의 `title`은
  데스크톱 호버 툴팁이라 폰에서는 아무 일도 없었고, 지도에 점만 찍히고 그게 뭔지 알 수
  없으면 지도가 아니라 무늬다. 말풍선이 아니라 흰 테두리를 두른 글자다 — 마커마다 흰
  상자가 뜨면 지도가 상자로 덮인다.
  누르면 뜨는 이름표도 함께 남긴다(정류장은 방면까지 붙어 "안동역(안동터미널) ·
  노하동입구 방면"). 빈 곳이나 "처음 화면으로"를 누르면 닫힌다

### 이름을 몇 개까지 인쇄할 것인가
마커가 **9개 이하일 때만** 인쇄한다(`LABEL_LIMIT`). 둘러보기는 마커가 49개까지 가는데
전부 인쇄하면 글자가 서로를 덮어 아무것도 안 읽힌다. 상용 지도는 겹침을 계산해 솎아내지만
그건 이 카드가 할 일이 아니다. 개수로 끊고, 많을 때는 눌러서 보게 한다.
상세(최대 5개)는 늘 인쇄되고, 홈은 도보권 관광지 수에 따라 갈린다.

### 시각을 SSR에서 만들지 않는다
`updatedAt`은 `onMounted`에서만 채운다. 서버 시각으로 "방금"을 찍으면 하이드레이션이
어긋나고, 서버와 사용자의 시계가 다를 수도 있다. SSR에서는 시각 없이 배지만 나간다.

### 상세의 배지는 도착이 없을 때도 남긴다
예전에는 `status === 'arriving'`일 때만 띄웠다. 그런데 다시 확인하고 싶은 순간은
정확히 "접근 중인 버스가 없어요"를 봤을 때다. 새로고침이 배지에 붙어 있으므로
그때 사라지면 안 된다.

### 상류 문자열을 innerHTML에 넣지 않는다
이름표는 `document.createElement` + `textContent`로 만든다. 정류장·관광지 이름은
상류(안동시·관광공사)가 준 문자열이다. 지도 라벨 하나 때문에 남의 데이터를
실행시킬 이유가 없다. `CustomOverlay`는 문자열 대신 DOM 요소를 받으므로 비용도 없다.
(마커 클릭은 `maps.event`로 붙지만 **CustomOverlay에는 지도 이벤트가 안 붙는다** —
정류장 점은 DOM `addEventListener`로 건다)

### ⚠️ CustomOverlay는 좌표에 가운데 정렬된다
정류장 점을 `transform: translate(-11px,-11px)`로 당겼다가 되돌렸다. SDK가 이미
content를 좌표 중심에 붙이므로 두 번 밀린다(기존 "나" 점에 transform이 없는 이유).
이름표는 `absolute`로 띄운다 — 상자 크기가 점 그대로여야 중심이 이름표 길이만큼
밀리지 않는다.

## ADR-028 상류가 종점을 안 준다 — 방면은 routeNm에서 건지고, 없으면 말하지 않는다

**결정일**: 2026-08-14
**상태**: 확정

### 사건
화면에 `청호한우촌앞 -> · 11정거장 전`이 떴다. 화살표 뒤가 비어 있고 점만 남았다.

`formatDirection`은 `via`("기점 -> 종점")에서 종점만 잘라 "○○ 방면"을 만든다.
종점이 비면 **via를 그대로 돌려주도록** 되어 있었다. 그 폴백이 화면에 새어 나온 것이다.

**상류가 조용히 바뀌었다.**

| 날짜 | via 실측 |
|---|---|
| 2026-08-13 | `"정부경북지방합동청사 -> 국립경국대"` |
| 2026-08-14 | `"정부경북지방합동청사 -> "` — 표본 50건 **전부** 종점 없음 |

ADR-006이 "명세서를 신뢰하지 말 것"이라 했는데, 이번엔 **실측한 응답조차 하루 만에
바뀐다**는 게 드러났다. 필드가 사라진 게 아니라 값만 비었으므로 타입 검사로는 안 잡힌다.

### 결정
1. **`routeNm`에서 건진다.** `"610(만휴정-길안-국립경국대-교보건너-안동터미널)"` —
   괄호 안 마지막 토큰이 종점이다. 같은 응답에 이미 들어 있어 추가 호출이 없다
2. **via가 우선한다.** 상류가 다시 채우면 그쪽이 정본이다
3. **둘 다 없으면 빈 문자열**을 돌려주고 화면은 **줄을 통째로 지운다.**
   앞 문구가 없으면 구분점(·)도 찍지 않는다. 점만 남으면 그게 고장으로 보인다

폴백으로 원문을 흘리지 않는다. 사람이 읽을 수 없는 조각을 보여주느니 아무것도
안 보여주는 편이 낫다. 이건 ADR-016("추정한 막차를 보여주지 않는다")과 같은 규칙이다.

`/api/spot-bus`는 도착 4필드만 내려보내고 있어 `routeNm`을 추가했다. 화면에 그대로
뜨는 값이 아니라 방면을 건지는 재료다.

### 같은 노선의 다음 차
"이 버스를 놓치면 얼마나 기다리나"에 답한다. 정류장에는 여러 노선이 서므로 목록의
다음 줄은 대개 **다른 노선**이다. 같은 번호를 찾아야 답이 된다. 목록이 이미 도착
임박순이라 앞에서부터 첫 번째로 만나는 같은 번호가 그 차다.

실측(2026-08-14): 염광교회앞 — 212번 3분 후, 그다음 212번 11분 후.
표본 21곳 중 4곳에서 같은 노선 2대가 동시에 잡혔다. **드물다.**
없으면 아무것도 말하지 않는다. 배차 간격을 추측해 채우지 않는다 — 추측한 다음 차는
막차 추정과 같은 종류의 거짓말이다.

회귀는 `node scripts/check-bus-logic.ts`가 지킨다(via 우선 · routeNm 폴백 · 빈 문자열).

## ADR-029 사진은 공공데이터 API 안에서만 구한다 — 세 단계, 그리고 https

**결정일**: 2026-08-16
**상태**: 확정

### 원칙
관광 이미지는 **공공데이터 API에서만** 가져온다. 다른 웹사이트를 긁지 않는다.
출처를 밝힐 수 없는 사진은 이 서비스에 실을 수 없기 때문이다(→ `/about` 데이터 출처).

### 세 단계
전부 한국관광공사 API다. 뒤로 갈수록 증거가 약해지므로 순서를 바꾸지 않는다.

| 단계 | 서비스 | 근거 | 성과 |
|---|---|---|---|
| 1 | KorService2 `areaBasedList2` | 좌표 200m + 이름 | 54곳 중 41곳 병합 |
| 2 | KorService2 `searchKeyword2` | 이름(areacode 빈 항목 구제) | 결측 46 → 21건 보충 |
| 3 | **PhotoGalleryService1** `gallerySearchList1` | 이름 + 촬영장소 | +1건 |

### 3단계를 붙인 이유와 한계
**한계부터.** 결측 14곳 중 채운 것은 **1곳(부용대)뿐이다.** 나머지 13곳은
행사·신규시설·상호(안동수페스타·플레이방월드·빙수곳간·드론코리아아카데미…)여서
공공데이터 어디에도 사진이 없다. 조회를 늘려도 안 나온다.

그럼에도 붙이는 이유는 **KorService2가 흔들릴 때 남는 유일한 사진 소스**이기 때문이다.
실측: 안동 사진 1504건 중 관광지 54곳 가운데 17곳이 이름으로 걸린다.

⚠️ **관광지마다 부르지 않는다.** `keyword=안동`으로 한 번 받아(1000건) 이름을 맞춘다.
개별 호출은 14번인데 한 번에 받는 편이 싸고, 제목에 없는 이름이 태그(`galSearchKeyword`)에
있는 경우까지 잡는다. 부용대가 그렇게 걸렸다 — 사진 제목은 "안동하회마을"이다.

⚠️ **이 서비스에는 좌표가 없다.** 1·2단계처럼 거리로 검증할 수 없어서
`galPhotographyLocation`에 '안동'이 있는 것만 남긴다. 동명이소를 거를 유일한 수단이므로
이 조건을 빼면 안 된다.

### ⚠️ 상류가 http와 https를 섞어 준다 — 배포에서만 터진다
실측(2026-08-16): 관광지 사진 41장 중 **23장이 `http://`**, 갤러리는 1000건 중 883건이다.
배포는 https이므로 그대로 두면 그 절반이 **Mixed Content로 차단된다.**
개발(`http://localhost`)에서는 멀쩡히 보이므로 눈으로는 절대 안 잡힌다.

같은 경로를 https로 요청하면 동일한 이미지가 200(image/jpg)으로 열리는 것을 확인했다.
호스트는 `tong.visitkorea.or.kr` 하나뿐이다.

이미지가 들어오는 자리가 넷(지역 병합·키워드 보충·갤러리·음식점)이라 대입하는 쪽마다
고치지 않고 `httpsImage()` 한 곳을 지나가게 했다. 새 소스를 붙일 때도 그 함수를 통과시킬 것.

## ADR-030 영문은 나란히 둔다 — 언어 전환을 만들지 않는다

**결정일**: 2026-08-16
**상태**: 대부분 폐기. **이름을 지어내지 않는다**는 원칙과 커버리지 실측만 유효하다.
"언어 전환을 만들지 않는다"는 ADR-031이, "국문 옆에 영문을 나란히 둔다"는 ADR-032가
뒤집었다. 아래 본문의 "나란히 둔다"는 그 시점의 기록으로 읽을 것.

### 커버리지가 결정했다
영문 데이터를 붙일 수 있게 되어(EngService2 활용신청) 다국어를 검토했다.
**언어 전환(토글)은 만들지 않는다.** 실측이 그 방향을 막았다.

| 대상 | 영문 있음 |
|---|---|
| 관광지 | **14 / 54** (26%) — 지역 조회만 썼을 때다. ADR-033에서 17 / 54로 올린다 |
| 음식점 | **2 / 15** (13%) |
| **정류장** | **2105 / 2105 (100%)** |

영어로 전환해 놓고 관광지 이름의 74%가 국문으로 남으면, 반만 바뀐 화면이 안 바꾼
것보다 나쁘다. 게다가 전환을 만들면 버튼·안내 문구 전부를 번역해야 하는데
그 문구들이 이 서비스의 알맹이다("돌아오는 편 시각은 공식 시간표에 없어요" 같은).

대신 **국문 옆에 영문을 나란히 둔다.** 있으면 한 줄이 늘고 없으면 그 줄이 사라진다.
한국인에게 방해되지 않고, 외국인에게는 있는 만큼 도움이 된다.

### 정류장이 진짜 수확이다
`stationEngNm`은 **2107곳 전부** 채워져 온다. 우리가 `StationPin`을 만들면서
버리고 있었을 뿐이다(ADR-024의 payload 다이어트). 외국인 여행자가 가장 먼저 막히는
지점이 "내가 선 정류장이 어디인가"인데, 그 답이 이미 받고 있던 응답 안에 있었다.

`안동역(안동터미널)` 아래 `Andong Station(Andong Terminal)`이 붙는다.
응답은 201KB → 242KB(gzip 47KB → 51KB). gzip 4KB로 커버리지 100%를 산다.

### ⚠️ EngService2는 국문과 두 가지가 다르다
- **분류 코드 체계가 다르다.** `contentTypeId=12`(관광지)로 조회하면 **0건**이다.
  안동 32건의 코드는 75·76·78·80·82·85 대역이다. 그래서 타입을 지정하지 않고
  지역만으로 조회한다. (2026-08-24부터 `lDongRegnCd=47&lDongSignguCd=170` —
  같은 조회가 32건이 아니라 57건을 준다. → ADR-034)
- **좌표로 이으면 안 된다.** 두 데이터셋의 대표 좌표가 다른 지점을 가리켜
  하회마을은 1,580m가 벌어진다(ADR-021). 연결 고리는 **제목 괄호 안의 국문명**이다.
  `"Andong Folk Village (안동민속촌)"` → `안동민속촌`. 32건 전부 이 꼴이다.

### 목록 카드에는 안 붙였다
`SpotCard`는 한 화면에 49장까지 깔린다. 26%만 영문이 붙으면 어떤 카드는 세 줄,
어떤 카드는 두 줄이 되어 격자가 들쭉날쭉해진다. 이름을 확인하러 들어가는 자리
(상세 화면)와 지금 서 있는 자리(정류장 카드)에만 둔다.

## ADR-031 언어는 주소로 가른다 — `/`는 국문, `/en`은 영문

**결정일**: 2026-08-18
**상태**: 확정

### ADR-030의 무엇이 남고 무엇이 바뀌는가

ADR-030은 두 가지를 함께 결정했다. 하나는 **이름을 어떻게 다루는가**이고
(영문이 있으면 영문, 없으면 국문, 지어내지 않는다) 다른 하나는 **언어 전환을
만들지 않는다**였다. 앞의 것은 그대로 남는다. 커버리지 실측이 근거였고 그 수치는
변하지 않았다. 뒤의 것만 바꾼다.

바꾸는 이유는 ADR-030이 든 근거가 "전환은 안 된다"가 아니라 **"반만 바뀌면 안
된다"**였기 때문이다. 반만 바뀌는 것을 막는 방법은 전환을 포기하는 것 말고도 있다.
문구를 하나도 남기지 않고 옮기고, 이름은 있는 만큼만 옮기고, 그 사실을 화면에서
숨기지 않는 것이다. 문구 사전(`app/i18n/messages.ts`)에서 `en`이 `ko`의 타입을
만족해야 하므로 **문구 누락은 컴파일에서 걸린다.** ADR-030이 걱정한 "안내 문구가
번역되지 않아 알맹이가 빠지는 일"을 구조가 막는다.

### 토글이 아니라 주소인 이유

쿠키 토글로도 만들 수 있었다. 실제로 그 방향으로 한 번 짰다가 되돌렸다.

| | 쿠키 토글 | 주소 분리 |
|---|---|---|
| 공유 | 영문을 보여주려면 "우측 상단에서 영어를 누르세요"를 함께 보내야 한다 | 링크가 곧 영문 화면이다 |
| 검색 | 한 주소에 두 언어. 색인되는 것은 하나뿐이다 | 두 주소가 각각 색인된다 (`hreflang`으로 서로를 가리킨다) |
| 첫 페인트 | 서버가 요청 쿠키를 읽어야 한다. 어긋나면 하이드레이션이 깨진다 | 주소만 보면 서버·브라우저가 같은 답을 낸다 |
| 캐시 | 같은 주소가 언어별로 다른 HTML. 캐시 키에 언어를 넣어야 한다 | 주소가 다르니 섞이지 않는다 |
| 되돌리기 | 뒤로가기가 언어를 되돌리지 않는다 | 뒤로가기가 그대로 동작한다 |

공유가 결정적이었다. 외국인 여행자에게 이 서비스를 알리는 경로는 대부분 링크다
(숙소·안내소·지인). 그 링크가 국문으로 열리면 거기서 끝난다.

### 페이지 파일은 복제하지 않는다

`nuxt.config.ts`의 `pages:extend`가 `app/pages/`에서 만들어진 라우트를 한 벌 더
만들어 `/en`을 붙인다. 컴포넌트는 같은 것을 가리킨다.

```
/            → /en
/browse      → /en/browse
/spots/:id() → /en/spots/:id()
```

`app/pages/en/`을 만들어 파일을 복제하는 길도 있었지만 택하지 않았다. 화면 로직을
고칠 때마다 두 곳을 고쳐야 하고, 한쪽만 고친 날 두 언어가 **다르게 동작한다.**
번역이 어긋나는 것은 눈에 보이지만 동작이 어긋나는 것은 안 보인다.

언어는 `useLocale()`이 경로에서 읽는다. 상태를 따로 들지 않는다 — 상태와 주소가
어긋나는 순간이 반드시 오고(새로고침·뒤로가기·공유받은 링크), 그때 화면이 자기가
어느 언어인지 모르게 된다.

### ⚠️ 내부 링크는 전부 `localePath()`를 거친다

이 구조의 유일한 실패 방식이다. `<NuxtLink to="/browse">`를 하나 남겨 두면 영문
화면을 보던 사람이 그 링크에서 국문으로 떨어지고, 돌아올 방법은 뒤로가기뿐이다.
링크는 언제나 국문 경로로 적고 `localePath('/browse')`가 접두어를 붙인다.
셸(레이아웃)·카드·목록·상세의 "근처에 함께 볼 곳"이 전부 이 경로를 지난다.

### 자동 리다이렉트는 넣지 않는다

`Accept-Language`를 보고 영문으로 보내지 않는다. 국내 사용자도 브라우저 로캘이
영문인 경우가 흔하고, 그때 정본 화면을 뺏는 셈이 된다. 헤더에 두 언어를 나란히
두고 사람이 고른다. 드롭다운도 쓰지 않는다 — 언어가 둘뿐이라 여는 동작이 순수한
손해이고, 닫혀 있는 동안 "영어가 있다"는 사실 자체가 숨는다.

### 영문 화면에서 국문이 남는 자리 — 전부 의도한 것이다

| 자리 | 왜 남는가 |
|---|---|
| 관광지 이름 40/54 | 상류(EngService2)에 영문이 없다. 지어내면 그 이름으로 길을 못 묻는다 |
| 주소 | 상류에 영문 주소가 없다 |
| 관광지 설명 | 국문만 온다. 기계로 옮기지 않는다 |
| 방면(`○○ 방면`) | 노선 문자열 속 지명이라 맞출 상대가 없다 → ADR-028 |
| 지도 위 이름표 | 배경 지도(카카오맵)가 국문이다. 핀만 영문이면 지도와 어긋나 오히려 못 찾는다 |
| 시간표 출발지(`터미널발`) | 안동시 시간표 문서의 표기 그대로다 |
| 걷는 길의 지명 | 공식 영문명을 확인하지 못했다. 문장(`걸어서 2분`)만 옮겼다 |

반대로 **영문으로 반드시 나가야 하는 것**은 정류장 이름과 한계 고지 문장이다.
정류장은 `stationEngNm`이 2105곳 전부 채워져 오므로 "어디서 내리나"에 영문으로
답할 수 있다. 관광지 상세의 정류장명은 정적 매핑(`spot-station-map.json`)에서
와서 영문이 없었으므로, `/api/spot-bus`가 `stationId`로 `/api/bus/stations`를
조회해 이어 붙인다(1일 캐시라 추가 비용이 없다).

한계 고지는 `server/data/spot-station-map.json`의 `note`·`warning`이다. 우리가 쓴
문장이므로 `noteEn`·`warningEn`을 나란히 넣었다. **영문 화면에서만 이 문장이 국문으로
남으면, 영어 사용자만 근거 없는 확신을 갖고 밤에 정류장에 서 있게 된다.** → ADR-016

### 상태에는 문구가 아니라 키를 담는다

`useLocation`이 그 자리였다. 폴백 이유를 완성된 국문 문장으로 담고 있었는데,
`useState`는 라우트 이동으로 초기화되지 않으므로 언어를 바꿔도 그 문장만 이전 언어로
남는다. `'denied'` 같은 키를 담고 화면이 `t.location[...]`으로 옮긴다.

같은 이유로 **분류 칩이 들고 있는 값도 국문 원본이다.** 번역된 문자열을 상태에 담으면
`spot.category === '역사관광'` 비교가 영문 화면에서 전부 어긋나 목록이 통째로 빈다.

## ADR-032 한 화면에는 한 언어만 — 나란히 두던 이름을 걷어낸다

**결정일**: 2026-08-19
**상태**: 확정. ADR-030의 "국문 옆에 영문을 나란히 둔다"를 폐기한다.

### 나란히 두기가 필요했던 이유가 사라졌다

ADR-030에서 두 언어를 한 줄씩 겹쳐 둔 것은 **언어 전환이 없었기 때문이다.**
화면이 하나뿐이니 그 하나가 두 사람을 다 받아야 했고, 그래서 국문 이름 아래
영문을 붙였다. 다음 날 ADR-031이 주소로 언어를 갈랐다. `/`는 국문 화면이고
`/en`은 영문 화면이다. 두 사람이 각자의 화면을 갖게 된 순간, 한 화면이 두
사람을 받을 이유가 없어졌다. **그런데 겹쳐 둔 줄만 그대로 남아 있었다.**

남겨 두면 치르는 값이 있다.

- **읽는 사람이 매 항목마다 한 줄을 건너뛴다.** 국문 화면에서 영문 줄은 읽을
  줄이 아니고, 영문 화면에서 국문 줄도 그렇다. 정류장 카드처럼 이름이 화면
  맨 위에 오는 자리에서, 정작 필요한 정보(도착 시각)가 그만큼 아래로 밀린다.
- **항목마다 줄 수가 다르다.** 영문이 붙는 관광지는 54곳 중 17곳이라 어떤
  카드는 세 줄, 어떤 카드는 두 줄이 된다. 격자가 들쭉날쭉해진다 —
  ADR-030이 목록 카드에는 안 붙인 이유가 이것인데, 상세와 정류장 카드에서만
  같은 문제를 감수할 근거가 언어 분리 이후에는 없다.
- **언어를 골랐다는 사실이 화면에서 부정된다.** 영어를 눌러 `/en`으로 온
  사람에게 국문이 계속 따라붙으면, 고른 것이 무엇이었는지 흐려진다.

걷어낸 자리는 셋이다 — 관광지 상세의 제목 아래, `BusPanel`·`SpotBusPanel`의
정류장 이름 아래. `useDisplay()`에서 `otherName`·`stationOtherName`을 지웠다.

### "표지판을 손으로 가리킨다"는 어떻게 되는가

ADR-030이 국문을 남긴 실용적 근거였다. 그 필요는 인정하지만 **이름 아래 한 줄로
푸는 문제가 아니다.** 실제로 길을 묻는 순간에 필요한 것은 이름 한 줄이 아니라
"어느 승강장인가"이고, 그건 이미 지도가 답한다 — 지도 위 이름표는 배경 지도
(카카오맵)가 국문이라 **영문 화면에서도 국문으로 둔다**(ADR-031의 표 그대로).
정류장 카드의 길찾기 링크도 좌표를 그대로 카카오맵에 넘긴다.

즉 현장에서 국문 글자가 필요한 사람은 지도에서 그것을 얻는다. 모든 목록·카드에
국문을 한 줄씩 뿌려 두는 방식은 그 필요에 비해 값이 너무 컸다.

### 영문 화면에 국문이 남는 것과는 다른 문제다

이 ADR이 지우는 것은 **일부러 덧붙인 반대편 언어**뿐이다. 상류에 영문이 없어
국문이 나오는 자리(관광지 이름 40/54, 주소, 설명, 방면 표기 등)는 그대로다.
ADR-031의 표가 여전히 유효하다. 그 자리를 로마자로 지어내 채우지 않는다 —
우리만 아는 영문명으로는 길을 물을 수도 검색할 수도 없다.

**따라서 `/en`이 "영문만"이 되지는 않는다.** 될 수 있는 것은 "우리가 아는
영문은 전부 영문으로, 모르는 것은 국문 그대로, 같은 말을 두 번 쓰지 않는다"까지다.

### 검색은 두 언어를 계속 본다

`browse.vue`의 `matchesKeyword`는 국문명·주소·영문명을 모두 뒤진다. 그대로 둔다.
검색어는 **입력**이지 표시가 아니라서, 두 언어를 받아도 화면에 다른 언어가
나타나지 않는다. 좁히면 국문 화면에서 `Hahoe`를 친 사람이 0곳을 받을 뿐이다.

## ADR-033 영문명은 세 번 찾는다 — 지역 조회만으로는 하회마을이 빠진다

**결정일**: 2026-08-19
**상태**: 확정

### 26%인 줄 알았는데 우리가 덜 찾고 있었다

ADR-030이 "관광지 54곳 중 14곳(26%)"을 상류의 한계로 기록했다. 그 수치가
`EngService2/areaBasedList2(areaCode=35, sigunguCode=11)` **한 번**의 결과였다는
것이 문제였다. 영문 레코드 중에 `areacode`가 **빈 값**인 것들이 있다.

```
264148 | areacode="" sigungucode="" | Andong Hahoe Village (안동 하회마을 …)
```

안동 최대 관광지가 영문 데이터를 **가지고 있는데도** 목록에서 빠져 있었다.

이건 새 함정이 아니다. ADR-022가 이미 같은 문장을 적어 두었다 — *"관광지
areacode가 빈 값이라 지역 조회에 안 잡힐 뿐, 이름으로 찾으면 이미지가 있다."*
**이미지에는 그 처방을 썼고 영문명에는 안 썼다.** 같은 상류, 같은 결함, 다른 대응.

### 세 단계로 찾는다

| 단계 | 호출 | 얻는 것 |
|---|---|---|
| 1. 지역 조회 `areaBasedList2(areaCode=35)` | 1회 | 32건 후보 → 14곳 매칭 |
| 2. 광역 검색 `searchKeyword2(keyword='안동')` | 1회 | 후보 +20건 → **+안동하회마을** |
| 3. 이름 재검색 `searchKeyword2(관광지 이름)` | 결측 × 최대 2 | **+월영교 +부용대 +만휴정** |

**14/54 → 17/54.** 비율로는 26% → 31%지만 들어온 자리가 다르다. 방문 순위
**1·2·8·10위**가 채워지면서 상위 11곳 중 8곳이 영문 이름을 갖는다.

2단계를 따로 두는 이유는 값이 싸기 때문이다. 호출 한 번에 후보가 20건 는다.
3단계는 결측 40곳에 대해 44회를 더 쓰므로 **관광지에서만 켠다**(`deepSearch`).
음식점 15곳은 전부 이름으로 재검색해 봤지만 이미 붙은 2곳 말고는 0건이다 —
ADR-023이 이미지에서 확인한 것과 같다. 음식점은 지역 조회에 정상적으로 잡히고,
**그 레코드에 영문이 없다.** 조회를 몇 번 하든 없는 것은 없다.

실측(2026-08-19, 캐시 비운 상태): `/api/spots` 응답 2.9초. 3단계를 켠 뒤에도
ADR-022 시절 기록된 11초보다 짧다.

### 양방향 `includes`는 오탐을 낳고 있었다

기존 매칭은 `korean.includes(key) || key.includes(korean)`이었다. 그래서
**도산서원선비문화수련원이 화면에서 "Dosanseowon Confucian Academy"였다.**
서원과 수련원은 다른 시설이다. 영문 화면만 보는 사람은 이 카드를 유네스코
서원으로 읽고 들어간다.

포함관계는 방향에 따라 뜻이 다르다.

| 관계 | 예 | 판정 |
|---|---|---|
| 조각 == 상류 국문명 | `하회마을` == `안동 하회마을 [유네스코…]` | 같은 곳 |
| 상류 국문명이 조각으로 **시작** | `묵계서원` → `묵계서원 및 안동김씨 묵계종택` | 같은 곳을 길게 적었다 |
| **우리 이름이 더 길다** | `도산서원선비문화수련원` ⊃ `도산서원` | **다른 곳** |

우리 이름이 더 길다는 것은 보통 "그 안에 있는 다른 시설"이라는 뜻이다.
슬래시 별칭(`낙동강12경(부용경)/부용대`)은 조각으로 먼저 가르므로 이 규칙에
걸리지 않는다. `nameFragments()`를 갤러리 매칭과 함께 쓴다.

### ⚠️ `searchKeyword2`는 전국을 뒤진다 — 주소로 걸러야 한다

2·3단계를 붙이면 검색 범위가 안동을 벗어난다. 실제로 걸려 온 것들이다.

```
안동시립박물관    → 강릉시 오죽헌/시립박물관   @ Gangneung-si
백조공원/음악분수 → 방축천 음악분수           @ Sejong-si
천년숲           → 경북천년숲정원            @ Gyeongju-si
```

셋 다 이름 규칙만으로는 통과한다("천년숲" ⊂ "경북천년숲정원"). 거를 수단은
`addr1`뿐이다 — **영문 레코드는 `addr1`에 `Andong-si`가 있어야 받는다.**
좌표로 거르지 않는 이유는 ADR-021이다. 두 데이터셋의 대표 좌표가 하회마을에서만
1,580m 벌어져, 거리를 넉넉히 주면 동명이소가 통과하고 조이면 본체가 떨어진다.
실측: 안동 영문 레코드 32건 전부 주소에 `Andong-si`가 들어 있다.

### 확인하고 접은 길들

| 시도 | 결과 |
|---|---|
| `contentId`로 국문↔영문 잇기 | **불가.** 두 서비스의 ID 체계가 별개다. 안동 32건 교집합 **0건**, 서로의 ID를 반대편 `detailCommon2`에 넣으면 `totalCount 0` |
| `areaBasedSyncList2` | 281건이 오지만 249건이 `showflag=0`(삭제). 살아 있는 건 같은 32건이다 |
| `lDongRegnCd=47&lDongSignguCd=47170` | **0건.** 영문 레코드의 lDong 값은 `47`/`170`이라 시군구 코드가 안 맞는다 |
| `keyword='Andong'`(영문) | 32건이 오지만 국문 `'안동'`이 준 것 외에 새로 걸리는 것이 0건 |
| 나머지 37곳 이름 개별 검색 | **전부 0건.** 시장·문화예술의전당·자연휴양림·물놀이장 — 번역된 적이 없다 |

마지막 줄이 이 ADR의 천장이다. **31%가 상류의 실제 한계다.** 로마자로 지어내
채우지 않는다는 ADR-030의 원칙은 그대로다.

### 대괄호 꼬리는 떼고 괄호 주석은 남긴다

상류 제목이 등재 사실을 대괄호로 붙여 준다.

```
Dosanseowon Confucian Academy [UNESCO World Heritage] (도산서원 [유네스코 세계유산])
```

국문 화면은 "도산서원"으로만 나오므로 그대로 두면 영문 제목만 두 배로 길어진다.
이름 자리에는 이름만 둔다 → `Dosanseowon Confucian Academy`.

반대로 **괄호 안의 영문 주석은 남긴다.** `Andong Gunja Village (Ocheon Historic
Site)`에서 괄호 안은 그 마을의 다른 이름이라 이름의 일부다. 그래서 제목을 자를 때
`replace(/\s*\(.*$/, '')`를 쓰지 않는다 — 첫 괄호부터 지우면 이 설명이 함께
날아가고, 중첩 괄호(`(안동 군자마을(오천유적지))`)도 정규식 한 줄로는 못 센다.
뒤에서부터 짝을 맞춰 **한글이 든 마지막 그룹만** 떼어낸다.

### 아직 안 쓰는 것 — 영문 설명과 영문 주소

`EngService2/detailCommon2`가 매칭된 레코드에 **완전한 영문 `overview`**와 영문
`addr1`을 준다. 지금은 붙이지 않았다. 관광지 설명은 `Spot.description`을 채울
소스가 아직 미정이고(미해결 과제), 영문 주소만 17곳에 붙이면 목록 안에서 영문
주소와 국문 주소가 섞인다. 붙일 때가 오면 여기 적힌 매칭이 그대로 쓰인다.

> **2026-08-24 후속** — 이 ADR의 3단계 구조는 ADR-034로 걷어냈다. 원인이 상류
> 결함이 아니라 **우리가 쓰던 조회 파라미터**였다. 법정동 코드로 한 번 부르면
> 세 단계 전부와 같은 17곳이 나온다. 위 표의 진단은 틀렸고, 매칭 규칙
> (`splitEngTitle`·`isSameEngPlace`)은 그대로 살아 있다.

## ADR-034 지역 코드를 법정동 코드로 바꾼다 — 없던 게 아니라 안 부르고 있었다

**결정일**: 2026-08-24
**상태**: 확정

### 1년치 우회로가 전부 같은 오진 위에 서 있었다

이 저장소에는 "안동 핵심 관광지가 KorService2에 없다"는 전제로 쌓아 올린 것이
여럿이다. ADR-004가 그렇게 적었고, 08-02가 "이름으로 재검색하면 찾을 수 있다"는
우회로를 냈고, ADR-022가 이미지 보충을, ADR-033이 영문명 3단계를 만들었다.
ADR-010은 아예 "축제 0건"을 근거로 기능 하나를 통째로 뺐다.

**전부 틀렸다.** 레코드는 처음부터 있었다. KorService2와 EngService2는 지역
필터를 두 벌 받는데, 우리가 쓰던 쪽이 좁았다.

| 조회 | `areaCode=35` `sigunguCode=11` | `lDongRegnCd=47` `lDongSignguCd=170` |
|---|---|---|
| 관광지(12) | 63건 | **107건** |
| 문화시설(14) | 11건 | **26건** |
| 축제(15) | **0건** | **7건** |
| 음식점(39) | 15건 | **27건** |
| 영문(EngService2) | 32건 | **57건** |
| 하회마을·도산서원·월영교·병산서원·봉정사·만휴정 | 전부 없음 | **전부 있음** |

이 항목들은 상류에서 `areacode`·`sigungucode`가 빈 값이고 법정동 코드만 채워져
있다. ADR-022와 ADR-033이 "상류 데이터 결함"이라 부른 것의 정체다. 결함은
맞지만, 그 결함을 **비껴가는 문이 같은 API에 이미 열려 있었다.**

`⚠️ lDongSignguCd`는 **`170`**이다. LocgoHub는 같은 법정동 코드를 `47170`으로
받는데, 여기에 `47170`을 주면 **오류 없이 조용히 0건**이 온다. 두 상수가 같은
체계의 다른 자릿수라 섞기 쉽고, 섞으면 목록이 통째로 비면서 에러도 안 난다.

### 이미지 보충의 2단계가 네트워크에서 메모리로 내려왔다

원인이 바뀌니 처방의 모양이 바뀐다. 예전 2단계는 **없는 것을 찾으러 밖에 나가는**
일이었다. 지금은 그 레코드가 이미 손안의 풀에 있다. 1차 병합이 놓치는 이유는
"없어서"가 아니라 **좌표 200m 게이트** 때문이다 — 두 API의 대표 좌표가 다른
지점을 가리켜 하회마을만 1,580m가 벌어진다(ADR-021).

그래서 판정 규칙은 그대로 두고 후보의 출처만 바꿨다(`pickByName`).

| 단계 | 예전 | 지금 | 얻는 곳 |
|---|---|---|---|
| 1. 지역 병합 (좌표 200m) | 〃 | 〃 | 30곳 |
| 2. 이름 매칭 | `searchKeyword2` 수십 회 | **풀 안에서, 호출 0회** | +6곳 |
| 3. 이름 재검색 | — | `searchKeyword2` 21회 | +4곳 |
| 4. 관광사진 갤러리 | 〃 | 〃 | +1곳 |

3단계가 남은 이유는 풀이 관광지(12)+문화시설(14)뿐이기 때문이다. 다른
`contentTypeId`로 등재된 4곳은 여전히 밖에서 찾아야 한다.

영문명은 3단계가 통째로 사라졌다. 법정동 조회 **1회**가 옛 3단계(호출 2 + 40회)와
**같은 17곳**을 준다. 옛 두 경로가 주는 레코드는 법정동 조회에 전부 포함되고,
이름 재검색 40회는 **0곳**을 더 찾았다.

### 고친 것은 중앙값이 아니라 꼬리다

같은 날 같은 회선에서 캐시를 비우고 4회씩 쟀다.

| | 실측 | 최악 |
|---|---|---|
| 옛 방식 | 2.76 / 2.89 / 4.09 / **12.61**초 | **12.6초** |
| 새 방식 | 1.71 / 1.74 / 1.75 / 1.84초 | 1.84초 |

중앙값은 3.5초 → 1.75초지만, **서버리스 10초 제한을 넘기던 것은 중앙값이 아니라
꼬리였다.** 호출이 수십 회면 "가장 느린 한 번"에 걸릴 확률이 누적되고, 그 요청이
타임아웃되면 캐시가 영영 안 채워진다. 호출을 줄이자 분산이 함께 사라졌다.
문서에 적혀 있던 11초는 과장이 아니라 그 꼬리를 본 기록이었다.

응답 내용은 대조해서 동일함을 확인했다 — 54곳, 이미지 41곳(76%, 같은 사진·같은
`contentid`), 영문 17곳. 유일한 차이는 안동군자마을이
`Andong Gunja Village (Ocheon Historic Site)`로 나오는 것인데, 괄호 안 영문 주석은
이름의 일부라 남기기로 ADR-033이 이미 정해 둔 쪽이다.

### 정적 스냅샷을 만들지 않는다

"배포 전에 빌드 타임 생성이나 스케줄 워밍으로 옮긴다"가 원래 계획이었다. 그
계획은 API 응답을 파일로 굳히는 방향이었고, 심사 요건과 부딪힌다.

> 데이터 활용은 한국관광공사 OpenAPI 형태만 인정되며, 단순 파일 데이터
> 다운로드 활용은 인정되지 않아 심사에서 제외됩니다. — ADR-003

실제로는 API를 호출해 만든 결과라도 저장소에 데이터 파일로 보이면 저촉되는
것처럼 읽힌다. 100% 런타임 조회로 남길 수 있으므로 그 긴장을 통째로 없앤다.
성능 때문에 데이터 활용 점수를 걸 이유가 없다.

### 음식점은 함께 옮기지 않았다

`fetchFoodPlaces`만 옛 지역 코드로 남겨 뒀다. 범위가 15건 → 27건으로 **늘어나기**
때문이다. 늘어나는 12곳의 이름을 보고 향토음식 태깅(ADR-023)이 그것들에도
성립하는지 확인해야 한다. 콜드스타트를 고치는 작업에 데이터 범위 변경을 얹으면
둘 중 무엇이 화면을 바꿨는지 나중에 못 가른다.

### 남는 것

- ADR-010(축제 제외)은 **번복 대상이다.** 근거였던 "0건"이 조회 방식의 결과였다.
- 안동호반자연휴양림과 그 방문자센터가 같은 `contentid`에 붙어 사진이 겹친다.
  옛 방식에도 있던 것이라 이번 변경과 무관하지만, LocgoHub가 한 시설을 두
  항목으로 등재한 자리다. 별도로 판단한다.

## ADR-035 축제를 잇는다 — 열릴 때만, 그리고 버스까지

**결정일**: 2026-09-01
**상태**: 확정 (**ADR-010 번복**)

### ADR-010의 "0건"은 데이터가 아니라 조회 방식이었다

ADR-010은 `areaBasedList2`로 축제(contentTypeId=15)를 조회해 `totalCount: 0`을
받고 기능을 통째로 뺐다. ADR-034가 같은 오진의 다른 얼굴을 이미 정정했다 —
그 0건은 옛 지역 코드로 물었기 때문이다.

| 조회 | `areaCode=35` `sigunguCode=11` | `lDongRegnCd=47` `lDongSignguCd=170` |
|---|---|---|
| 축제(15) | **0건** | **7건** |

실측(2026-09-01, `searchFestival2`, 203ms 1회): 7건, **이미지 7/7 = 100%**
(관광지는 76%), 좌표·주소 전부 있음. 관광지보다 데이터가 깨끗하다.
7건 전부 `areacode`·`sigungucode`가 빈 값이고 법정동 코드만 채워져 있다.

**ADR-010이 남긴 "향후" 제안도 함께 반증됐다.** "중심관광지 API의 축제 항목을
활용한다"고 적었고 "차전장군노국공주축제가 54위로 존재한다"를 근거로 들었는데,
실측하면 LocgoHub 안동 목록 54곳에 **축제는 0건**이다(분류 분포: 문화관광 21 ·
역사관광 17 · 레저스포츠 5 · 기타관광 4 · 쇼핑 3 · 자연관광 2 · 체험관광 2).
축제로 갈 수 있는 문은 `searchFestival2` 하나뿐이다.

### `searchFestival2`여야 하는 이유는 날짜다

`areaBasedList2`에 `contentTypeId=15`를 주는 길도 있고 `searchKeyword2`로
이름을 잡는 길도 있다. 둘 다 쓰지 않는다. **그 응답에는 `eventstartdate`가
없다.** 축제에서 날짜를 잃으면 남는 것은 이름뿐이고, 그러면 지난 축제와 지금
열리는 축제를 화면이 구분할 수 없다.

`⚠️ eventStartDate`는 "그 기간에 **열리는**"이 아니라 "그 기간에 **시작하는**"이다.
필수 파라미터인데 `eventStartDate=오늘`로 주면 **0건**이 온다 — 진행 중인
축제조차 안 나온다. 넓게 받아서 우리가 거르는 것이 유일하게 맞는 방식이다.

`⚠️ progresstype`·`festivaltype`을 진행 상태로 쓸 수 없다. 이름은 그렇게
읽히지만 실측 값은 `"선택안함"` 아니면 빈 문자열이고 `festivaltype`은 7건
전부 빈 값이다. **진행 여부는 우리가 날짜로 판정한다.**

### 탭이 아니라, 있을 때만 나타나는 헤더 아이콘

축제 탭을 만들지 않는다. 레이아웃이 이미 같은 판단을 내려 뒀다 — "안내는 NAV에
넣지 않는다. 목적지가 아니라 참고 자료이고, 넣으면 모바일 탭바가 4칸이 되어 주
동선 셋이 좁아진다." 축제는 그보다 더하다. 안동 축제는 7건이고 대부분의 날에
진행중이 0건이라, 탭으로 두면 **주 동선 하나를 내주고 빈 화면을 얻는다.**

그래서 데이터가 있을 때만 존재한다. 없으면 헤더의 그 자리가 통째로 비고 언어
링크가 오른쪽 끝을 그대로 차지한다. 정류장을 확인하지 못한 관광지를 비워 두는
것과 같은 규칙이다(ADR-016).

홈이 아니라 헤더에 두는 이유는 전역이기 때문이다. 홈에만 두면 공유 링크로
관광지 상세에 바로 들어온 사람은 지금 축제가 열리는 줄 모른 채 화면을 닫는다.

### 진행중만 보여주면 대부분의 날에 빈 화면이다

2026-09-01 기준 진행중 **0건**, 예정 3건, 종료 4건이다. 진행중만 거는 설계는
가장 단순하고 가장 자주 아무것도 안 보여준다. **예정 30일 창까지 연다.**

| 날 | 진행중만 걸었다면 | 예정 30일까지 열면 |
|---|---|---|
| 09-01 (오늘) | 없음 | K-스토리 D-16, 탈춤 D-23 |
| 09-20 (URL 제출) | 없음 | 탈춤 D-4, 안아드림 D-12 |
| 09-24 ~ 10-04 | 탈춤 진행중 | 탈춤 **진행중** |
| 10-28 (최종 발표) | 없음 | 없음 |

30일보다 넓히지 않는다. 넉 달 뒤 축제까지 띄우면 이 아이콘이 상시 노출되고,
"지금 뭔가 열린다"는 신호가 아니라 그냥 또 하나의 메뉴가 된다.

**10-28에는 아이콘이 사라진다.** 그날 화면 어디에도 축제 데이터를 쓴다는 흔적이
남지 않으므로, 출처는 `/about`의 데이터 출처 목록이 상시로 떠맡는다. 기능이
조건부라고 출처까지 조건부일 이유는 없다.

### 캐시하는 것과 하지 않는 것이 갈린다

| | 주기 | 이유 |
|---|---|---|
| 원본 목록 | **1일 캐시** | 축제 등재는 월 단위로도 안 바뀐다 |
| 진행/예정 판정 | **캐시 안 함** | 날짜가 바뀌면 답이 바뀌어야 한다 |

축제는 이 서비스에서 **날짜에 의존하는 유일한 데이터**다. 관광지처럼 결과까지
통째로 캐시하면 자정을 넘겨 "지금 열립니다"가 하루 틀어진다.

`⚠️` 오늘을 **KST로 계산한다.** 배포 환경(서버리스)의 시스템 시각은 UTC라
`new Date().toISOString()`을 그대로 쓰면 KST 09-24 00:30이 UTC로는 아직 09-23이다.
탈춤페스티벌이 시작하는 바로 그 순간에 "D-1"이라 적히는 오차가 여기서 난다.

### 축제 목록이 아니라 이 서비스의 화면이 되려면 버스까지 가야 한다

축제 이름과 날짜는 어디에나 있다. "그래서 어느 버스를 타느냐"에 답하는 곳이 없어서
이 서비스를 만들었다(ADR-012). 팝업은 가까운 정류장과 실시간 도착까지 잇는다.

관광지는 `spot-station-map.json`에 **사람이 확인한** 매핑을 둔다. 축제에는 그
방식을 쓸 수 없다 — 매년 바뀌고 새로 생기는데 손으로 확인한 매핑은 그 속도를 못
따라가고, 못 따라간 해에는 화면이 조용히 비거나 작년 정류장을 가리킨다.
**좌표에서 계산하고, 계산해서 구했다는 사실을 화면에 적는다.**

계산으로 뽑아도 되는 조건인지 먼저 쟀다. 실측(2026-09-01) 7건 전부 최근접
정류장이 400m 이내다.

| 축제 | 최근접 정류장 | 거리 |
|---|---|---|
| 안동국제탈춤페스티벌 | 탈춤공원건너 | **97m** |
| 안동벚꽃축제 · 동아시아문화도시 | 탈춤공원건너 | 137m |
| 차전장군 노국공주축제 | 구 안동역 | 126m |
| 안동 수(水)페스타 | 현진에버빌 | 183m |
| 2026 경북 K-스토리 페스티벌 | 청소년수련관쉼터 | 200m |
| 안아드림 페스티벌 | 농협경북도청지점 | 295m |

`⚠️` **승강장을 하나만 주면 안 된다.** 탈춤페스티벌의 1·2위가 `탈춤공원건너`(97m)와
`탈춤공원앞`(98m)이다. 1m 차이의 반대 방향 승강장이고, 가장 가까운 쪽이 내가 갈
방향이라는 보장이 없다. 게다가 **영문명이 둘 다 `Talchum gong-won`으로 같다** —
영문 화면에서는 두 칩이 글자 그대로 구별되지 않는다. 방면(`direction`)이 유일하게
둘을 가르는 정보다. 홈이 같은 이유로 같은 처방을 쓴다.

### 영문은 있는 만큼만

`EngService2/searchFestival2` + 법정동 코드로 3건이 온다(옛 지역 코드로는 0건).
국문 7건과 이어지는 것은 **탈춤페스티벌 하나**다. 하필 그 하나가 심사 기간에
열리는 축제라 값이 크다.

`⚠️` **contentid가 다르다** — 국문 506670, 영문 697123. 두 서비스는 ID 체계가
별개다(ADR-033). 잇는 고리는 제목 괄호 안의 국문명과 날짜이고, **둘 다** 맞을 것을
요구한다. 같은 이름의 축제가 해마다 열리는 데이터라 이름만 보면 작년 회차에
올해 이름을 붙이게 된다.

`⚠️` 영문 목록이 국문 목록의 부분집합이 아니다. `월영야행`과
`하회별신굿탈놀이 상설공연`은 **영문에만 있다.** 그래도 영문 화면의 목록을 영문
응답으로 만들지 않는다. 두 언어가 다른 축제를 보여주면 같은 서비스가 아니게 된다.
영문 응답은 이름을 붙이는 데만 쓴다.

### 안 한 것

- `detailIntro2`(contentTypeId=15)를 부르지 않았다. `eventplace`·`playtime`·
  `usetimefestival`·`sponsor1`·`program`을 준다. 축제당 호출 1회가 늘어난다.
  주소로도 화면이 서므로 이번 범위에 넣지 않았다.
- 관광지 상세(`/spots/[id]`)에 "이 근처에서 축제가 열려요"를 붙이지 않았다.
  탈춤공원 반경 안에 관광지가 여럿이라 성립하지만, 축제 팝업이 이미 그 답을 준다.

## ADR-036 운행 상태를 넷으로 가른다 — `runTotCnt` 0의 뜻이 하나가 아니다

**결정일**: 2026-09-10
**상태**: 확정 (**ADR-015의 연장**)

### 화면이 점심때 "오늘 운행이 끝났어요"라고 말하고 있었다

ADR-015는 도착정보가 빈 배열일 때 `runTotCnt`로 두 상황을 갈랐다.

```
runTotCnt > 0 → waiting  "배차가 길어요. 기다리면 옵니다"
runTotCnt = 0 → closed   "오늘 이 노선 운행이 끝났어요"
```

그 이분법이 틀렸다. `runTotCnt`가 0인 이유는 **셋**이다.

| 이유 | 예 |
|---|---|
| 첫차 전 | 06:36에 월영교 112번(첫차 08:25) |
| 배차가 길어 지금 노선 위에 차가 없다 | **12:42에 같은 노선** — 하루 7회라 낮에도 빈다 |
| 막차 후 | 22:00 이후 |

실측(2026-09-10 06:36): 안동 전체 **58개 노선 63대**가 운행 중인데 112번만 0대.
같은 날 12:42에도 0대. 그 두 시각에 "오늘 운행이 끝났어요"는 부정확한 것이 아니라
**정반대**이고, 여행자에게 그날 그 관광지를 포기하라고 말한다.

### 빠져 있던 신호는 "안동 전체가 도는가"

안동시 API는 노선별 첫차·막차(`stTm`·`edTm`)를 전부 null로 준다(ADR-016). 시계로
"첫차 전"을 추정할 근거가 없다. 대신 상류가 실제로 주는 값이 하나 더 있다 —
**다른 노선들의 `runTotCnt`**. 노선 하나가 0인 것과 421개가 전부 0인 것은 다르다.

```ts
decideStatus(arrivalCount, runTotCnt, fleetRunning)
  arrivalCount > 0        → 'arriving'
  runTotCnt > 0           → 'waiting'    이 노선이 돈다. 기다리면 온다
  fleetRunning            → 'routeIdle'  이 노선만 0. 끝났다고 말하면 안 된다
  아니면                   → 'offHours'   안동 전체가 멈춘 시간대
```

`/api/spot-bus`는 이미 421개 노선 목록을 통째로 받고 있어서(`/api/bus/routes`,
1분 캐시) **추가 상류 호출이 0회**다. 한 줄을 더 훑을 뿐이다.

### 상태 이름이 시각을 주장하지 않게 한다

`closed`("끝났다")를 `offHours`("다니지 않는 시간")로 개명했다. 문구도 같이 바꿨다 —
"지금은 버스가 다니지 않는 시간이에요"는 새벽 3시에도 밤 11시에도 참이다. 시계로
첫차 전/막차 후를 갈라 말하는 안도 있었지만 채택하지 않았다. 그러려면 "정오 이전이면
첫차 전"류의 임의의 경계가 코드에 들어가고, 그건 상류가 주지 않는 것을 추정하는
일이다. ADR-016이 막차에 대해 내린 판단과 같은 기준이다.

`routeIdle`의 본문은 첫차가 아니라 **운행 시각**을 가리킨다. 낮 12시에
"첫차 시각을 확인하세요"는 어긋난다.

### 곁가지로 고친 것

**`SpotBusPanel`의 `default:` 갈래.** `status`가 예상 밖 값이거나 `undefined`여도
가장 센 경고(빨간 톤 "오늘 끝났어요")로 떨어지고 있었다. 모르는 상태에서 가장 센
문장을 고르는 것이 가장 나쁜 기본값이다. 갈래를 전부 적고 모르는 값은 가장 약한
쪽(`routeIdle`, 회색)으로 보낸다.

**`/api/spot-routes`의 캐시가 1시간이었다.** 그 응답에서 시시각각 바뀌는 값이
`runTotCnt` 하나인데 배지가 최대 1시간 묵는다. 첫차가 08:25에 나가도 화면은
"차가 없어요"를 들고 있었다. `/api/bus/routes`와 같은 1분으로 맞췄다.

**두 카드가 같은 신호를 본다.** 상세 화면에는 실시간 카드와 노선 카드가 나란히
뜨는데, 각자 다른 근거로 운행 여부를 말하면 언젠가 서로 다른 말을 한다.
`fleetRunning`을 두 응답에 함께 실었다.

### 홈은 건드리지 않았다

`BusPanel`은 정류장 단위라 노선을 특정할 수 없어 애초에 단정하지 않는다
("배차 간격이 길어서일 수도, 오늘 운행이 끝나서일 수도 있어요"). 틀린 문장이 아니다.
30초마다 도는 화면이라 전체 운행 신호를 넣으려면 별도 캐시 유틸이 필요하고,
그건 이번 범위가 아니다.

**회귀 검증**: `node scripts/check-bus-logic.ts` — 네 상태 전부. 특히
`decideStatus(0, 0, true) === 'routeIdle'`이 뒤집히면 아침에 온 여행자가
그날 그 관광지를 포기한다.

## ADR-037 종점 승강장에는 도착 정보가 온다 — 기점만 걸러낸다

**결정일**: 2026-09-10
**상태**: 확정 (**ADR-015 부분 정정**)

### 하나의 조건이 두 가지를 묶고 있었다

ADR-015는 "접근 중인 차량"이 성립하지 않는 승강장을 화면에서 뒤로 밀기로 했다.
그 판정을 `build-station-directions.ts`가 **"노선 중간에 한 번도 놓이지 않음"**
하나로 계산했다. 그 조건은 기점과 종점을 한 덩어리로 묶는다.

둘은 다르다. 기점에는 그 정류장을 향해 오는 차가 없지만, **종점에는 있다.**
지금 그리로 달려오는 중이다.

### 실측 (2026-09-10 19:20 · 49개 노선 76대 운행 중)

53곳을 전부 조회하고, 각 정류장이 노선에서 맡는 역할로 갈랐다. 0건은 그대로
근거가 되지 않는다 — 그 정류장에 오는 노선에 차가 없어서일 수 있다. 그래서
**도착 측 차량이 실제로 도는 정류장만** 유효 표본으로 셌다.

| 분류 | 곳 | 유효 표본 | 도착 있음 |
|---|---|---|---|
| 기점으로만 등장 | 18 | 7 | **0** |
| 종점으로만 등장 | 18 | 3 | **3 (전부)** |
| 기점이자 종점 | 17 | 3 | 2 |
| 대조군(중간에 놓임) | 30 | — | 20 |

종점 쪽 관측:

```
354000522 봉정사                310번 9분 후
354002045 국립경국대             급행1 1분, 110 4분 (4건)
370002052 정부경북지방합동청사     212번 1분 (5건)
```

ADR-015의 기점 판정은 그대로 맞다 — 기점 전용 7곳이 전부 0건이다.
틀린 것은 **종점을 거기 묶은 것**이다.

### 그래서 조건을 기점 전용으로 좁혔다

```
before  중간 == 0                    → 53곳
after   중간 == 0 && 종점 == 0        → 18곳 (+ 실측 예외 1곳)
```

**34곳이 잘못 분류돼 있었다.** 홈은 그 승강장들을 칩 목록 뒤로 밀고 흐리게 칠하고
"이 승강장은 도착 정보가 뜨지 않아요 · 다른 승강장을 골라 주세요"라고 말하고
있었다. 실제로는 버스가 오는 곳이다.

### 예외 하나는 손으로 적었다

354000536 안동역(안동터미널) — 종점 62 / 기점 4 / 중간 0. 구조만 보면 종점이라
도착이 와야 하는데 **그리로 오는 노선에 26대가 도는 시각에 0건**이었다.
2026-08-13 측정도 같았다. 회차·하차 전용 승강장으로 보이지만 상류가 그 사실을
필드로 주지 않으므로 `MEASURED_EMPTY`에 손으로 적고 근거를 함께 남겼다.

⚠️ 이 목록을 추측으로 늘리지 않는다. **"운행 중인 차가 그 정류장으로 오는데
0건"을 실제로 관측한 승강장만** 넣는다. 근거 없이 넣으면 멀쩡한 승강장이
화면에서 사라지고, 그건 이번에 고친 것과 같은 실수다.

### 꼬리표 문구도 바꿨다

"종점 승강장 · 도착 정보 없음" → "도착 정보가 없는 승강장". 이제 이 꼬리표가
붙는 19곳은 대부분 기점이므로 옛 문구는 사실과 다르다. 어느 쪽인지 말하지 않고
결과만 적는다 — 여행자에게 필요한 것은 그 사실이다.

### 왜 새벽에는 못 쟀나

이 측정은 버스가 도는 시간에만 성립한다. 같은 조회를 01:09에 돌렸을 때는 422개
노선 전부 0대라 모든 정류장이 0건이었고, "종점이라 0"과 "운행이 끝나서 0"을
구분할 수 없었다. 판정을 데이터로 바꾸려면 그 데이터가 살아 있는 시각에 재야 한다.

**회귀 검증**: `node scripts/check-bus-logic.ts` — 종점으로 등장하는 승강장이
걸리지 않는지, 기점 전용이 걸리는지.

## ADR-038 걷는 길도 버스와 잇는다 — 시작점까지는 타고 가고 끝점에서는 타고 돌아온다

**결정일**: 2026-09-10
**상태**: 확정

### 세 탭 중 하나가 서비스의 조직 원리에서 빠져 있었다

이 서비스의 조직 원리는 한 문장이다 — "배차 간격이 길다는 것은 대기 시간이
생긴다는 뜻이고, 그 시간에 주변을 다녀올 수 있다"(ADR-012). 홈과 둘러보기는
그 원리대로 만들어졌는데 **걷는 길만 버스와 이어져 있지 않았다.** 코스 2개,
84줄, 완전 정적. 시작점까지 어떻게 가는지도, 끝점에서 어떻게 돌아오는지도
말하지 않았다.

"걸어서 이어지는 길"이라고 해서 버스와 무관한 것이 아니다. **시작점까지는 타고
가야 하고, 끝점에서는 타고 돌아와야 한다.**

### 이미 만들어 둔 것으로 이어진다

코스의 시작·끝이 전부 관광지 이름이라 `/api/spot-routes`(ADR-036)가 그대로
답한다. 새 엔드포인트도, 새 데이터도 필요 없었다.

```
강변 옛길   안동임청각 → 월영교
달빛 물길   안동민속촌 → 월영교
```

끝점은 `/api/spot-bus`도 함께 부른다. 거기에만 있는 것이 하나 있어서다 —
사람이 확인한 시간표에서 나온 **경고 문장**. 404는 오류가 아니라 "그 관광지는
확인된 7곳이 아니다"라는 뜻이므로 그때는 그 줄을 그리지 않는다(ADR-016).

### 그 경고가 이 화면에서 가장 값이 크다

`달빛 물길`은 `밤` 코스이고 "해 지면 조명이 켜져요"로 끝난다. 그 끝점이 월영교이고,
월영교 막차는 **18:45**다.

> 야경 명소이지만 막차가 18:45다. 해가 진 뒤 방문하면 돌아오는 버스가 없다.

이 서비스는 그동안 **돌아올 수 없는 밤 코스를 안내하고 있었다.** ADR-016이
"갈 수는 있는데 못 돌아오는 안내가 가장 위험하다"고 적어 둔 그 실패가, 정작
그 문장을 쓴 사람이 만든 화면에 있었다.

### 손으로 적은 노선 번호가 틀어져 있었다

`달빛 물길`의 첫 걸음 설명이 **"3번 버스에서 내리면 시작"**이었다. 안동민속촌에
오는 노선은 **112번**이다(실측 2026-09-10). 언제부터 틀렸는지 알 수 없고,
검증할 방법도 없었다 — 데이터에 손으로 적힌 숫자였기 때문이다.

노선 번호를 코스 데이터에서 지웠다. 이제 상류에서 계산해 채운다. 손으로 적으면
또 틀어지고, 틀어져도 아무도 모른다.

### 문구는 관광지 상세와 같은 사전을 쓴다

`t.spotRoutes.routeLabel` · `getOff` · `thenWalk` · `note`를 그대로 쓴다. 같은
사실을 두 화면이 다른 말로 하면 읽는 사람이 다른 것으로 읽는다. 근거를 밝히는
한 줄("직접 확인한 안내는 아니에요")도 같은 문장이다.

### 코스는 버스가 죽어도 남는다

버스 줄만 붙거나 안 붙고, 코스 자체는 그대로 뜬다. 걷는 길은 상류 장애와 무관해야
한다 — 버스가 끊긴 시간대에 여행자에게 남는 유일한 선택지이기 때문이다.

## ADR-039 음식점도 법정동 코드로 — 그리고 분류 근거가 `cat3`에서 `lclsSystm2`로

**결정일**: 2026-09-10
**상태**: 확정 (ADR-034의 마무리 · **ADR-023 일부 정정**)

### 마지막까지 옛 조회에 남아 있던 곳

ADR-034가 관광지를, ADR-035가 축제를 법정동 코드로 옮겼다. 음식점만 남겨 뒀고
그 이유를 이렇게 적어 뒀다 — "늘어나는 12곳이 무엇인지, 향토음식 태깅(ADR-023)이
그 이름들에도 성립하는지 확인하지 않고 옮기면 분류 근거가 흐려진다."

확인했다.

| | 옛 조회 (`areaCode=35`) | 법정동 (`47`/`170`) |
|---|---|---|
| 음식점 | **15건** | **28건** |
| 빠지는 곳 | — | **0곳** |

메모에 적힌 27건도 옛 수치였다. 실제로는 28건이고 13곳이 순증한다.

### 찜닭이 1곳에서 6곳이 됐다

```
밀레니엄안동찜닭 · 안동신세계찜닭 · 원조안동찜닭 본점 · 위생찜닭 · 중앙찜닭
```

**안동의 대표 음식인데 목록에 한 곳뿐이었다.** 그게 취향이나 큐레이션의 결과가
아니라 조회 파라미터 때문이었다. ADR-034에서 하회마을·도산서원이 통째로 빠져
있던 것과 같은 결함이 식도락 탭에도 있었던 것이다.

향토음식 태깅은 **이름 패턴이라 새 이름에도 그대로 성립한다.** 걱정했던 지점은
문제가 아니었다. 진짜 문제는 다른 데 있었다.

### `cat3`가 비어서 온다

새로 들어온 13곳의 분류 필드를 열어 보니:

| 필드 | 옛 15건 | 새 13곳 |
|---|---|---|
| `cat1` · `cat2` · `cat3` | 15/15 | **0/13** |
| `lclsSystm1` · `2` · `3` | 15/15 | **13/13** |

ADR-023은 두 필드 중 `cat3`를 골랐고 근거를 이렇게 적었다 — "둘 중 아무거나
써도 되지만 cat3가 두 API에 공통으로 있으므로 이쪽을 쓴다." 그 전제가 무너졌다.

`cat3`만 보면 **카페 세 곳이 한식으로 분류된다.**

```
브레드 79 (FD05) · 아차가 (FD05) · 월영당 (FD05)  →  cat3='' 이므로 '한식'
```

옛 15건에서 두 필드의 대응은 정확히 1:1이었다(`A05020100↔FD01`,
`A05020900↔FD05`). 그래서 `lclsSystm2`로 옮겨도 **옛 레코드의 분류는 한 건도
바뀌지 않는다.** 새 레코드만 제자리를 찾는다.

둘 다 확인한다 — 어느 한쪽이 비어도 나머지가 답한다. 상류가 `cat3`를 다시 채우거나
옛 조회로 받은 레코드가 섞여 들어와도 무너지지 않는다.

```ts
if (kor.lclsSystm2 === FOOD_LCLS.CAFE || kor.cat3 === FOOD_CAT3.CAFE) return '카페'
```

### 결과

| 분류 | 전 | 후 |
|---|---|---|
| 찜닭 | 1 | **6** |
| 헛제삿밥 | 2 | 2 |
| 한식 | 8 | 13 |
| 카페 | 4 | **7** |
| 영문명 | 2 | **5** |
| 사진 | 9/15 | 17/28 |

### 남은 것

`안동한우갈비`는 여전히 `한식`이다. 이름에 '한우'가 있지만 향토음식 분류표에
'한우'를 넣지 않았다 — 넣기 시작하면 그 근거가 응답 밖에 있게 되고, ADR-023이
막으려던 것이 바로 그것이다. 이름이 스스로 밝히는 것만 태깅한다.

`KOR_SERVICE_REGION`(옛 지역 코드)은 이제 아무도 쓰지 않는다. 지우지 않고
`@deprecated`로 남긴다 — 이 상수가 무엇이었고 왜 물러났는지가 ADR-034·ADR-035·
ADR-039를 잇는 기록이다.

**회귀 검증**: `node scripts/check-spot-match.ts` — `cat3`만 있는 경우,
`lclsSystm2`만 있는 경우, 둘 다 있는 경우를 각각 고정했다.

## ADR-040 실패할 수 있는 것과 오래 사는 것을 같은 캐시에 담지 않는다

**결정일**: 2026-09-10
**상태**: 확정

### 배포본이 영문 이름을 하나도 안 보여주고 있었다

음식점을 법정동 코드로 옮긴 뒤(ADR-039) 배포본을 확인하다 발견했다.

| | 배포본 | 로컬 (같은 코드) |
|---|---|---|
| 관광지 영문명 | **0 / 44** | 17 / 44 |
| 음식점 영문명 | **0 / 28** | 5 / 28 |

`/en/browse`가 도산서원·안동하회마을을 **국문으로** 내보내고 있었다. 영문 화면
전체가 그랬다. 상류(EngService2)는 정상이었다 — 직접 부르면 57건이 온다.

### 원인은 캐시의 경계였다

`attachEnglishNames`는 실패를 조용히 삼키고 원본을 그대로 돌려준다. 이름 한 줄이
본체를 죽이면 안 되므로 그 자체는 맞다. 문제는 **그 호출이 `/api/spots`의 캐시된
본문 안에 있었다**는 것이다.

```
캐시(1일) ─┬─ 관광지 병합 · 사진 보충   ← 오래 사는 것
           └─ 영문 이름 조회            ← 실패할 수 있는 것
```

상류가 한 번 흔들리는 순간 그 빈손이 결과에 섞여 **하루 동안 얼어붙는다.**
경고 로그는 남지만 화면은 조용히 국문으로 나간다. 배포 직후 콜드스타트에
한 번만 걸려도 그날 하루가 그렇게 간다.

### 축제가 이미 답을 갖고 있었다

ADR-035는 같은 자리에서 다르게 했다 — "캐시함: 원본 목록 / 캐시 안 함: 진행 판정.
관광지처럼 결과까지 통째로 캐시하면 자정을 넘겨 '지금 열립니다'가 하루 틀어진다."

같은 처방을 옮긴다.

```
cachedSpots()          목록 · 사진 보충          1일 캐시
attachEnglishNames()   요청 시점                 영문 풀만 따로 1일 캐시
```

영문 풀은 **성공한 것만 캐시된다.** 그 조회 함수 안에서 try/catch를 하지 않는 것이
요점이다 — 던지면 `defineCachedFunction`이 아무것도 저장하지 않고 다음 요청이 다시
시도한다. 실패를 캐시에 넣지 않는다.

요청마다 추가로 도는 것은 44 × 57번의 이름 비교뿐이다. 네트워크는 늘지 않는다.

### 회귀 스크립트가 한 번 잡았다

이 변경의 첫 판에서 `defineCachedFunction`을 모듈 최상위에서 불렀다. `tourApi.ts`는
`scripts/check-spot-match.ts`가 node로 직접 들여오는 파일이라, Nitro 자동 임포트가
없는 그 환경에서 임포트 순간 ReferenceError가 났다.

`pnpm typecheck`는 통과했다. 타입은 전역 선언이 있고 값은 없기 때문이다 —
`26749d1`에서 겪은 것과 같은 계열이다. 첫 호출 때 만들도록 늦췄다.

**이 저장소에서 `typecheck`는 세 환경 중 하나만 본다.** Nuxt 런타임 · Nitro 빌드 ·
node 직접 실행이 각각 다른 것을 요구하고, 셋 다 실제로 깨져 봤다.
`server/utils/` 아래를 건드리면 `pnpm build`와 회귀 스크립트를 같이 돌린다.

## ADR-041 축제 팝업에서 정류장을 걷어낸다 — 고르라고 내밀 수 없는 정보였다

**결정일**: 2026-09-11
**상태**: 확정 (**ADR-035 일부 번복**)

### ADR-035는 "축제를 잇는다 — 열릴 때만, 그리고 버스까지"였다

축제 팝업에 축제장 좌표에서 계산한 최근접 승강장 셋을 띄우고, 고른 승강장의
실시간 도착까지 붙였다. 근거가 계산이라는 사실도 화면에 적어 뒀다
(`festival.stationNote`). 그 정직성은 지금도 맞다고 본다.

문제는 정직성이 아니라 **그 정보로 무엇을 할 수 있느냐**였다.

### 계산이 승강장을 가르지 못한다

ADR-035 자신이 실측을 적어 두고 있었다.

```
탈춤페스티벌 1위  탈춤공원건너  97m   Talchum gong-won
탈춤페스티벌 2위  탈춤공원앞    98m   Talchum gong-won
```

**1m 차이의 반대 방향 승강장이고 영문명이 같다.** 그래서 방면(`direction`)을
붙이고, 칩으로 고르게 하고, 기·종점 승강장은 뒤로 미는 처방을 차례로 쌓았다.
처방이 셋이나 필요했다는 것이 신호였다.

2026-09-10에 관광지 44곳으로 같은 방식을 재봤을 때 답이 나왔다 —
**30곳에서 같은 이름의 승강장이 120m 안에 둘씩 있었고**, 차이가 0m인 곳도 있었다
(이천동석불상 83m / 83m). 거리로는 못 고른다. 관광지에서는 그래서 승강장을
포기하고 **노선**으로 갔다(ADR-036). 축제에는 그 길이 없다 — 축제장은 정류장이
아니라 좌표이고, 노선 색인은 정류장으로 들어간다.

고를 수 없는 것을 셋 늘어놓고 고르라고 하는 화면은 안내가 아니다.

### 그래서 팝업은 축제만 말한다

```
사진 · 이름 · 기간 · D-n · 주소 · 카카오맵으로 길찾기
```

길찾기는 남긴다. 목적지가 승강장이 아니라 **축제장**이라 우리가 못 고르는 판단이
들어가지 않는다. 카카오맵은 출발지를 사용자 기기에서 잡으므로 우리가 좌표를
받을 일도 없다(ADR-024).

### 잃는 것과 얻는 것

잃는 것은 "축제 옆 버스 도착"이다. 작지 않다 — ADR-012가 말한 차별성의 한 조각이다.
다만 그 조각은 그동안 **가장 약한 근거 위에 서 있었다.** 같은 차별성을 관광지
상세는 44곳에서 노선으로, 걷는 길은 갈 때·올 때 노선으로 말한다(ADR-036·038).
셋 중 유일하게 검증되지 않은 것을 덜어낸 것이다.

얻는 것:

- `/api/festivals`가 정류장 목록(2107건)을 더 받지 않는다. 응답 2,560 → **1,352바이트**
- 팝업이 스크롤 없이 축제 셋을 보여준다
- `FestivalArrivals.vue`와 문구 다섯 개가 사라진다

### 되돌린다면

축제장에서 가장 가까운 정류장을 **사람이 확인해** `spot-station-map.json` 같은
매핑으로 두는 길은 남아 있다. ADR-035가 그 길을 접은 이유는 축제가 매년 바뀌어
손 매핑이 못 따라간다는 것이었고, 그 판단도 여전히 맞다. 계산으로도 안 되고
손으로도 안 된다면 **안 하는 것이 맞다.**

## ADR-042 함께 많이 찾는 곳 — 거리로 못 고르는 것을 방문 데이터가 고른다

**결정일**: 2026-09-11
**상태**: 확정

### "근처에 함께 볼 곳"은 거리만 안다

관광지 상세의 그 목록은 `nearest()`가 직선거리로 고른다. 그건 **걸어갈 수 있는가**에
답하는 좋은 방법이고, 차 없는 여행자에게 값이 있다. 다만 답하지 못하는 질문이 있다 —
**사람들이 실제로 무엇을 같이 보는가.** 가깝다고 같이 보는 것이 아니고, 멀어도 같이 본다.

### 여섯 번째 관광공사 API

`TarRlteTarService1/areaBasedList1` — "관광지별 연관 관광지 정보". 활용신청이
이미 승인돼 있었는데 쓰지 않고 있었다.

실측(2026-09-11, `baseYm=202608`):

| | |
|---|---|
| 안동 레코드 | **951건** |
| 우리 44곳 중 데이터가 있는 곳 | **21곳** |
| 관광지당 연관 개수 | 최소 18 · 중앙값 50 |
| 연관 항목 중 우리 목록으로 링크되는 것 | 264 / 951 |

```
안동하회마을 → 월영교 · 병산서원 · 부용대 · 봉정사
봉정사      → 월영교 · 도산서원 · 병산서원 · 안동하회마을
고산정      → 도산서원 · 농암종택 · 선성수상길 · 만휴정
```

데이터가 상식과 맞는다. 그리고 hubRank와 같은 계열의 **행동 데이터**라 이 서비스가
이미 하는 이야기에 그대로 얹힌다.

### 이름으로 잇지 않는다

상류의 `tAtsCd`·`rlteTatsCd`가 **우리 `Spot.id`와 같은 값**이다. 둘 다 LocgoHub
계열의 해시라 그대로 맞는다. 이 프로젝트에서 이름 매칭은 늘 오탐의 원천이었고
(도산서원 ↔ 도산서원선비문화수련원, ADR-033), 그 위험이 여기는 **0**이다.

### 안동 밖은 뺀다

`rlteSignguCd`가 안동이 아닌 항목이 섞여 온다. 걸러낸다. 차 없이 여행하는 사람에게
옆 시군의 관광지를 "함께 찾는 곳"이라고 내밀면 갈 수단이 없다.

우리 목록에 없는 곳(호텔·식당)은 **남긴다.** 링크는 못 걸지만 이름과 분류는 보여준다.
방문 데이터가 말하는 사실이고, 여행자에게는 그것도 정보다.

### 기준월을 고정하지 않는다

`baseYm`이 필수인데 **이번 달은 대개 아직 안 올라와 있다.** 실측: `202609` 0건,
`202608` 951건. 달을 코드에 박으면 언젠가 조용히 빈다. 이번 달부터 최대 6개월을
거슬러 첫 데이터를 쓴다. 하루 캐시라 추가 호출은 사실상 없다.

### 두 목록을 함께 둔다 — 얼굴을 다르게

같은 화면에 장소 목록이 둘이면 왜 두 번 나오는지가 안 읽힌다. 근거가 다르므로
생김새도 다르게 뒀다.

```
함께 많이 찾는 곳   이름 + 분류        (방문 데이터 순)
근처에 함께 볼 곳   사진 + 거리 + 도보  (직선거리 순)
```

위 목록에 이미 나온 곳은 아래에서 뺀다. 하회마을에서 부용대가 두 번 나오던 것이
한 번이 되고, 그 자리에 하회세계탈박물관이 올라온다.

없으면 섹션이 아예 안 뜬다(44곳 중 23곳). 404가 아니라 빈 배열로 답하는 이유도
그것이다 — `/api/spot-bus`의 404는 "아직 확인 못 했다"는 뜻이라 화면이 그 사실을
말해야 하지만, 이쪽은 말할 것이 없다.

## ADR-043 걷는 길에 재료가 없던 게 아니라 우리가 44곳만 보고 있었다

**결정일**: 2026-09-11
**상태**: 확정 (ADR-008 보완)

### 먼저 ADR-008을 다시 확인했다

"걷기 코스를 공공 API에서 가져올 수 없다"는 판단이었다. 이 프로젝트는 같은 모양의
판단을 두 번 틀렸으므로(축제 0건 → 951건, 관광지 63건 → 107건) 다시 쟀다.

| 조회 | 옛 지역 코드 | 법정동 코드 |
|---|---|---|
| 여행코스(contentTypeId=25) | **1건** | **1건** |

"고즈넉한 쉼이 흐르는 안동 1박2일 여행 코스" 하나뿐이고 차량 이동 전제다.
두루누비에 안동이 없다는 것도 2026-08-16에 이미 확인했다.
**이번에는 ADR-008이 맞았다.** 그 질문은 닫는다.

### 그런데 코스가 없는 것과 재료가 없는 것은 다르다

`/walk`이 쓸 수 있는 재료를 세어 봤다.

```
관광지(12)  107건 + 문화시설(14)  26건 = 133곳 · 사진 있는 것 126곳
```

우리 `/api/spots` 44곳은 LocgoHub 인기 순위가 붙은 것만 남긴 목록이라, **걷는 길에
오히려 필요한 작은 곳들이 통째로 빠져 있었다** — 신세동 벽화마을, 법흥사지
칠층전탑, 태사묘, 영호루, 봉정사영산암, 개목사.

실제로 손으로 짠 코스의 지점 6개 중 **5개가 그 133곳 풀에 사진과 함께 있었다.**
데이터가 없던 게 아니라 우리가 좁은 목록만 보고 있었다.

### 좌표를 이으면 동네가 나온다

800m 이내를 이어 연결 요소를 찾으니 3곳 이상 묶음이 **12개** 나온다.

| 곳 | 묶음 | 가장 가까운 정류장 |
|---|---|---|
| 16 | 안동 구도심 — 임청각·칠층전탑·신세동벽화마을·태사묘·영호루 | 웅부공원 39m |
| 9 | 도산·예안 — 선성현문화단지·국학진흥원·호계서원·예끼마을 | 한국국학진흥원 58m |
| 7 | 안동댐 — 낙강물길공원·안동댐·시립박물관·월영교·석빙고 | 공예전시관 36m |
| 6 | 하회 건너편 · 6 내앞마을 · 5 가송 · 4 하회 입구 · 3 봉정사 … | 21~218m |

**12개 중 11개가 정류장 250m 이내다.** 걸어서 이어지는데 버스로도 닿는다.

그리고 손으로 짠 코스 2개는 각각 이 묶음의 일부였다 — '강변 옛길'은 16곳짜리
시내 묶음의 4곳, '달빛 물길'은 7곳짜리 안동댐 묶음의 3곳이다.

가송 묶음(고산정·가송마을·분강서원·맹개마을·농암종택)은 특히 값이 있다.
고산정과 농암종택은 **시내에서 한 번에 가는 버스가 없는 4곳 중 둘**인데(ADR-036),
서로 걸어서 이어진다는 사실이 그 화면에서 가장 필요한 정보다.

### ⚠️ 묶음은 코스가 아니다

좌표가 말하는 것은 **"이것들이 가깝다"까지**다. 순서도 소요 시간도 말하지 않는다.
직선거리로 순서를 정하면 실제 보행로와 어긋나는데, 그건 이 프로젝트가 안 하기로
한 종류의 추정이다(ADR-016).

그래서 두 목록을 나란히 두되 **생김새를 다르게** 했다.

```
코스 2개    점과 선으로 순서를 그린다 · 소요 시간 · 갈 때·올 때 노선   손으로 짰다
동네 12개   이름을 늘어놓기만 한다 · 최대 폭 · 가장 가까운 정류장      좌표가 골랐다
```

"순서와 소요 시간은 정하지 않았어요"를 화면에 적는다. 근거가 다르면 다르다고 말한다.

### 이름은 안에 있는 것을 가리킨다

묶음 이름은 안에서 방문 순위가 가장 높은 곳을 쓴다. 없으면 첫 지점의 이름을 쓴다.

⚠️ 정류장 이름으로 떨어뜨리지 않는다. 처음에 그렇게 했더니 **"주하1 일대"**가
나왔다 — 정류장 번호가 붙은 행정 이름이라 여행자가 읽을 이름이 아니다. 그 묶음의
첫 지점은 "안동 주하리 뚝향나무"다.

상류 이름의 대괄호 꼬리표는 제목에서만 뗀다("안동 하회마을 [유네스코 세계유산]" →
"안동 하회마을"). 지점 목록에는 원래 이름이 그대로 남는다.

### 지도는 하나만

묶음마다 지도를 넣으면 카카오맵 인스턴스가 12개가 되고 화면이 그만큼 무거워진다.
묶음의 중심을 점 하나로 찍으면 "안동 어디에 흩어져 있는가"라는, 이 목록에서 지도가
답해야 할 유일한 질문에 답이 된다.

**회귀 검증**: `node scripts/check-spot-match.ts` — 연결 요소(A–B–C가 한 묶음),
최소 개수, 폭 계산.

## ADR-044 한지 위의 명조 — 기본값을 지우는 것이 디자인이었다

**결정일**: 2026-09-11
**상태**: 확정

### 문제: 화면이 "어디서 본 것"처럼 보였다

기능은 다 붙었는데 화면이 안동을 말하지 않았다. 순백 바탕 · 크게 둥근 모서리 ·
카드마다 그림자 · 제목까지 산세리프. 이건 안동의 얼굴이 아니라 **아무것도 고르지
않았을 때 나오는 얼굴**이다. 프레임워크와 UI 킷의 기본값이 그대로 남아 있으면
어떤 주제를 담아도 같은 화면이 된다.

문화·관광 서비스에서 이건 감점이다. 심사자가 보는 첫 3초에 "이 서비스가 다루는
곳이 어디인가"가 화면에서 읽혀야 한다.

### 결정: 네 가지만 바꾼다

값을 많이 바꾸는 것이 아니라 **기본값을 떠난다**는 것이 요점이다.

| | 전 | 후 | 이유 |
|---|---|---|---|
| 바탕 | `#ffffff` | `#fbfaf6` | 한지. 사진이 순백 위에서 오려낸 것처럼 뜨지 않는다 |
| 먹색 | `#222222` | `#1f1b17` | 중성 회색에서 따뜻한 쪽으로. 회색 계열 전부 같이 옮겼다 |
| 제목 | Pretendard | Noto Serif KR | 부리(serif)가 있는 글자가 목조 건축·서원과 같은 문법이다 |
| 라운드 | 12·16px | 6·10px | 크게 둥글면 앱 UI가 된다. 도록·인쇄물 쪽으로 당긴다 |
| 그림자 | 카드마다 | 헤어라인 한 겹 | 깊이를 그림자가 아니라 선에서 낸다 |

### 명조는 제목에만 쓴다

본문까지 명조로 가면 이 서비스가 죽는다. 여기서 가장 자주 읽히는 것은 **버스 도착
시각과 정류장 이름**이고, 그건 정보 밀도가 높은 짧은 문자열이다. 명조는 그 자리에서
읽기 부담이 커진다. 제목에만 쓰면 인상은 바뀌고 가독성은 그대로다.

폰트 스택도 그래서 이 순서다.

```
'Noto Serif KR', 'Nanum Myeongjo', 'Apple SD Gothic Neo', serif
```

⚠️ 영문 세리프(Georgia·Times)를 앞에 두지 않는다. 제목 대부분이 한글이라 영문
세리프가 먼저 잡히면 한글만 산세리프로 떨어져 **한 줄 안에서 글꼴이 갈린다.**

`display=swap`이라 폰트가 늦게 와도 글자가 먼저 보인다. 구글이 unicode-range로
쪼개 주므로 화면에 실제로 뜬 글자 조각만 내려온다 — 실측으로 weight 600에서
8조각이 받아졌다.

### 붙어 있는 면은 흰색이 아니라 한지다

`--color-paper` 토큰을 따로 뒀다. 헤더와 하단 탭이 순백이면 한지 바탕과 만나는
경계에 **흰 띠**가 생긴다. 반대로 얹혀야 하는 것(검색창 · 축제 시트 · 지도 위
알약)은 흰색으로 남긴다. 거기서는 흰색이 "얹힌 종이"로 읽힌다.

지도 위 마커도 같이 옮겼다. `MapCard`는 SDK에 CSS 변수를 넘길 수 없어 색을 직접
적는데, 그 값이 옛 `#222222`·`#929292` 그대로였다. 지도 이름표만 차가운 회색이면
그 요소만 화면에서 떠 보인다.

### primary는 바꾸지 않았다

`#d9453c`는 그대로다. 로고 자산(`public/logo/`)과 공유 카드가 이 값으로 만들어져
있어서, 화면만 고치면 **화면과 로고가 다른 빨강**이 된다. 색 하나를 바꾸는 일이
아니라 자산을 다시 만드는 일이라 이번 범위 밖이다.

### 곁가지: 걷는 길 지도의 축척

디자인을 보다가 발견했다. `걸어서 이어지는 동네` 지도가 세종과 동해까지 보여 주고
있었다. 묶음 12개는 안동시 전체에 걸쳐 **29km × 33km**로 흩어져 있는데 지도 상자는
1030 × 260px이라, 세로가 먼저 막혀 축척이 세 단계 밀렸다(실측 16km 눈금).

넓은 화면에서만 상자를 키워 정사각형에 가깝게 만든다 —
`clamp(260px, 46vw, 420px)`. 좁은 화면은 상자도 좁아서 이미 세로가 맞는다.

## ADR-045 팝업이 열리면 뒤 화면은 멈춘다 — `<dialog>`가 안 해 주는 하나

**결정일**: 2026-09-11
**상태**: 확정 (ADR-035 · ADR-041 보완)

### 두 가지가 걸렸다

축제 팝업에서 휠을 굴리면 목록 끝에서 스크롤이 **뒤 페이지로 넘어갔다.** 닫고 나면
읽던 자리가 아니라 엉뚱한 곳에 서 있게 된다. 그리고 오른쪽 위의 닫기가 "닫기"라는
**낱말**이라, 제목 옆에 읽을 것이 하나 더 있는 것처럼 보였다.

### 네이티브 `<dialog>`는 스크롤을 막지 않는다

ADR-035에서 네이티브 `<dialog>`를 고른 이유는 Esc·포커스 가두기·inert를 공짜로
받기 위해서였다. 그 판단은 그대로 유효하다. 다만 **배경 스크롤 잠금은 그 목록에
없다** — 직접 붙여야 한다.

### `overflow: hidden`을 쓰지 않았다

가장 흔한 방법이지만 **iOS 사파리에서 듣지 않는다.** 이 서비스는 버스를 기다리며
휴대폰으로 보는 화면이고, 그게 주 환경이다. 주 환경에서 안 되는 방법을 고를 수 없다.

대신 본문을 통째로 띄운다.

```
body { position: fixed; top: -{스크롤위치}px; left: 0; right: 0 }
```

스크롤할 것 자체가 없어진다(`scrollHeight - clientHeight === 0`으로 실측).
대신 두 가지를 되돌려 줘야 한다.

| 부작용 | 대응 |
|---|---|
| 띄우는 순간 맨 위로 튄다 | 음수 `top`으로 붙잡았다가 풀 때 `scrollTo`로 되돌린다 |
| 스크롤바가 사라져 화면이 오른쪽으로 튄다 | 사라진 폭만큼 `padding-right` |

### 닫는 길이 셋인데 잠금은 하나다

X 버튼 · 백드롭 · Esc. 셋 다 `hide()`로 모으고, Esc는 `@cancel`로 들여보낸다.

⚠️ 해제를 `close` 이벤트 **하나에만** 걸지 않는다. `hide()`에서도 한 번 푼다.
두 번 풀어도 아무 일이 없지만(`unlockScroll`이 잠긴 상태만 되돌린다), 한 번도
안 풀리면 **페이지 전체가 굳는다.** 값이 다른 두 실패의 비용이다.
팝업을 연 채 화면을 떠나는 경로(길찾기 링크·뒤로가기)도 있어 `onUnmounted`에도 건다.

### 낱말 대신 ×

문구는 지우지 않고 `aria-label`로 옮겼다. 화면 낭독기는 그대로 "닫기"를 읽는다.
i18n 키(`festival.close`)도 그대로 쓴다 — 자리만 바뀌었다.

**실측(2026-09-11)**: 스크롤 380에서 열고 → 배경 이동 0 → X·백드롭·cancel 세 경로
모두 잠금 해제 + 380 복귀. Esc 키 입력은 자동화 환경이 페이지로 전달하지 못해
`cancel` 이벤트로 대신 확인했다.
