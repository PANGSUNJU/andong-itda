# 설계 결정 기록 (Architecture Decision Record)

안동잇다 개발 과정에서 내린 기술적 판단과 그 근거를 기록한다.
"무엇을 했는가"보다 "왜 그렇게 했는가"를 남기는 것이 목적이다.

---

## ADR-001. 백엔드 서버와 데이터베이스를 두지 않는다

**결정일**: 2026-07-23
**상태**: 확정

### 배경
안동잇다는 공공 OpenAPI를 조합해 정보를 제공하는 서비스다.
원천 데이터를 직접 생산하지 않고, 외부 API의 데이터를 가공·결합해 보여주는 구조다.

### 결정
별도 백엔드 서버(Spring Boot 등)와 RDB를 두지 않는다.
Nuxt 하나로 프론트엔드와 서버 API 라우트를 모두 처리하고, Vercel에 배포한다.

```
브라우저 → Nuxt server/api (프록시 + 캐싱) → 공공 OpenAPI
```

### 근거
- **원천 데이터를 소유하지 않는다.** 관광지·버스 정보는 공공 API가 원본이며,
  이를 DB에 복제해두면 갱신 시점 관리라는 문제만 새로 생긴다.
- **데이터 규모가 작다.** 안동 관광지는 100개 내외 수준으로, DB가 필요한 규모가 아니다.
- **개발 리소스를 핵심 기능에 집중한다.** 1인 개발이고 마감이 정해져 있다.
  서버 구축·배포·운영에 드는 시간을 기능 완성도에 쓰는 편이 심사 배점상으로도 유리하다.
  (심사 기준: 서비스 완성도 30점 = 기획력 30점)

### 트레이드오프
- 응답 속도가 외부 API 성능에 종속된다 → 서버 라우트 캐싱으로 완화
- 외부 API 장애 시 서비스가 함께 영향받는다 → 폴백 UI 필요
- 사용자별 데이터(찜하기 등)를 서버에 저장할 수 없다 → localStorage로 처리

## ADR-002. 서버 API 라우트를 반드시 경유한다

**결정일**: 2026-07-23
**상태**: 확정

### 결정
모든 외부 API 호출은 브라우저에서 직접 하지 않고 Nuxt `server/api`를 경유한다.

### 근거
세 가지 문제가 동시에 해결되기 때문이다.

1. **인증키 보호** — TourAPI 인증키가 클라이언트 번들에 노출되면 안 된다.
   서버에서만 `.env`의 키를 참조한다.
2. **Mixed Content 차단 회피** — 안동시 버스 API(`http://bus.andong.go.kr`)와
   LocgoHub API(`http://apis.data.go.kr`)가 모두 http다.
   https로 배포되는 페이지에서 브라우저가 http 요청을 차단한다.
   서버 간 통신은 이 제약을 받지 않는다.
3. **CORS** — 공공 API 대부분이 브라우저 직접 호출을 허용하지 않는다.

## ADR-003. 원천 데이터는 실시간 호출, 자체 가공 데이터만 정적 관리

**결정일**: 2026-07-23
**상태**: 확정

### 배경
공모전 심사 요건에 다음 조항이 있다.

> 데이터 활용은 한국관광공사 OpenAPI 형태만 인정되며,
> 단순 파일 데이터(Excel, CSV 등) 다운로드 활용은 인정되지 않아 심사에서 제외됩니다.

성능만 생각하면 관광지 데이터를 미리 받아 JSON으로 박아두는 편이 빠르지만,
이는 위 조항에 저촉될 소지가 있다.

### 결정
데이터를 두 종류로 나눠 다르게 취급한다.

| 구분 | 처리 방식 | 예시 |
|---|---|---|
| **공공 API 원천 데이터** | 런타임에 실제 호출 + 서버 캐싱 | 관광지, 음식점, 축제, 버스 도착정보 |
| **자체 생성 가공 데이터** | 정적 JSON 관리 | 관광지↔정류장 매핑 |

캐싱은 성능 최적화이지 데이터 사전 다운로드가 아니다.
매핑 테이블은 TourAPI가 제공하지 않는, 직접 만들어낸 부가가치 데이터다.

### 캐시 정책
| 데이터 | TTL | 근거 |
|---|---|---|
| 버스 실시간 도착 | 캐시 없음 | 실시간성이 기능의 본질 |
| 관광지·음식점 목록 | 6시간 | 변경 빈도 낮음 |
| 중심관광지 순위 | 1일 | 월 1회 갱신(매월 8일) |
| 축제·행사 | 6시간 | 일 단위 변경 |

## ADR-004. 중심관광지 API를 데이터 뼈대로 삼는다

**결정일**: 2026-07-23
**상태**: 확정

### 배경
국문 관광정보 서비스(KorService2)로 안동 데이터를 조회한 결과,
안동의 대표 관광지가 데이터셋에 없다는 문제를 발견했다.

| 조회 | 개수 | 문제 |
|---|---|---|
| KorService2 지역기반 관광지(contentTypeId=12) | 64 | 하회마을·도산서원·월영교 없음 |
| KorService2 지역기반 문화시설(contentTypeId=14) | 12 | 박물관 위주 |

반면 기초지자체 중심관광지 정보(LocgoHubTarService1)에는 전부 존재했다.

> **정정 (2026-08-02)** — 원문에 "키워드 검색(searchKeyword2)으로도 확인되지
> 않았다"고 적었으나 **틀렸다.** `searchKeyword2`로 이름을 검색하면 전부 있고
> 이미지도 전부 있다.
>
> 없는 게 아니라 **`areacode`·`sigungucode`가 빈 값**이라 지역 기반 조회
> (`areaBasedList2`)의 그물에 안 걸리는 것이다. 한국관광공사 쪽 데이터 결함이다.
>
> ```
> 하회마을 894027 · 도산서원 126200 · 월영교 988449
> 병산서원 126227 · 봉정사 126158 · 만휴정 126998   — 전부 areacode ''
> ```
>
> 이 ADR의 **결정 자체는 유효하다.** LocgoHub는 순위를 주고 KorService2는
> 이름 검색이 필요하므로 여전히 LocgoHub가 뼈대다. 다만 "KorService2에는
> 없다"를 전제로 한 서술(아래 ADR-021 포함)은 "지역 조회로는 안 잡힌다"로 읽어야 한다.
> 보충 구현은 `backfillImages()`. → ADR-022 부수 효과

```
1위 안동하회마을 / 2위 월영교 / 3위 병산서원 / 4위 도산서원 / 5위 봉정사
```

### 결정
**LocgoHubTarService1을 관광지 데이터의 뼈대로 삼고,
KorService2를 상세 정보 보강용으로 결합한다.**

### 근거
두 API는 서로의 결핍을 채운다.

| API | 가진 것 | 없는 것 |
|---|---|---|
| LocgoHub | 실제 방문 기반 순위, 좌표, 핵심 관광지 | 설명, 이미지, 운영시간 |
| KorService2 | 설명, 이미지, 주소, 운영시간 | 대표 관광지, 인기도 |

두 API를 결합하는 것 자체가 제안서에서 밝힌 "데이터 융합" 전략의 실현이며,
심사 항목의 데이터 활용 적절성(20점)에 대한 근거가 된다.

### 조인 방법
두 API 사이에 공통 키가 없다.
(LocgoHub: `hubTatsCd` 해시 / KorService2: `contentid`)

좌표와 이름으로 매칭한다.
1. 좌표 거리 200m 이내 AND 이름 유사도 임계값 이상 → 동일 장소로 판정
2. 매칭 성공 → 순위 + 상세정보 병합
3. 매칭 실패 → LocgoHub 단독 표시, 이미지는 폴백 처리

## ADR-005. API별로 지역 코드 체계가 다르다

**결정일**: 2026-07-23
**상태**: 확정 (주의사항)

### 문제
같은 "안동시"를 가리키는 코드가 API마다 다르다.
이를 모르고 호출하면 빈 응답을 받는다.

| API | 파라미터 | 안동시 값 |
|---|---|---|
| KorService2 (국문 관광정보) | `areaCode` + `sigunguCode` | `35` + `11` |
| LocgoHubTarService1 (중심관광지) | `areaCd` + `signguCd` | `47` + `47170` |

파라미터 이름 자체도 다르다 (`areaCode` vs `areaCd`).

### 대응
API별 지역 코드를 상수로 분리해 관리한다.

```ts
// constants/region.ts
export const ANDONG = {
  korService: { areaCode: '35', sigunguCode: '11' },
  locgoHub:   { areaCd: '47',  signguCd: '47170' },
} as const
```

## ADR-006. 버스 도착 시간은 계산하지 않고 API 값을 그대로 쓴다

**결정일**: 2026-07-23
**상태**: 확정 (당초 기획 변경)

### 배경
제안서에서는 "남은 정류장 수 → N분 후 계산"으로 기획했다.
API 명세서에도 응답 필드가 `rstop`(남은정류장), `provideType`(도착예정)으로 기재되어 있다.

### 실제 응답
명세서와 실제 응답 필드가 달랐다.

```json
{
  "routeNum": "212",
  "routeNm": "212(국립경국대-도청)",
  "via": "국립경국대 -> 정부경북지방합동청사",
  "predictTm": 3.0,
  "remainStation": 4
}
```

`predictTm`에 도착 예정 시간이 분 단위로 이미 계산되어 온다.

### 결정
자체 계산 로직을 만들지 않고 `predictTm`을 그대로 표시한다.
`remainStation`은 보조 정보로 함께 노출한다.

### 근거
- 추정 계산보다 운영 시스템의 값이 정확하다
- 계산 로직 자체가 불필요해져 구현 범위가 줄어든다

### 예외 처리
`predictTm`이 null로 오는 경우(차량 위치 미확보)를 대비해
`remainStation` 기반 대체 표시 또는 "곧 도착" 폴백을 둔다.

### 부수 발견
명세서에 없던 `via` 필드(기점 → 종점)가 실제로는 응답에 포함된다.
여행자가 버스 정보에서 가장 혼란스러워하는 "이 버스가 내가 가려는 방향인가"를
해결해주는 정보이므로, 화면에 우선 노출한다.

## ADR-007. 막차·귀로 안내를 실시간 3단 결합으로 구현한다

**결정일**: 2026-07-23 (제외) → **2026-07-29 번복**
**상태**: 확정 (구현)

### 최초 판단 (2026-07-23) — 오류
안동시 버스 API 5개 오퍼레이션 어디에도 운행 시간표·막차 필드가 없다는 이유로
막차 안내 기능을 MVP에서 제외했다.

### 번복 사유 (2026-07-29)
명세서만 보고 판단한 것이 잘못이었다. 노선 목록(`tab=3`)을 실제로 호출해보니
**방향별 노선이 별도 routeId로 등록되어 있었다.**

```
354300006  210(교보생명-하회마을)     ← 가는 편
354300008  210(하회마을-교보생명)     ← 오는 편  ★
354300386  급행3(안동터미널-도산서원)
354300387  급행3(도산서원-안동터미널) ★
```

시간표 문서에 귀로 시각이 생략되어 있었을 뿐,
운행 자체는 왕복으로 등록되어 있었다.

또한 노선 목록 응답에 **`runTotCnt`**(현재 운행 중 차량 수)가 있음을 발견했다.
실제 값을 대조해 의미를 확인했다.

| 노선 | runTotCnt | 검증 |
|---|---|---|
| 급행2 계열 | 0 | 주말 전용 노선, 호출 시점이 수요일이므로 정확 |
| 210 하회 양방향 | 1 | 각 방향 1대 운행 중 |
| 210 병산서원 | 0 | 하루 3회 운행이라 대기 시간대 |
| 순환1 / 110번 | 4 / 5 | 시내 노선이라 다수 |

### 결정
세 소스를 결합해 귀로 안내를 구현한다.

| 정보 | 출처 |
|---|---|
| 지금 오는 버스 | `tab=2` 도착정보의 `predictTm` |
| 오늘 운행 여부 | `tab=3`의 `runTotCnt` |
| 첫차·막차 | 안동시 공공데이터 운행시간표 (정적) |

```
도착정보 있음                 → "12분 후"
도착정보 없음 + runTotCnt > 0 → "접근 중인 버스 없음 · 배차가 길어요"
도착정보 없음 + runTotCnt = 0 → "오늘 운행이 끝났어요" (경고)
```

세 번째 분기가 이 기능의 본질이다.
막차 시각을 알려주는 것보다 **"지금 차가 다니는가"**를 알려주는 것이
여행자의 불안을 실제로 해소한다. 시각을 보여주면 사용자가 계산해야 하지만,
운행 종료를 알려주면 즉시 행동을 바꿀 수 있다.

### 한계
`tab=3` 응답의 `stTm`, `edTm`, `maxInterval`, `minInterval`, `runCnt` 필드는
**전부 null**이다. 안동시가 해당 항목을 입력하지 않았다.
따라서 첫차·막차는 정적 시간표에 의존한다.

### 교훈
**문서보다 실물이 정확하다.**
명세서에 없던 `via`·`predictTm`·`runTotCnt`가 실제 응답에는 있었고,
명세서에 있던 `rstop`·`provideType`은 오지 않았다.
이후 모든 API 판단은 실호출 결과를 기준으로 한다.

## ADR-008. 낙강물길공원 야간 코스 기획을 재검토한다

**결정일**: 2026-07-23
**상태**: 검토 필요

### 발견
LocgoHub 응답에서 해당 장소의 명칭이 다음과 같이 확인된다.

```
"낙강물길공원/공사중(2028년12월31일개장예정)"
```

제안서에서 야간 도보 코스의 핵심으로 제시한 장소가 현재 방문 불가 상태다.

### 대응 방향
야간 코스를 월영교 중심으로 재구성한다.
월영교는 중심관광지 2위이며 야간 조명으로 알려진 곳이다.
인접한 월영공원(76위), 안동민속촌(55위)과 도보 연결이 가능한지 검토한다.

> **두루누비 확인 완료 (2026-08-16)** — 걷기 코스를 공공 API에서 가져올 수 있는지가
> 미해결로 남아 있었다. **가져올 수 없다. 그래서 우리가 만든 코스를 쓴다.**
>
> `Durunubi/courseList` 실측: 전국 **144개 코스**가 전부이고 `routeList`는 **4개**다.
>
> | routeIdx | 노선 | 코스 수 |
> |---|---|---|
> | T_ROUTE_MNG…0001 | 남파랑길 | 31 |
> | T_ROUTE_MNG…0043 | 서해랑길 | 44 |
> | T_ROUTE_MNG…0047 | DMZ 평화의 길 | 30 |
> | T_THEME_MNG…11235 | 해파랑길 | 39 |
>
> 즉 이 API가 담은 것은 두루누비 전체가 아니라 **「코리아둘레길」 하나**다.
> 해안선과 접경을 따라 한반도 외곽을 도는 길이라 **내륙인 안동은 지날 수가 없다.**
> `sigun` 값 57종 중 경북은 경주·포항·영덕·울진 넷뿐이고 전부 동해안이다.
> 제주올레·지리산둘레길·북한산둘레길도 0건이다. 누락이 아니라 수록 범위 밖이다.
>
> ⚠️ `brdDiv`를 어떤 값으로 넣어도 항상 144건이 온다. 파라미터가 먹지 않으므로
> "분류를 바꾸면 더 나온다"는 기대를 하지 말 것.
>
> 문자열 '안동'으로 검색하면 2건이 걸리는데 둘 다 `sigun`이 아니라 본문이다 —
> 파주 코스의 "부인 안동김씨", 화천 코스의 "안동철교". 코스 위치와 무관하다.
>
> 안동 걷기길을 공공 데이터로 얻으려면 두루누비가 아니라 안동시·경북 쪽을 찾아야 한다.

## ADR-010. 축제·행사 연동을 MVP 범위에서 제외한다

**결정일**: 2026-07-23
**상태**: 확정 (당초 기획 변경)

### 배경
제안서에서 야간 도보 코스에 "오늘의 야간 행사"를 함께 안내하도록 기획했다.

### 문제
`areaBasedList2`로 안동 축제/행사(contentTypeId=15)를 조회한 결과 `totalCount: 0`이었다.

주목할 점은, 중심관광지 API(LocgoHub)에는 "차전장군노국공주축제"가 54위로 존재한다는 것이다.
즉 안동에 축제가 없는 것이 아니라, 국문 관광정보 서비스의 축제 데이터셋에
안동 축제가 등록되어 있지 않은 것이다.

### 결정
축제·행사 연동 기능을 MVP에서 제외한다.

### 근거
- 축제는 야간 코스의 **보조** 정보였고, 핵심 기능(버스 안내·주변 탐색·관광지 정보)이 아니다
- 데이터가 없는 기능을 억지로 넣으면 빈 화면만 노출되어 완성도를 오히려 해친다
- ADR-008(낙강물길공원 공사중)로 야간 코스 자체를 재구성해야 하는 상황과 맞물린다

### 향후
축제 데이터가 필요해지면 중심관광지 API의 축제 항목을 활용하거나,
안동시 자체 공공데이터를 검토한다.

## ADR-011. 음식점 데이터 구성

**결정일**: 2026-07-23
**상태**: 확정

### 조회 결과
안동 음식점(contentTypeId=39) `totalCount: 16`.
수는 적지만 제안서에서 목표한 향토음식이 모두 포함되어 있다.

| 향토음식 | 해당 업소 |
|---|---|
| 헛제삿밥 | 맛50년 헛제사밥, 헛제사밥까치구멍집 |
| 찜닭 | 안동 유진찜닭 |
| 간고등어·한식 | 옥야식당, 일직식당, 안동한우갈비 |

### 분류 기준
응답의 카테고리 코드로 탭을 구분한다.

| 코드 | 분류 |
|---|---|
| `lclsSystm2 = FD01` / `cat3 = A05020100` | 향토음식·한식 |
| `lclsSystm2 = FD05` / `cat3 = A05020900` | 카페·베이커리 |

### 이미지 결손
16건 중 7건(약 44%)이 `firstimage` 빈 값이다.
옥야식당, 헛제사밥까치구멍집 등 인지도 높은 업소가 포함되어 있어
카드 UI에서 폴백 이미지 처리가 필수다.

### 보완 방향
중심관광지 API의 안동구시장·중앙신시장을
"식도락 거점"으로 함께 노출해 음식점 수 부족을 보완한다.
제안서에서 언급한 찜닭골목이 곧 안동구시장 일대다.

> **보강 (2026-08-02)** — 구현 전에 재조회했다. 위 수치는 그대로 재현된다
> (16건, 이미지 9/결측 7, `cat3`·`lclsSystm2` 1:1). 다만 세 가지가 추가로 드러났다.
>
> **1. 이미지 결측 7건은 보충할 수 없다.** ADR-022에서 관광지 이미지를
> `searchKeyword2`로 채웠기에 같은 방법을 기대했으나 **0/7이다.**
> 원인이 다르다. 관광지는 지역 조회에 안 잡히는 레코드가 따로 있었지만,
> 음식점은 지역 조회에 정상적으로 잡히고 그 레코드에 이미지가 없다.
> **진짜로 없는 것이다.** 폴백이 유일한 답이고 `SpotPhoto`가 이미 그렇게 돼 있다.
>
> **2. `tel`이 16건 전부 빈 값이다.** `areaBasedList2`는 전화번호를 주지 않는다.
> `FoodPlace.tel`을 정의해 뒀지만 채울 소스가 없다. `detailCommon2`가 필요한데
> 미검증이다. **전화 걸기 UI를 넣지 말 것.** 16곳 전부 빈 버튼이 된다.
>
> **3. 위 분류표는 API가 준 것이 아니다.** API가 주는 구분은 한식(FD01) /
> 카페(FD05) 둘뿐이다. 이름으로 찜닭·헛제삿밥은 판별되지만
> **간고등어(옥야식당·일직식당)는 이름에 안 드러난다.** 이 표는 사람이 아는
> 사실로 만든 것이므로, 코드로 재현하려면 별도 결정이 필요하다.
> **→ ADR-023에서 확정했다.** 이름이 밝히는 찜닭·헛제삿밥만 태깅하고
> 간고등어는 넣지 않는다. 위 표는 사람의 지식으로 남고 코드에는 들어가지 않는다.
>
> ⚠️ 원문의 "안동구시장(21위)·중앙신시장(23위)"에서 순위를 뺐다.
> 202606 실측은 **29위·26위**다. `hubRank`는 매월 바뀐다. → ADR-021

## ADR-012. 화면 구조를 4개 페이지로 확정한다

**결정일**: 2026-07-23
**상태**: 확정

### 설계 기준
이 서비스의 사용 장면은 "여행 계획 단계"가 아니라
**"안동에 도착한 여행자가 현장에서 폰을 꺼내는 순간"**이다.
따라서 화면은 "지금 여기서 무엇을 할 수 있는가"에 즉답하는 구조여야 한다.

또한 데이터 조사 결과, 안동 관광지는 대부분 시내가 아닌 외곽(풍천면·도산면 등)에 있다.
사용자는 두 상태 중 하나이며 화면은 양쪽을 모두 커버해야 한다.

| 상태 | 필요한 것 |
|---|---|
| A. 시내에 있음 | 도보권 장소 + 다음 목적지로 가는 버스 |
| B. 외곽 관광지에 있음/가려 함 | 해당 관광지 정보 + 오가는 버스 |

### 화면 구조

```
[지금 여기]  홈 — 미니맵 / 가까운 정류장 버스 / 도보권 장소 / 인기 관광지
[둘러보기]   목록 — 관광지·식도락 탭, 리스트↔지도 토글
  └ 상세     관광지 상세 — 정보 + 지도 + 여기 가는 버스
[도보 코스]  낮·밤 코스
```

### 홈 화면의 정보 우선순위
**버스를 최상단에 배치한다.**

제안서의 핵심 인사이트는 "배차 간격이 길다 = 대기 시간이 생긴다 =
그 시간에 주변을 즐길 수 있다"이다.
이를 화면 순서로 그대로 옮긴다.

1. 가까운 정류장의 다음 버스 (몇 분 후)
2. 그 시간 안에 걸어서 갈 수 있는 곳
3. 안동 인기 관광지 순위

### 관광지 상세 화면의 차별점
관광지 정보와 버스 안내를 **한 화면에** 배치한다.

기존 안동 서비스들은 교통 정보(안동버스정보 앱)와 관광 정보(안동을 담다, 안동관광)가
분리되어 있어 여행자가 앱을 오가야 했다.
이 화면이 제안서에서 밝힌 차별성의 실체다.

### 폴백
위치 권한 거부 또는 안동 외 지역인 경우, 안동역을 기준 위치로 사용한다.

## ADR-013. 지도를 도입하되 전면 지도 UI는 채택하지 않는다

**결정일**: 2026-07-23
**상태**: 확정

### 결정
카카오맵을 도입하되, 지도 중심 UI가 아니라 필요한 화면에 부분 배치한다.

| 위치 | 형태 | 목적 |
|---|---|---|
| 홈 | 미니맵 (높이 200px 내외) | 현재 위치·정류장·주변 관광지 위치감 |
| 관광지 상세 | 위치 지도 | 관광지 ↔ 가까운 정류장 거리 시각화 |
| 둘러보기 | 리스트↔지도 토글 | 전체 분포 파악 (기본값은 리스트) |

### 근거
**지도를 넣는 이유** — 안동 관광지는 시내와 외곽에 흩어져 있어,
리스트만으로는 "이게 걸어갈 거리인지 버스를 타야 하는지" 감이 오지 않는다.
위치 기반 서비스의 핵심 가치가 전달되지 않는다.

**전면 지도 UI를 피하는 이유** — 마커 클러스터링, 바텀시트, 지도-리스트 상태 동기화 등
개발량이 크게 늘어난다. 모바일에서는 정보 밀도도 리스트가 더 높다.
1인 개발·기한 제약 하에서 핵심 기능 완성도(심사 30점)를 지키는 편이 낫다.

### 지도 선택
카카오맵을 사용한다.
- 국내 지도 데이터 정확도가 높다
- 스크립트 로드 방식이 단순해 Nuxt 통합 부담이 적다
- 무료 할당량이 서비스 규모에 충분하다

> **구현 (2026-08-02)** — JavaScript 키를 발급받아 `MapCard`에 실제 지도를 붙였다.
> 위 표에서 하나가 달라졌다. **둘러보기의 리스트↔지도 토글은 만들지 않았다.**
> 우측 지도가 상시 노출되고 목록 필터를 그대로 따라가므로 토글이 가리킬 상태가 없다.
> 칩으로 '카페'만 걸러 놓으면 지도에도 5곳만 남는다. 토글은 두 화면이 서로
> 다른 것을 보여줄 때 필요한 장치인데, 여기서는 둘이 같은 것을 본다.
>
> **처음에는 지도를 조작할 수 없게 했다**(`draggable: false`, `setZoomable(false)`).
> 스크롤을 지키려는 것이었다.
>
> **정정 (2026-08-13)** — 이동·확대·축소를 연다. 고정된 그림으로는 "이게 걸어갈
> 거리인가"를 카드 안에서 확인할 수 없어 결국 지도 앱으로 나가게 된다. 전면 지도
> UI를 안 쓴다는 결정과 카드 크기는 그대로다. 조작만 열었다.
>
> 스크롤은 다른 방법으로 지킨다. **휠 줌만 끈다**(`scrollwheel: false`).
> 데스크톱에서 카드 위 스크롤이 확대로 바뀌면 페이지가 그 자리에 붙잡힌다.
> 휠을 껐으니 줌 수단이 더블클릭뿐이 되지 않도록 `ZoomControl`을 붙였다.
> 모바일은 한 손가락 드래그가 지도 이동이 된다 — 카드 높이(200~340px)만큼
> 페이지 스크롤을 내준 셈이고, 이동이 되는 값으로 그만큼을 지불한다.
>
> 마커는 기본 핀을 쓰고, 홈의 중심(=사용자 위치)만 원과 점으로 따로 그린다.
> 중심을 마커로 그리면 관광지 마커와 모양이 같아져 어느 것이 나인지 알 수 없다.
>
> ⚠️ **키가 있어도 도메인이 등록되지 않으면 지도는 안 뜬다.**
> 카카오는 등록되지 않은 출처에 SDK 대신 401을 준다.
> 실측(2026-08-02): `caller=http://localhost:3123` → `AccessDeniedError: domain mismatched`.
> **포트까지 본다.** 콘솔 > 앱 설정 > 플랫폼 > Web에 쓰는 주소를 그대로 등록해야 한다.
> 실패는 조용하므로 `MapCard`가 "지도를 불러오지 못했어요"로 구분해 보여준다.
> "지도 준비 중"(키 없음)과 다른 문구다. 둘을 같은 말로 덮으면 원인을 못 찾는다.
>
> ⚠️ **지도를 붙이면 좌표가 카카오로 나간다.** 둘러보기·상세는 관광지 좌표뿐이라
> 무관하지만, 홈의 반경 원은 사용자 위치를 넘긴다. 위치정보 취급 범위가 여기서
> 한 번 넓어진다는 사실을 남겨 둔다.

## ADR-014. 찜하기 기능을 MVP에서 제외한다

**결정일**: 2026-07-23
**상태**: 확정 (후순위 이관)

제안서 발전 방향에 "사용자 맞춤 내 여행 저장 기능"을 포함했다.

MVP 범위에서 제외하고, 핵심 기능 완성 후 여유가 있으면 구현한다.

| 354000701 | 하회보건진료소 | 시내→하회 종점 | ✅ 210번 25분 후 |
| 354002046 | 하회보건진료소 | 하회→시내 기점 | ❌ 빈 배열 |

기점 정류장은 "접근 중인 차량"이라는 개념이 성립하지 않으므로
도착정보 API가 항상 빈 배열을 반환한다.

### 결정
관광지마다 정류장을 두 개씩 매핑하되 용도를 나눈다.

- **inbound** — 실시간 도착정보 조회에 사용
- **outbound** — 도착정보 조회 불가. 정적 시간표와 `runTotCnt`로 대체

`data/spot-station-map.json`에 `realtimeAvailable: false`로 명시한다.

### 주의
관광지에서 나가는 편은 원리적으로 실시간 조회가 불가능하다.
"들어온 차가 회차해서 나간다"는 사실과 계획 시간표로 안내하며,
**정확한 출발 시각을 추정해 단정하지 않는다.**
부정확한 교통 정보는 여행자를 정류장에 세워둔다.

## ADR-016. 버스 시간표는 정적 파일로, 관광 데이터는 API로 관리한다

**결정일**: 2026-07-29
**상태**: 확정 (ADR-003 보완)

### 배경
공모전 심사 요건은 "한국관광공사 OpenAPI 형태만 인정"이다.
이 조항은 관광공사 API 활용을 필수로 요구하는 것이며,
다른 출처의 보조 데이터를 파일로 쓰는 것을 금지하지 않는다.

관광공사 API 활용은 LocgoHubTarService1과 KorService2로 이미 충족했다.

### 결정
안동시 공공데이터포털의 시내버스 운행시간표 엑셀을 정적 데이터로 활용한다.

### 파싱 방식
4개 파일, 42개 시트, 166개 정류장 컬럼을 수확했다.
시트마다 컬럼 구조가 전혀 달라 완전 파싱을 포기하고
**첫차·막차·운행횟수만** 추출하는 방식을 택했다.

파싱상 마주친 문제들:
- 시트별 헤더 구조 상이 (`구분` 열이 없는 시트가 4개)
- 시각 형식 혼재 (`datetime.time`, `"06:40"` 문자열이 한 시트에 공존)
- 셀 안에 경로 설명 문장이 들어 있음
- 시트별 시행일 상이 (파일명은 26.8.1이나 210번은 24.1.5 기준)
- 조건부 운행 규칙 (급행2는 8월·축제기간 한정)

### 발견된 구조적 한계
공식 시간표는 **안동 기준으로만** 작성되어 있다.
생활 노선(610 길안, 512 도산, 임하)에는 "○○에서 안동출발" 컬럼이 있으나
**관광 노선(210 하회, 310 봉정사, 112 안동댐)에는 없다.**

주민 통근 노선은 귀로가 필요하니 적었고, 관광 노선은 그 배려가 없었다.
이 공백 자체가 제안서의 문제의식("정보가 흩어져 있어 동선을 짜기 어렵다")을
실증하는 근거다.

### 화면에서 경고해야 할 위험 정보
- **병산서원** — 하루 3회, 마지막 도착 15:30. 오후 출발 시 방문 불가
- **월영교** — 야경 명소이나 막차 18:45. 조명 점등 시각에 버스가 끊긴다

## ADR-017. 개발 환경 — 경로에 비ASCII 문자를 두지 않는다

**결정일**: 2026-07-30
**상태**: 확정 (환경 제약)

### 증상
`pnpm install`이 정상 종료되었으나 `pnpm dev` 실행 시
`'nuxt'은(는) 내부 또는 외부 명령... 아닙니다` 오류가 발생했다.
`package.json`은 정상이었고 의존성 591개도 설치되어 있었다.

개발 폴더 경로는 영문으로 유지한다.

## ADR-018. 공공 API 인증키는 한 번 디코딩해서 쓴다

### 배경
`/api/spots` 첫 구현에서 LocgoHub·KorService2가 모두 401 Unauthorized를 반환했다.
키는 `.env`에 정상적으로 들어 있었다.

### 원인
data.go.kr은 인증키를 **Encoding**과 **Decoding** 두 형태로 발급한다.
`.env`에 담겨 있던 값은 Encoding 키였다(96자, `%` 이스케이프 포함, 디코딩하면 88자).
이걸 그대로 쿼리 파라미터로 넘기면 ofetch가 직렬화하며 한 번 더 인코딩해
`%`가 `%25`가 된다. 서버는 존재하지 않는 키를 받는다.

실측(2026-07-30, KorService2 areaBasedList2):

| 전달 방식 | 결과 |
|---|---|
| 원문 그대로 (재인코딩 없음) | 200 OK |
| `encodeURIComponent` 적용 | **401 Unauthorized** |
| 디코딩 후 재인코딩 | 200 OK |

### 결정
키를 한 번 `decodeURIComponent`로 원문화해 보관하고,
인코딩은 쿼리 직렬화 단계에 딱 한 번만 맡긴다. (`server/utils/tourApi.ts`)

### 근거
Encoding 키와 Decoding 키 **어느 쪽을 붙여넣어도 동작한다.**
Decoding 키에는 `%`가 없어 디코딩이 무연산이기 때문이다.
키 형태를 사람이 기억해야 하는 설계는 다른 PC에서 반드시 한 번 더 틀린다.
유효하지 않은 이스케이프가 섞인 키는 디코딩이 실패하므로 원문을 그대로 쓴다.

### 기록 사유
PROJECT-PROMPT §2에는 "Decoding 키 사용"이라고 적혀 있으나
실제 `.env`에 들어 있던 값은 Encoding 키였다.
401은 키가 틀렸다는 신호로 읽히기 때문에 원인을 엉뚱한 데서 찾게 된다.

## ADR-019. 안동시 버스 API는 https로 직접 호출한다

### 배경
지시서와 타입 주석 모두 베이스를 `http://bus.andong.go.kr/m01/s04.do`로 적고 있고,

## ADR-020. 관광지 통합 정보의 시간표는 spot-station-map.json에서 가져온다

### 배경
`/api/spot-bus/[spot]`의 `schedule` 필드를 채울 소스가 두 개다.
`server/data/timetable-spots.json`(엑셀 파싱 원본)과
`server/data/spot-station-map.json`의 `timetable` 필드.

### 문제
`timetable-spots.json`은 `SpotTimetable` 타입과 구조가 맞지 않는다
(`routes[].times[]` + `summary` 형태). 게다가 내용이 어긋난다.

| 관광지 | map의 `returnTimesKnown` | timetable-spots의 `hasReturnTimetable` |
|---|---|---|
| 안동하회마을 | false | **true** |
| 봉정사 | false | **true** |
| 도산서원 | **true** | false |
| 병산서원 | false | false |

원인은 두 가지다. `timetable-spots.json`은 주말·8월 한정 급행2를 귀로 시간표로 세고,
정작 도산서원의 온혜발 귀로(07:50~20:40)는 파싱에서 놓쳤다.
수록 범위도 5곳뿐이라 만휴정·임청각이 없고, 월영교는 "안동댐·월영교"로 이름이 다르다.
월영교 운행 횟수도 원본은 9회(10:30·12:50 중복)지만 정리본은 7회다.

### 결정
`spot-station-map.json`의 `timetable`을 유일한 소스로 쓴다.
`timetable-spots.json`은 그 원본으로 남기고 런타임에서 읽지 않는다.

### 근거
`spot-station-map.json`의 `timetable`은 파싱 원본을 사람이 검증·정리한 결과이고,
타입상으로도 `SpotTimetable` 그 자체라 무변형으로 내려보낼 수 있다.
파싱 산출물을 그대로 쓰면 중복 시각과 계절 노선이 막차 정보에 섞인다.

`returnTimesKnown: false`인 관광지의 귀로 시각은 추정해서 채우지 않는다.
부정확한 막차 정보는 여행자를 정류장에 세워둔다. → ADR-016

## ADR-021. 두 관광 API의 조인은 좌표를 1순위, 이름을 게이트로 쓴다

### 배경
ADR-004에서 좌표 + 이름으로 매칭하기로 정했으나 구체적 기준은 미정이었다.

### 결정
1. LocgoHub 좌표에서 **200m 이내** KorService2 후보를 거리순으로 세운다
2. 이름 유사도 **0.4 이상**인 것 중 가장 가까운 항목을 택한다
3. 통과하는 후보가 없으면 병합하지 않고 LocgoHub 단독으로 표시한다

이름 비교 전에 `안동` 접두어와 괄호를 제거한다
(`안동하회마을`→`하회마을`, `개목사(안동)`→`개목사`).
그 외에는 2-gram Dice 계수를 쓴다. 유사도 라이브러리는 도입하지 않았다.

좌표 필드명이 서로 다르다. LocgoHub는 `mapX`/`mapY`(대문자), KorService2는
`mapx`/`mapy`(소문자)이며 **양쪽 다 문자열로 온다.** 숫자 변환이 필요하다.

### 근거 — 이름을 보조 게이트로 둔 이유
거리만으로는 틀린다. 실측에서 **안동시립박물관의 최근접 항목은 1m 거리의
"안동민속촌"이었다.** 이름 게이트가 이를 걸러내고 87m 거리의 정답
(contentid 129772)을 골랐다. 같은 방식으로 오매칭 9건을 막았다.

거리를 1순위로 둔 이유는 그 반대다. 이름 표기는 데이터셋마다 흔들리지만
좌표는 흔들리지 않는다. 이름을 1순위로 두면 접두어 차이에서 먼저 무너진다.

### 실측 결과 (2026-07-30, baseYm 202606)
- 숙박 36건 제외 후 64건 중 **19건 병합** (주소 19, 이미지 18)
- ADR-004에 적어둔 알려진 겹침 4건 전부 매칭:
  안동시립박물관↔129772, 이육사문학관↔2721929,
  하회세계탈박물관↔130150, 체화정↔1621549

### 알게 된 것 — 결측 범위가 문서보다 넓다
KorService2 **지역 조회로** 안 잡히는 것이 하회마을·도산서원·월영교만이 아니다.
**병산서원·봉정사·안동역·만휴정·부용대도 없다.**
최근접 항목이 287m~2.4km 거리에 유사도 0이라 반경을 넓혀도 해결되지 않는다.
인기 상위 6곳이 전부 LocgoHub 단독 표시이므로 **이미지 폴백 UI가 상위권에서 바로 필요하다.**

> **정정 (2026-08-02)** — "반경을 넓혀도 해결되지 않는다"는 맞지만,
> 결론이 "그러니 폴백뿐"은 아니었다. 반경이 아니라 **조회 방식**을 바꿔야 했다.
> `searchKeyword2`로 이름을 검색하면 이 6곳이 전부 이미지까지 딸려 온다.
> → ADR-004 정정, ADR-022

### 알게 된 것 — hubRank는 매월 바뀐다
202606 기준 1위 월영교, 2위 안동하회마을로 지시서 기록(1위 하회마을)과 다르다.
알려진 겹침 4건의 순위도 25→31, 36→45, 59→56, 86→63으로 이동했다.
순위를 코드나 정적 데이터에 하드코딩하지 않는다.

## ADR-022 여행자 목록의 노이즈는 이름 패턴으로 걷어낸다

**결정** — LocgoHub 목록에서 골프장·영화관·교통시설·체육시설·도매시장을
이름 패턴으로 제외한다. 구현은 `noiseReason()`이고 `fetchHubSpots`에서 숙박
필터(ADR-009) 바로 옆에 건다.

### 문제
LocgoHub는 통신사 방문 데이터 기반이라 "사람이 많이 간 곳"을 준다.
그건 "여행자가 갈 만한 곳"과 다르다. 실측(202606) 상위권이 이렇다.

```
 6위 안동역        10위 안동터미널     17위 남안동CC
19위 안동레이크GC   20위 리버힐CC       21위 CGV/안동
```

방문 데이터로서는 정확한 결과다. 안동역에는 실제로 사람이 많이 간다.
하지만 "안동에서 뭘 하지?"에 대한 답으로 CGV를 6번째로 내미는 목록은 못 믿는다.

### 왜 카테고리로 자르지 않는가
상류 분류가 목적과 어긋난다.

| 카테고리 | 걷어낼 것 | 남길 것 |
|---|---|---|
| 문화관광 | CGV/안동, 롯데시네마 | 하회세계탈박물관, 이육사문학관 |
| 레저스포츠 | 남안동CC, 리버힐CC | 선성수상길, 유교랜드 |
| 쇼핑 | 안동수산물도매시장 | 중앙신시장, 안동구시장 |

카테고리를 자르면 양쪽이 같이 날아간다. 남길 것이 더 중요한 항목들이다.

### 왜 이름 패턴인가
무딘 도구지만 여기서는 그게 맞다.

1. 걷어낼 대상이 **전부 이름에 정체를 드러낸다.** CC·GC·시네마·역·구장·도매시장
2. 무엇이 왜 빠졌는지 **읽어서 감사할 수 있다.** 분류 코드는 그게 안 된다
3. 오탐이 나면 이름만 보고 즉시 안다

슬래시 앞부분으로만 판정한다. 뒤까지 보면 "한국국학진흥원/KSI연수원"이
엉뚱한 패턴에 걸리고 "안동퇴계예던길/1코스"도 위험하다.

전통시장(중앙신시장·안동구시장·구담시장)은 남긴다. 여행자가 실제로 간다.
도매시장만 뗀다.

### 실측 결과 (2026-08-02, baseYm 202606)
**64건 → 49건. 15건 제외, 오탐 0건.**

```
교통시설 3   안동역, 안동터미널, 옹천역/폐역
골프장   3   남안동CC, 안동레이크GC, 리버힐CC
영화관   2   CGV/안동, 롯데시네마/프리미엄안동
체육시설 4   안동드림베이스볼파크, 안동강변구장,
             용상체육공원/야구장, 안동시생활체육공원
도매시장 3   안동시농산물도매시장, 안동수산물도매시장, 안동청과합자회사
```

### 부수 효과 — 이미지 결측률이 함께 내려간다
제외한 15건 중 14건이 이미지가 없던 항목이다. 당연하다.
**역과 골프장에 관광 사진이 없는 것이 정상이다.**
노이즈 필터와 이미지 결측은 같은 문제의 두 얼굴이었다.

이미지 보유율 **61% → 76%**. 백필 대상이 줄어 첫 요청도 16초 → 11초로 짧아졌다.

### 한계
이름에 정체가 안 드러나는 것은 못 거른다. `웨이블리`(91위),
`플레이방월드`(51위)가 남아 있다. 패턴 목록은 앞으로 늘어날 텐데,
**새 항목을 넣기 전에 실제 응답에서 오탐부터 확인할 것.**
회귀는 `node scripts/check-spot-match.ts`가 지킨다.

## ADR-023 음식점 분류는 응답에서 다시 만들 수 있는 것만 쓴다

**결정일**: 2026-08-02
**상태**: 확정

**결정** — `foodCategory`를 `찜닭 | 헛제삿밥 | 한식 | 카페` 네 값으로 한다.
앞의 둘은 **상호에서 읽어내고** 뒤의 둘은 API의 `cat3`를 옮긴다.
간고등어는 넣지 않는다. 구현은 `foodCategoryOf()`이고 `/api/food`가 쓴다.

### 문제
API가 주는 구분은 한식(FD01) / 카페(FD05) 둘뿐이다.
그런데 이 탭의 이름은 "식도락"이고, 안동에서 그 말은 찜닭·헛제삿밥·간고등어를 뜻한다.
16곳을 한식 11 / 카페 5로만 내놓으면 탭이 존재할 이유가 없어진다.

ADR-011은 분류표를 적어 뒀지만 그건 **API가 아니라 사람이 아는 사실로 만든 것**이었다.
옥야식당이 간고등어집이라는 정보는 응답 어디에도 없다.

### 선택지
| | 방법 | 문제 |
|---|---|---|
| 1 | 한식/카페 2분류만 | 정직하지만 향토음식이라는 색이 사라진다 |
| 2 | **이름 패턴 + API 2분류** | 간고등어를 놓친다 |
| 3 | 16곳 정적 매핑 | 정확하지만 출처가 사람이고 손으로 관리한다 |

**2번을 택했다.** 기준은 정확도가 아니라 **근거가 어디 있느냐**다.

1번은 가진 정보를 버린다. 찜닭·헛제삿밥은 상호가 스스로 밝히고 있는데
그걸 안 읽을 이유가 없다.

3번은 정확하다. `spot-station-map.json`이라는 선례도 있다. 하지만 그 파일에는
"임의로 채우지 말 것"이라는 조건이 붙어 있었고, 그건 **좌표로 검증할 수 있었기
때문에** 지킬 수 있는 조건이었다. 간고등어에는 대조할 원본이 없다.
검증 못 하는 사실을 코드에 박으면 다음 사람은 그게 어디서 왔는지 알 수 없다.

### 규칙
```
cat3 = A05020900        → 카페      API가 직접 답한 것이라 이름 추측보다 앞선다
title에 '찜닭'          → 찜닭      안동 유진찜닭
title에 '헛제사밥|헛제삿밥' → 헛제삿밥  맛50년 헛제사밥, 헛제사밥까치구멍집
그 외                   → 한식
```

상호 표기가 '헛제**사**밥'이고 분류명이 '헛제**삿**밥'이다. 둘 다 받는다.
표기를 하나만 잡으면 영원히 0건인 칩이 남는다.

카페 판정을 먼저 한다. 한식/카페는 API가 직접 준 답이므로 이름 추측보다 강하다.
향토음식 태깅은 그 한식 안에서만 한다.

### 결과 (2026-08-02 실측, 16건)
```
찜닭     1   안동 유진찜닭
헛제삿밥 2   맛50년 헛제사밥, 헛제사밥까치구멍집
한식     8   옥야식당, 일직식당, 안동한우갈비, 신라국밥, 효자통닭,
             황소곳간, 농가맛집 뜰, 묵향
카페     5   맘모스베이커리, 카페뒤뜰, 폴모스트, 396커피컴퍼니, 월영당
```

**옥야식당·일직식당이 '한식'에 있는 것은 버그가 아니라 결정이다.**
여기를 '간고등어'로 고치고 싶어진다면 그 근거가 응답 밖에 있다는 뜻이다.
회귀는 `node scripts/check-spot-match.ts`가 지킨다.

### `/api/food`가 `/api/spots`와 다른 점
| | `/api/spots` | `/api/food` |
|---|---|---|
| 소스 | LocgoHub + KorService2 병합 | KorService2 단독 |
| 순위 | `hubRank` | **없다** (LocgoHub에 음식점이 없다) |
| 이미지 보충 | 46건 중 21건 채움 | **안 한다** (0/7) |
| 첫 요청 | 약 11초 | 2~3초 |

이미지 보충을 붙이지 않는 이유는 결측의 원인이 다르기 때문이다.
관광지는 `areacode`가 빈 값이라 지역 조회에 안 잡히는 레코드가 따로 있었지만,
음식점은 지역 조회에 정상적으로 잡히고 **그 레코드에 이미지가 없다.**
조회를 몇 번 하든 없는 건 없다. 44% 결측은 `SpotPhoto` 폴백이 받는다.

순위가 없으므로 "인기순" 토글도 만들지 않는다. 없는 축을 비활성 버튼으로
남겨두지 않는다. 기본 정렬은 분류 순서(`FOOD_CATEGORY_ORDER`)이고
향토음식을 앞에 세운다.

### 화면
- 칩은 `FOOD_CATEGORY_ORDER` 상수에서 만든다. 관광지 탭과 반대다.
  거기는 분류가 상류의 것이라 응답에서 만들었고, 여기는 우리가 정의한
  닫힌 집합이라 상수에서 만든다. 단, 0건인 분류는 칩을 띄우지 않는다
- 칩 선택 상태를 탭마다 따로 둔다. 하나로 묶으면 '역사관광'을 고른 채
  식도락으로 넘어갔을 때 사용자가 건 적 없는 필터로 0곳이 뜬다
- **카드에 상세 링크를 붙이지 않는다.** `/spots/[id]`는 `/api/spots`에서 id를
  찾는데 음식점은 거기 없어 404가 된다. 갈 곳 없는 링크를 만들지 않는다
- **전화 버튼을 넣지 않는다.** `tel`이 16건 전부 빈 값이다 → ADR-011
- 사진 없는 카드가 7곳이라 목록 아래에 이유를 한 줄 적는다.
  폴백이 고장으로 보이면 안 된다

### 한계
새 음식점이 등록되고 그 상호에 '찜닭'이 없으면 '한식'이 된다.
패턴 목록은 늘어날 텐데 **추가 전에 실제 응답의 `title`부터 확인할 것.**
상호에 없는 단어를 넣으면 영원히 0건인 칩이 생긴다.

## ADR-024 사용자 좌표는 브라우저 밖으로 내보내지 않는다

**결정일**: 2026-08-06
**상태**: 확정

**결정** — 좌표를 파라미터로 받는 서버 라우트를 두지 않는다.
`/api/spots/nearby`와 `/api/bus/nearby-stations`를 삭제하고, 목록을 통째로
내려보낸 뒤 브라우저에서 `nearest()`로 고른다.

### 문제
법적 검토 과정에서 코드가 문서와 다르다는 것이 드러났다.
"좌표는 브라우저 메모리에서만 쓰고 서버로 보내지 않는다"고 적어 뒀지만
실제로는 이런 요청이 나가고 있었다.

```
GET /api/spots/nearby?lat=36.5684&lng=128.7294&radius=30000&limit=12
GET /api/bus/nearby-stations?lat=36.5684&lng=128.7294&limit=5
```

`useFetch`의 `query`가 `computed`라 `locate()`가 성공하는 순간 실제 GPS 좌표로
재요청이 나간다. 그리고 **쿼리스트링은 요청 URL의 일부라 배포 로그에 남는다.**
DB가 없다는 것과 로그가 없다는 것은 다른 이야기였다.

이 구조에서는 「위치정보의 보호 및 이용 등에 관한 법률」상 사업자가 위치정보를
'수집'한 것으로 볼 여지가 생긴다. 제9조 위치기반서비스사업 신고 대상이 되면
제40조에 따라 3년 이하 징역 또는 3천만원 이하 벌금이 걸린다.
계정이 없으니 개인위치정보가 아니라는 주장도 가능하지만, 로그에 IP와 좌표가
한 줄로 남는 이상 다툼의 여지가 크다. 다투지 않는 쪽을 택한다.

### 왜 서버에서 계산했었나
두 라우트의 주석이 이유를 적어 두고 있었다.

- `nearby-stations` — 정류장 전체가 1.86MB다. 브라우저로 내려보낼 수 없다
- `spots/nearby` — 하버사인을 클라이언트에 두 번째로 구현하게 된다

**둘 다 사실이 아니었다.**

`walkMinutes`는 이미 `#shared`에 있었고 `distanceMeters`만 `server/utils`에
있었다. 옮기면 구현은 한 벌이다.

크기는 재 봤다 (2026-08-06 실호출, 2107건).

| | raw | gzip |
|---|---|---|
| 14필드 전부 | 1,479 KB | 125 KB |
| 4필드 | 165 KB | 39 KB |
| 4필드 + 좌표 5자리 | **153 KB** | **31 KB** |

1.86MB의 정체는 안 쓰는 필드 10개(다국어명 3종·BIT ID·카드번호 등)와
소수점 10자리 좌표였다. 화면이 쓰는 건 `stationId`·`stationNm`·좌표뿐이다.
31KB면 사진 한 장이다.

### 선택지
| | 방법 | 문제 |
|---|---|---|
| 1 | 사업 신고 + 약관 + 동의 절차 | 신고·약관·동의·확인자료 보관이 전부 따라온다. 무료 공모전 출품물에 붙일 무게가 아니다 |
| 2 | 좌표를 뭉개서 전송 | 소수점 2자리(1.1km)면 최근접 정류장이 바뀐다. 정밀도를 지키면 여전히 개인 위치다. 법적으로 애매한 채로 남는다 |
| 3 | **목록을 내려보내고 브라우저가 계산** | 31KB를 더 받는다 |

**3번을 택했다.** 31KB로 쟁점 자체가 사라진다.

### 구조
- `distanceMeters`를 `server/utils/tourApi.ts`에서 `shared/constants/location.ts`로 옮겼다
- `nearest(items, from, { radius, limit })`를 같은 파일에 두었다. 정류장과 관광지가
  같은 함수로 돈다 — 그래서 `/api/bus/stations`가 상류의 `gpsX`/`gpsY`를
  `lat`/`lng`으로 바꿔 내보낸다
- `stationId` 중복 제거를 `stations` 라우트로 옮겼다. 캐시되는 자리라 한 번만 돈다
- 상세 화면의 "근처에 함께 볼 곳"은 자기 자신을 **먼저** 뺀다.
  나중에 빼던 기존 코드는 4곳을 고른 뒤 3곳만 남기고 있었다
- SSR은 그대로다. 첫 렌더는 안동역 폴백 기준으로 계산되고, 브라우저에서 좌표가
  잡히면 같은 `computed`가 다시 돈다. 네트워크 요청은 추가로 나가지 않는다 → ADR-012 유지

### 남는 것
**좌표 발자국이 0이 되지는 않는다.** 홈의 `MapCard`가 사용자 좌표를 지도 중심으로
받고, 카카오맵 SDK가 그 중심으로 타일을 요청한다. 우리 서버에서 지워도 카카오에는 간다.
지도를 쓰는 모든 서비스가 같고 카카오는 등록된 사업자지만, "좌표가 아무 데도 안 간다"고
쓰면 거짓말이다. 안내 문구에 지도 사용을 밝힌다.

법 해석에 다툼의 여지가 있는 부분도 남는다. 단말 내 처리만으로도 위치기반서비스에
해당한다는 해석이 문언상 불가능하지 않다. 위치정보지원센터 서면 질의 항목으로 남긴다.

### 검증
`node scripts/check-spot-match.ts` — `nearest`의 거리순 정렬·반경 컷·개수 제한과
원본 배열 불변을 확인한다. 홈의 두 목록이 전부 이 함수 하나로 돈다.

## ADR-025 도착 버스가 닿는 관광지는 노선상 순번으로 판정한다

**결정일**: 2026-08-07
**상태**: 확정

**결정** — 도착정보에 그 버스가 닿는 관광지를 붙인다. 판정 근거는
`routeId` 일치 **그리고** `arrival.stationOrd < spot.stationOrd`다.
순번을 확인하지 못한 관광지는 표시하지 않는다.

### 문제
홈은 "212번 12분 후"까지만 말했다. 화면에 있던 `via`는 노선의 기점 → 종점이라
종점이 우연히 관광지일 때만 읽혔다. 종점이 안동터미널이면 그 버스가 도산서원을
지나는지 알 방법이 없었다.

상세 화면은 "하회마을 가려면 뭘 타나"에 답하는데, 홈은 그 반대인
"지금 오는 이 버스가 어디로 가나"에 답하지 못했다. 두 화면을 잇는 것이
이 서비스의 주장이므로 그대로 둘 수 없다.

### 왜 routeId만으로는 안 되는가
같은 노선이어도 내 정류장이 관광지보다 뒤면 그 버스는 이미 지나쳤다.
"→ 하회마을"을 잘못 붙이면 여행자를 반대 방향 버스에 태운다.
ADR-015·ADR-016이 일관되게 거부해 온 종류의 거짓말이다.

그래서 순번을 비교한다. `BusArrival.stationOrd`(내 정류장의 노선상 순번)는
이미 응답에 오고 있었고, 관광지 쪽 순번만 없었다.

### 순번을 채우는 방법
`spot-station-map.json`에 `stationOrd`가 적혀 있던 것은 7곳 중 2곳(월영교·임청각)뿐이었다.
나머지는 `tab=4`(노선별 정류장)를 노선 수만큼 불러 `stationId`로 찾는다.
`tab=4`는 그동안 한 번도 쓰지 않은 오퍼레이션인데 `BusRouteStation` 타입에
`stationOrd`가 이미 정의되어 있었다.

1일 캐시한다. 노선의 정류장 순서는 시간표만큼도 자주 바뀌지 않는다.
도착정보는 캐시하지 않는 핫 패스이므로 이 조회가 거기 얹히면 안 된다.

### 실측 (2026-08-07, 7곳)
```
OK(기재)  월영교                     ord=7
OK(기재)  안동임청각·법흥사지칠층전탑   ord=3
OK(조회)  안동하회마을                ord=52 / 노선정류장 53
OK(조회)  만휴정                     ord=59 / 노선정류장 60
MISS      병산서원   route=354300007 station=354002027
MISS      봉정사     route=354300060 station=354002024
MISS      도산서원   route=354300386 station=354001832
```

### MISS 3건의 원인 — 매핑 데이터 오류다
세 곳 모두 `inbound.stationId`에 **나가는 편 노선의 기점 정류장 ID**가 들어가
있다. 들어오는 편 노선에는 그 ID가 아예 없다.

| 관광지 | 기재된 ID | 실제 위치 | 들어오는 편의 진짜 정류장 |
|---|---|---|---|
| 병산서원 | 354002027 | outbound ord=1 | `354000711` @ ord 57 |
| 봉정사 | 354002024 | outbound ord=1 | `354000522` @ ord 32 |
| 도산서원 | 354001832 | outbound ord=1 | `354001831` @ ord 64 |

**파장이 이 기능 밖에 있다.** `ord=1`은 기점이고, 기점 정류장의 도착정보는
항상 빈 배열이다(ADR-015). `/api/spot-bus/[spot]`이 실시간 도착을 조회하는
대상이 바로 이 `inbound.stationId`이므로, 세 곳의 상세 화면은 실시간 도착이
계속 비어 있었을 것이다. 이 기능이 아니었으면 드러나지 않았다.

### 3건을 고쳤다 (2026-08-07)
`spot-station-map.json`을 위 표대로 정정했다. 이 파일에는 "임의로 채우지 말 것"이
붙어 있지만, 여기서 넣은 값은 추측이 아니라 상류 `tab=4` 노선 정류장 목록에서
읽은 것이므로 그 금지에 걸리지 않는다. 근거는 위 표에 남아 있다.

```
병산서원   stationId 354002027 → 354000711   stationOrd 57 추가
봉정사     stationId 354002024 → 354000522   stationOrd 32 추가
도산서원   stationId 354001832 → 354001831   stationOrd 64 추가
           stationNm "도산서원(서원)" → "도산서원"
```

도산서원은 이름도 함께 고쳤다. `354001832`(나가는 편 기점)의 상류 표기가
"도산서원(서원)"이었을 뿐, 들어오는 편 정류장 `354001831`의 이름은 "도산서원"이다.
ID를 바꾸면서 이름을 그대로 두면 다음 사람이 대조할 때 어긋난다.

정정으로 `stationOrd`가 적힌 곳이 2곳에서 5곳이 됐다. `tab=4`를 실제로 부르는
대상은 하회마을·만휴정 2곳만 남았다.

### 정정 뒤 실측 (2026-08-10 월 10:09~10:19)
상류 `tab=4`로 세 정류장이 각 노선에 실존함을 먼저 확인했다. 순번은 위 표와 일치하고,
**셋 다 들어오는 편 노선의 종점**이었다. 기점(`ord=1`)을 조회하던 것을 종점으로 고친 셈이다.

```
병산서원  354000711  ord 57 / 노선 정류장 58 (마지막 순번 57)
봉정사    354000522  ord 32 / 노선 정류장 33 (마지막 순번 32)
도산서원  354001831  ord 64 / 노선 정류장 64 (마지막 순번 64)
```

도착정보(`tab=2`)를 옛 ID와 새 ID로 각각 불러 비교했다.

| 관광지 | 옛 ID | 새 ID | 노선 runTotCnt |
|---|---|---|---|
| 병산서원 | 0건 | 0건 | 0 (미운행) |
| 봉정사 | 0건 | 0건 | 0 (미운행) |
| 도산서원 | 0건 | **1건** | 1 (운행 중) |

**도산서원이 결정적이다.** 같은 시각 같은 노선인데 옛 ID는 0건, 새 ID는 급행3 1건이
잡혔다(`predictTm` 33분 → 21분, `remainStation` 32 → 18로 접근이 이어졌다).
버그는 해소됐다.

병산서원·봉정사가 0건인 것은 정정과 무관하다. 두 노선 모두 `runTotCnt=0`,
즉 그 시각에 도는 차가 없었다(ADR-015의 `closed`). 옛 ID였다면 운행 중이어도
영원히 0건이었을 것이므로 이 0건과는 의미가 다르다. 다만 **두 곳은 운행 시간대에
다시 확인해야 확증된다.** 210은 하루 3회다. → 미해결 과제

`/api/spot-bus/도산서원`도 `status=arriving`, `arrivals=1`, `runTotCnt=1`로 정합했다.

### 표시 규칙
- 순번을 확인하지 못한 관광지는 담기지 않는다. 빈 배열이 "닿는 곳이 없다"와
  "판정하지 못했다"를 구분하지 못하지만, 화면은 둘 다 아무것도 표시하지 않으므로
  구분할 이유가 없다. 틀린 것을 보여주지 않는 쪽이 기준이다
- 상세 화면(`SpotBusPanel`)에는 붙이지 않는다. 이미 목적지를 알고 들어온
  화면에서 "이 버스가 어디로 가는지"를 다시 말할 이유가 없다
- 한 노선의 `tab=4`가 실패해도 나머지는 살린다. 여기서 던지면 도착정보 전체가
  502가 된다. 부가 정보가 본체를 죽이면 안 된다

## ADR-026 같은 이름의 승강장은 "방면"으로 가르고, 도착이 없는 승강장은 뒤로 보낸다

**결정일**: 2026-08-13
**상태**: 확정

### 문제
홈의 정류장 칩에 **"안동역(안동터미널)"이 셋 나란히** 떴다. 이름·거리만으로는
어느 승강장에 서야 하는지 고를 수 없다. 게다가 그중 하나는 도착 정보가 늘 비었고,
그 승강장이 첫 화면에 기본 선택되고 있었다 — 기본 좌표(`ANDONG_ORIGIN`)가
하필 그 승강장의 좌표였기 때문이다. 서비스의 첫 문장이 "버스가 없어요"였다.

정류장 2105곳 중 **1644곳이 다른 정류장과 이름이 같다.** 특수한 사례가 아니다.

### 결정
카카오·네이버가 쓰는 것과 같은 꼬리표를 붙인다. **방면 = 노선상 다음 정류장의 이름.**
그리고 도착정보가 원리적으로 오지 않는 승강장은 목록 맨 뒤로 보낸다.

| stationId | 방면 | 판정 |
|---|---|---|
| 354000416 | 노하동입구 | 기점 59 / 중간 31 → 정상 |
| 354000459 | 송야교사거리 | 기점 5 / 중간 47 → 정상 |
| 354000536 | (하이마삼거리) | 종점 62 / 기점 6 / **중간 0** → 도착 없음 |

카카오맵 표기(`노하동 입구 방면` · `송야교사거리 방면`)와 일치한다.

### 방면을 구하는 방법
상류는 방면을 주지 않는다. 노선별 정류장 목록(`tab=4`)에서 직접 센다.

⚠️ **바로 다음 정류장을 그냥 집으면 안 된다.** 승강장이 여러 개인 곳은 다음 순번도
이름이 같아서 "안동역(안동터미널) 방면 안동역(안동터미널)"이 나온다.
**이름이 다른 첫 정류장**까지 건너뛴다. 노선마다 다음이 갈리면(지선 분기)
최다 득표 하나만 남긴다. 여럿을 붙이면 칩이 문장이 된다.

### 정적 파일로 굽는 이유
노선이 **421개**다. 요청 시점에 계산하면 상류를 421번 부른다. 캐시가 비는 첫 요청이
그 값을 다 치르므로 안 된다. `node scripts/build-station-directions.ts`로 미리 구워
`server/data/station-directions.json`에 둔다. 노선의 정류장 순서는 시간표만큼도
자주 바뀌지 않는다(ADR-016과 같은 판단). 노선 개편 때 다시 돌리면 된다.

### 도착이 없는 승강장 — 지우지 않고 뒤로 보낸다
**노선 중간에 한 번도 놓이지 않는 정류장**은 기점이거나 종점으로만 쓰인다.
그런 승강장에는 "접근 중인 차량"이 성립하지 않아 `tab=2`가 항상 빈 배열이다(ADR-015).
전체 2105곳 중 42곳이 해당한다.

지우지 않는 이유 — 실재하는 승강장이고, 거기 서 있는 사람에게는 "여기는 안 뜬다"는
사실 자체가 답이다. 목록에서 없애면 그 사람은 자기가 선 자리를 찾다가 화면을 닫는다.
대신 뒤로 밀어 기본 선택에서 빠지게 하고, 칩과 카드가 이유를 말한다.
**`실시간` 배지도 끈다.** 실시간이 원리적으로 없는 자리에서 점이 뛰면 기다리게 된다.

### 대가
응답이 164KB → 201KB(gzip 38KB → 47KB). 브라우저가 목록을 통째로 받기 때문이다(ADR-024).
이름이 겹치는 정류장이 1644곳이라 "겹치는 것만 붙이기"로 아껴 봐야 gzip 2KB다.
나눌 이유가 없어 전부 붙였다.

회귀는 `node scripts/check-bus-logic.ts`가 지킨다 — 같은 이름 건너뛰기와
기·종점 전용 판정 두 가지다.

## ADR-027 화면에서 끊지 않는다 — 길찾기·새로고침·되돌리기

**결정일**: 2026-08-14
**상태**: 확정

### 문제
화면마다 사용자가 더 할 수 있는 일이 없는 막다른 곳이 있었다.

| 자리 | 막다른 지점 |
|---|---|
| 홈 지도 | 움직일 수 있게 해 놓고 되돌아올 방법이 없다 |
| 홈 지도 | 승강장이 안 찍힌다. 이름이 같은 셋을 글자로만 갈라야 한다 |
| 홈 정류장 | "안동역(안동터미널)"까지 왔는데 **거기로 걸어가는 길**이 없다 |
| 홈 위치 | 권한을 거부하면 이유 한 줄이 남고 다시 시도할 수단이 없다 |
| 도착 카드 | "실시간" 점만 뛴다. 언제 받은 값인지, 다시 받을 방법이 없다 |
| 상세 | 자동 갱신 타이머가 아예 없어 열어 두면 값이 그대로 늙는다 |

### 결정
- **되돌리기** — `MapCard`에 "처음 화면으로". `draw()`에서 화면 맞추기를 `fit()`으로
  떼어내 데이터 갱신과 버튼이 같은 함수를 쓴다
- **정류장 마커** — 홈 지도에 정류장을 함께 찍는다. 관광지는 핀, 정류장은 점이다.
  고른 승강장만 채운 점과 방면 이름표로 도드라진다(ADR-026의 연장). 지도는 도보권
  관광지 섹션 밖으로 꺼냈다 — 그 목록이 비는 위치에서는 지도까지 함께 사라졌다
- **길찾기** — 카카오맵 `link/to`로 넘긴다. 홈은 정류장까지, 상세는 관광지까지.
  목적지만 넘기면 출발지는 앱이 현재 위치로 잡으므로 사용자 좌표를 URL에 싣지 않는다
  (ADR-024와 어긋나지 않는다)
- **실시간 배지** — `RealtimeBadge`로 묶어 도착 카드 둘이 함께 쓴다.
  갱신 시각("방금" · "3분 전")과 새로고침이 배지에 붙는다
- **위치 재시도** — 폴백 사유 옆에 "내 위치로 다시". 확인 중일 때는 그 문구를 보여준다
- **마커 이름** — 상용 지도처럼 마커 옆에 이름을 **인쇄해 둔다**. 기본 마커의 `title`은
  데스크톱 호버 툴팁이라 폰에서는 아무 일도 없었고, 지도에 점만 찍히고 그게 뭔지 알 수
  없으면 지도가 아니라 무늬다. 말풍선이 아니라 흰 테두리를 두른 글자다 — 마커마다 흰
  상자가 뜨면 지도가 상자로 덮인다.
  누르면 뜨는 이름표도 함께 남긴다(정류장은 방면까지 붙어 "안동역(안동터미널) ·
  노하동입구 방면"). 빈 곳이나 "처음 화면으로"를 누르면 닫힌다

### 이름을 몇 개까지 인쇄할 것인가
마커가 **9개 이하일 때만** 인쇄한다(`LABEL_LIMIT`). 둘러보기는 마커가 49개까지 가는데
전부 인쇄하면 글자가 서로를 덮어 아무것도 안 읽힌다. 상용 지도는 겹침을 계산해 솎아내지만
그건 이 카드가 할 일이 아니다. 개수로 끊고, 많을 때는 눌러서 보게 한다.
상세(최대 5개)는 늘 인쇄되고, 홈은 도보권 관광지 수에 따라 갈린다.

### 시각을 SSR에서 만들지 않는다
`updatedAt`은 `onMounted`에서만 채운다. 서버 시각으로 "방금"을 찍으면 하이드레이션이
어긋나고, 서버와 사용자의 시계가 다를 수도 있다. SSR에서는 시각 없이 배지만 나간다.

### 상세의 배지는 도착이 없을 때도 남긴다
예전에는 `status === 'arriving'`일 때만 띄웠다. 그런데 다시 확인하고 싶은 순간은
정확히 "접근 중인 버스가 없어요"를 봤을 때다. 새로고침이 배지에 붙어 있으므로
그때 사라지면 안 된다.

### 상류 문자열을 innerHTML에 넣지 않는다
이름표는 `document.createElement` + `textContent`로 만든다. 정류장·관광지 이름은
상류(안동시·관광공사)가 준 문자열이다. 지도 라벨 하나 때문에 남의 데이터를
실행시킬 이유가 없다. `CustomOverlay`는 문자열 대신 DOM 요소를 받으므로 비용도 없다.
(마커 클릭은 `maps.event`로 붙지만 **CustomOverlay에는 지도 이벤트가 안 붙는다** —
정류장 점은 DOM `addEventListener`로 건다)

### ⚠️ CustomOverlay는 좌표에 가운데 정렬된다
정류장 점을 `transform: translate(-11px,-11px)`로 당겼다가 되돌렸다. SDK가 이미
content를 좌표 중심에 붙이므로 두 번 밀린다(기존 "나" 점에 transform이 없는 이유).
이름표는 `absolute`로 띄운다 — 상자 크기가 점 그대로여야 중심이 이름표 길이만큼
밀리지 않는다.

## ADR-028 상류가 종점을 안 준다 — 방면은 routeNm에서 건지고, 없으면 말하지 않는다

**결정일**: 2026-08-14
**상태**: 확정

### 사건
화면에 `청호한우촌앞 -> · 11정거장 전`이 떴다. 화살표 뒤가 비어 있고 점만 남았다.

`formatDirection`은 `via`("기점 -> 종점")에서 종점만 잘라 "○○ 방면"을 만든다.
종점이 비면 **via를 그대로 돌려주도록** 되어 있었다. 그 폴백이 화면에 새어 나온 것이다.

**상류가 조용히 바뀌었다.**

| 날짜 | via 실측 |
|---|---|
| 2026-08-13 | `"정부경북지방합동청사 -> 국립경국대"` |
| 2026-08-14 | `"정부경북지방합동청사 -> "` — 표본 50건 **전부** 종점 없음 |

ADR-006이 "명세서를 신뢰하지 말 것"이라 했는데, 이번엔 **실측한 응답조차 하루 만에
바뀐다**는 게 드러났다. 필드가 사라진 게 아니라 값만 비었으므로 타입 검사로는 안 잡힌다.

### 결정
1. **`routeNm`에서 건진다.** `"610(만휴정-길안-국립경국대-교보건너-안동터미널)"` —
   괄호 안 마지막 토큰이 종점이다. 같은 응답에 이미 들어 있어 추가 호출이 없다
2. **via가 우선한다.** 상류가 다시 채우면 그쪽이 정본이다
3. **둘 다 없으면 빈 문자열**을 돌려주고 화면은 **줄을 통째로 지운다.**
   앞 문구가 없으면 구분점(·)도 찍지 않는다. 점만 남으면 그게 고장으로 보인다

폴백으로 원문을 흘리지 않는다. 사람이 읽을 수 없는 조각을 보여주느니 아무것도
안 보여주는 편이 낫다. 이건 ADR-016("추정한 막차를 보여주지 않는다")과 같은 규칙이다.

`/api/spot-bus`는 도착 4필드만 내려보내고 있어 `routeNm`을 추가했다. 화면에 그대로
뜨는 값이 아니라 방면을 건지는 재료다.

### 같은 노선의 다음 차
"이 버스를 놓치면 얼마나 기다리나"에 답한다. 정류장에는 여러 노선이 서므로 목록의
다음 줄은 대개 **다른 노선**이다. 같은 번호를 찾아야 답이 된다. 목록이 이미 도착
임박순이라 앞에서부터 첫 번째로 만나는 같은 번호가 그 차다.

실측(2026-08-14): 염광교회앞 — 212번 3분 후, 그다음 212번 11분 후.
표본 21곳 중 4곳에서 같은 노선 2대가 동시에 잡혔다. **드물다.**
없으면 아무것도 말하지 않는다. 배차 간격을 추측해 채우지 않는다 — 추측한 다음 차는
막차 추정과 같은 종류의 거짓말이다.

회귀는 `node scripts/check-bus-logic.ts`가 지킨다(via 우선 · routeNm 폴백 · 빈 문자열).

## ADR-029 사진은 공공데이터 API 안에서만 구한다 — 세 단계, 그리고 https

**결정일**: 2026-08-16
**상태**: 확정

### 원칙
관광 이미지는 **공공데이터 API에서만** 가져온다. 다른 웹사이트를 긁지 않는다.
출처를 밝힐 수 없는 사진은 이 서비스에 실을 수 없기 때문이다(→ `/about` 데이터 출처).

### 세 단계
전부 한국관광공사 API다. 뒤로 갈수록 증거가 약해지므로 순서를 바꾸지 않는다.

| 단계 | 서비스 | 근거 | 성과 |
|---|---|---|---|
| 1 | KorService2 `areaBasedList2` | 좌표 200m + 이름 | 54곳 중 41곳 병합 |
| 2 | KorService2 `searchKeyword2` | 이름(areacode 빈 항목 구제) | 결측 46 → 21건 보충 |
| 3 | **PhotoGalleryService1** `gallerySearchList1` | 이름 + 촬영장소 | +1건 |

### 3단계를 붙인 이유와 한계
**한계부터.** 결측 14곳 중 채운 것은 **1곳(부용대)뿐이다.** 나머지 13곳은
행사·신규시설·상호(안동수페스타·플레이방월드·빙수곳간·드론코리아아카데미…)여서
공공데이터 어디에도 사진이 없다. 조회를 늘려도 안 나온다.

그럼에도 붙이는 이유는 **KorService2가 흔들릴 때 남는 유일한 사진 소스**이기 때문이다.
실측: 안동 사진 1504건 중 관광지 54곳 가운데 17곳이 이름으로 걸린다.

⚠️ **관광지마다 부르지 않는다.** `keyword=안동`으로 한 번 받아(1000건) 이름을 맞춘다.
개별 호출은 14번인데 한 번에 받는 편이 싸고, 제목에 없는 이름이 태그(`galSearchKeyword`)에
있는 경우까지 잡는다. 부용대가 그렇게 걸렸다 — 사진 제목은 "안동하회마을"이다.

⚠️ **이 서비스에는 좌표가 없다.** 1·2단계처럼 거리로 검증할 수 없어서
`galPhotographyLocation`에 '안동'이 있는 것만 남긴다. 동명이소를 거를 유일한 수단이므로
이 조건을 빼면 안 된다.

### ⚠️ 상류가 http와 https를 섞어 준다 — 배포에서만 터진다
실측(2026-08-16): 관광지 사진 41장 중 **23장이 `http://`**, 갤러리는 1000건 중 883건이다.
배포는 https이므로 그대로 두면 그 절반이 **Mixed Content로 차단된다.**
개발(`http://localhost`)에서는 멀쩡히 보이므로 눈으로는 절대 안 잡힌다.

같은 경로를 https로 요청하면 동일한 이미지가 200(image/jpg)으로 열리는 것을 확인했다.
호스트는 `tong.visitkorea.or.kr` 하나뿐이다.

이미지가 들어오는 자리가 넷(지역 병합·키워드 보충·갤러리·음식점)이라 대입하는 쪽마다
고치지 않고 `httpsImage()` 한 곳을 지나가게 했다. 새 소스를 붙일 때도 그 함수를 통과시킬 것.
